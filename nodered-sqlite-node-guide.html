1. 概要：なぜデータを貯めるのか

センサーの値を Debug サイドバーに出すところまでは、Inject と Debug だけでできる。ところが現場で「先週の平均は」「あの停止は何時何分だったか」と聞かれた瞬間に、流れていった値は取り戻せない。

値を残す方法は 3 段階ある。

方法 できること 限界
context 変数 直前の値との比較、カウンタの保持 メモリ上のため再起動で消える。ファイル保存を設定しても、大量の履歴を持つ用途には向かない
ファイル（CSV） 追記していく記録、表計算ソフトへの受け渡し 「直近 1 時間の平均」のような絞り込みは、全行を読んで自分で計算することになる
データベース（SQLite） 条件を指定した絞り込み、期間集計、古い行の削除 SQL という別の言語を覚える必要がある

SQLite を選ぶ理由は、データベースサーバーを別に立てなくてよい点にある。ファイルが 1 つあればそれがデータベースであり、Node-RED と同じ機械の中で完結する。工場の現場に置いたエッジ機器で「まずデータを貯める」を始めるとき、追加のサーバーもネットワーク設定も要らないという条件は大きい。

使い分けの目安
1 台の機器で数十万件までを扱い、そこで集計まで済ませるなら SQLite で足りる。複数拠点のデータを 1 か所に集め、長期のトレンドを何年も保持するなら、時系列データベース（InfluxDB など）やサーバー型のデータベース（PostgreSQL など）が向く。SQLite はその手前の、最初の一歩を踏み出すための選択肢である。

2. インストール方法

サードパーティノードは Node-RED エディターの「パレットの管理」から導入する。手順は追加ノード共通である。

  1. 右上のメニュー（三本線）から「パレットの管理」を開く
  2. 「ノードを追加」タブを選ぶ
  3. 検索欄に node-red-node-sqlite と入力する
  4. 「ノードを追加」ボタンを押す
  5. 完了後、左のパレットの storage カテゴリに sqlite ノードが現れる

コマンドから入れる場合は、Node-RED のユーザーディレクトリ（通常は ~/.node-red）で次を実行する。

cd ~/.node-red npm i node-red-node-sqlite
導入に時間がかかる
このノードは内部で sqlite3 というネイティブモジュール（C 言語で書かれ、環境ごとにコンパイルが要る部品）を使う。公式 README によれば、Raspberry Pi のような機器ではビルドに 15 分から 20 分かかることがある。画面が止まったように見えても、完了するまで待つこと。
Node.js を更新したら再ビルドが要る
ネイティブモジュールは Node.js の版に結びついている。Node.js を上げたあとにノードが読み込めなくなった場合は、ユーザーディレクトリで再ビルドする。
cd ~/.node-red npm rebuild
v2.x では環境によってビルド済みバイナリが用意されておらず、GLIBC_2.38 not found のような読み込みエラーが出ることがある。その場合は sqlite3 のディレクトリで直接再ビルドする。
cd ~/.node-red/node_modules/sqlite3 npm run rebuild

3. SQLite の基礎知識

データベースはファイル 1 つ

MySQL や PostgreSQL は常駐するサーバープログラムであり、接続にはホスト名やポート、利用者名が要る。SQLite にはサーバーがない。/home/pi/data/sensor.db のようなファイルが 1 つあり、プログラムがそのファイルを直接読み書きする。バックアップはそのファイルをコピーするだけで済む。

テーブルと列

データは表（テーブル）の形で入る。列（カラム）にはあらかじめ名前と型を決めておく。測定値を貯めるなら、次のような形になる。

readings テーブル id | ts | name | value -----+------------------------+---------------+-------- 1 | 2026-08-09T10:00:00Z | temperature | 22.4 2 | 2026-08-09T10:01:00Z | temperature | 22.6 3 | 2026-08-09T10:01:00Z | humidity | 48.0

この表を作る SQL が CREATE TABLE である。

CREATE TABLE IF NOT EXISTS readings ( id INTEGER PRIMARY KEY AUTOINCREMENT, ts TEXT NOT NULL, name TEXT NOT NULL, value REAL );

IF NOT EXISTS を付けておくと、すでに表があるときは何もしない。フローを起動するたびに実行しても壊れないため、初期化用の Inject と組み合わせやすい。

型の扱いがゆるい

SQLite の型は、他のデータベースほど厳密ではない。列に INTEGER と書いても、文字列を入れると入ってしまう。使う型は実質 5 種類である。

型用途
INTEGER整数。カウント、UNIX 時刻
REAL小数。温度、電流値
TEXT文字列。センサー名、日時（ISO 8601 形式）
BLOBバイナリ。画像など
NUMERIC上記に当てはめて解釈される汎用型
日時専用の型はない
SQLite に日付型や時刻型は存在しない。実務では次の 2 通りのどちらかに決めて、混在させないことが重要になる。
  • TEXT で ISO 8601（2026-08-09T10:00:00.000Z）：そのまま読めるので調査が楽。同じ形式どうしなら、文字列の大小比較がそのまま時刻の前後比較になる
  • INTEGER で UNIX 時刻（ミリ秒）：計算が速く場所も取らないが、人が読めない
本ガイドは読みやすさを優先して TEXT の ISO 8601 で統一する。ただし比較する相手の形式をそろえないと誤判定が起きる。この落とし穴はセクション 7 で扱う。

書き込みは 1 つずつ

SQLite はファイルにロックをかけて書き込む。同じファイルを複数のプログラムから同時に書き込もうとすると待たされ、混み合えばエラーになる。Node-RED から 1 つのデータベース設定ノードを通して使う限り問題にならないが、別のプログラムから同じファイルを書きに行く構成は避けるほうがよい。

4. ノード構成

SQLite は 2 種類のノードで構成される。

sqlite（処理ノード）

フローに置いて SQL を実行する。入力 1、出力 1。実行結果は msg.payload に配列で返る。

sqlitedb（設定ノード）

データベースファイルの場所と開き方を持つ。フロー上には現れず、sqlite ノードの設定画面から作る。複数の sqlite ノードで共有できる。

inject → function → sqlite → debug

6. SQL クエリの 4 モード

4 つのモードは「SQL をどこから渡すか」と「値の埋め込みを安全に処理するか」で分かれる。ここが SQLite ノードで最初に迷うところである。

モード SQL の場所 値の渡し方 結果
msg.topic経由 msg.topic msg.payload の配列（条件つき、後述） msg.payload に行の配列
固定文 ノードの「SQL文」欄 渡せない（SQL は固定） msg.payload に行の配列
事前定義文 ノードの「SQL文」欄 msg.params のオブジェクト msg.payload に行の配列
一括(応答なし) msg.topic 渡せない msg.payload は空配列

msg.topic経由

SQL 文そのものを msg.topic に入れて渡す。Inject ノードのトピック欄に SQL を書いておけば、それだけで実行できるので試行に向く。

値を埋め込むこともできる。ただし条件があり、msg.payload が配列で、その要素数が msg.topic に含まれる $ の個数と一致したときにだけ、バインド値として使われる。一致しない場合は黙って無視され、値なしで実行される。

msg.topic = "INSERT INTO user_table (name, surname) VALUES ($name, $surname)"; msg.payload = ["John", "Smith"]; return msg;

固定文

SQL をノードに固定で書く。毎回同じ問い合わせを投げる用途（「直近 20 件を読む」など）に向く。値を差し替える手段がないため、条件が変わる問い合わせには使えない。

事前定義文

SQL をノードに書き、値は msg.params というオブジェクトで渡す。外から来た値を SQL に入れるときは、このモードを使う。

msg.params = { $id: 1, $name: "John Doe" }; return msg;

SQL 側は次のように書く。

INSERT INTO user_table (user_id, user) VALUES ($id, $name);
キーの先頭の $ を落とさない
msg.params のキー名は、SQL 中のプレースホルダと完全に一致させる。$ を書き忘れて { id: 1 } とすると SQLITE_RANGE: bind or column index out of range というエラーになる。

一括(応答なし)

msg.topic に入れた複数の SQL 文をまとめて実行する。セミコロンで区切って何文でも書ける。結果は返らず、msg.payload は空配列になる。テーブルと索引をまとめて作る初期化処理に向く。

SQL インジェクションという落とし穴

「msg.topic経由」と「固定文」は、受け取った文字列をそのまま実行する。したがって、外から来た値を文字列連結で SQL に埋め込むと、値のつもりで渡したものが命令として解釈されうる。これが SQL インジェクションである。

// 危険：入力値をそのまま連結している msg.topic = "SELECT * FROM readings WHERE name = '" + msg.payload + "'";

msg.payload に ' OR 1=1; DROP TABLE readings; -- のような文字列が入れば、表ごと消える。公式 README も、この 2 モードは「その性質上 SQL インジェクションである」と明記している。

判断の基準
SQL の中身が自分で書いた固定の文字列だけなら「msg.topic経由」「固定文」でよい。HTTP や MQTT から受け取った値、ダッシュボードの入力欄の値など、外から来た値を含むなら「事前定義文」を使う。事前定義文は値を値として扱うため、命令として解釈されることがない。

7. 実用的な使用パターン

パターン 1：起動時に一度だけテーブルを作る

Inject ノードの「Node-RED 起動の◯秒後」を有効にし、CREATE TABLE IF NOT EXISTS を実行する。すでにあれば何も起きないので、毎回の起動で安全に走る。

パターン 2：一定周期で測定値を記録する

Inject の繰り返し設定でセンサー読み取りを起動し、Function で msg.params を組み立て、事前定義文の sqlite ノードで書き込む。

書き込み周期は控えめに決める
1 秒ごとの書き込みは 1 日で 86,400 行になる。データ量そのものより、SD カードの書き込み回数を消費することが問題になりやすい。現場に置く機器では、記録周期と保持期間を先に決めること。詳しくは本番運用ガイドで扱う。

パターン 3：期間を指定して集計する

SQLite には日時を扱う関数がある。strftime で時刻を任意の粒度に丸め、GROUP BY でまとめると、1 時間ごとの平均が 1 つの SQL で得られる。

SELECT strftime('%Y-%m-%d %H:00', ts) AS hour, name, ROUND(AVG(value), 2) AS avg_value, COUNT(*) AS n FROM readings GROUP BY hour, name ORDER BY hour DESC LIMIT 24;

同じことをファイルで行うと、全行を読み込んで時刻を解釈し、自分でグループ分けして平均を出すことになる。データベースを使う利点がはっきり出る場面である。

パターン 4：時刻で絞り込むときの落とし穴

ここが本ガイドで最も間違えやすい箇所である。「30 日より古い行を消す」「直近 1 時間を集計する」のように時刻で絞り込むとき、比較する 2 つの値の形式をそろえないと、静かに誤った結果が返る。

原因は SQLite の datetime() 関数が返す形式にある。

値形式例
保存した ts（JavaScript の toISOString()）日付と時刻の間が T2026-08-10T00:22:39.253Z
datetime('now', '-1 hour') の戻り値日付と時刻の間が半角空白2026-08-10 00:52:39

この 2 つを文字列として比べると、11 文字目で T と半角空白を比較することになる。文字コードは T のほうが大きいため、同じ日付の行はすべて「新しい」と判定される。日付が違えば先頭の YYYY-MM-DD で決着するので正しく動いてしまい、当日ぶんだけが誤るという気づきにくい形で表面化する。

-- 誤り：形式が違うため、当日の行はすべて条件に合致してしまう SELECT * FROM readings WHERE ts >= datetime('now', '-1 hour'); -- 正しい：比較する側も同じ ISO 8601 の形式で作る SELECT * FROM readings WHERE ts >= strftime('%Y-%m-%dT%H:%M:%fZ', 'now', '-1 hour');

strftime('%Y-%m-%dT%H:%M:%fZ', ...) は 2026-08-10T00:52:39.253Z を返し、toISOString() の出力と完全に一致する。

もう 1 つのやり方と、その代償
datetime(ts) >= datetime('now', '-1 hour') のように両辺を datetime() で正規化しても正しく動く。ただし ts に関数を適用すると、パターン 6 で作る索引が使われなくなり、行数が増えたときに遅くなる。列にそのまま比較できる前者を勧める。

パターン 5：古いデータを消して容量を保つ

放置すればファイルは増え続ける。1 日 1 回、保持期間を超えた行を削除するフローを組んでおく。比較する側の形式は、パターン 4 のとおり保存形式にそろえる。

DELETE FROM readings WHERE ts < strftime('%Y-%m-%dT%H:%M:%fZ', 'now', '-30 days');
削除してもファイルは小さくならない
SQLite は削除した領域を再利用するため、行を消してもファイルサイズはすぐには縮まない。実際に縮めたい場合は VACUUM; を実行する。ただし実行中は一時的に元のファイルと同程度の空き容量を使うため、余裕のあるときに行う。

パターン 6：検索を速くする

行が数万を超えると、時刻での絞り込みが目に見えて遅くなる。よく条件に使う列には索引（インデックス）を作る。

CREATE INDEX IF NOT EXISTS idx_readings_ts ON readings (ts);

サイト独自のサンプルである

10. まとめ

覚えること内容
ノードは 2 種類SQL を実行する sqlite と、ファイルの場所を持つ sqlitedb（設定ノード）
モードの選択外から来た値を含むなら「事前定義文」と msg.params。自分で書いた固定の SQL なら「msg.topic経由」か「固定文」
結果の受け取りどのモードでも msg.payload に行の配列が返る（一括モードは空配列）
日時の扱い専用の型はない。TEXT の ISO 8601 か INTEGER の UNIX 時刻に統一する
時刻での絞り込み比較する側も保存形式にそろえる。ISO 8601 で保存したなら strftime('%Y-%m-%dT%H:%M:%fZ', 'now', ...) を使う。datetime('now', ...) と直接比べると当日ぶんが誤判定される
置きっぱなしにする前に保持期間を決めて削除フローを組む。索引を作る。書き込み周期を決める

次に読むとよいガイド

  • 本番運用ガイド：バックアップ、自動起動、SD カードの寿命対策。データベースを現場に置き続けるための前提
  • 可視化ウィジェット：集計した結果をチャートで見せる
  • CSV ノード：集計結果を表計算ソフトへ渡す
  • Catch ノード：SQL エラーを検知して通知につなげる

11. トラブルシューティング

症状 原因 対処
ノードが読み込めない、パレットに現れない ネイティブモジュールのビルドが済んでいない、または Node.js の版と合っていない cd ~/.node-red のあと npm rebuild。直らなければ cd ~/.node-red/node_modules/sqlite3 のあと npm run rebuild
SQLITE_CANTOPEN 指定したパスのディレクトリが無い、または書き込み権限が無い ディレクトリを作る（mkdir -p）。Node-RED の実行利用者に書き込み権限があるか確認する
SQLITE_RANGE: bind or column index out of range 事前定義文で msg.params のキーに $ が付いていない、または SQL 側のプレースホルダ名と一致していない キー名を $ts のように $ 付きにし、SQL 中の名前と完全に一致させる
事前定義文で「msg.params not defined」 手前のノードで msg.params を設定していない Function または Change ノードで msg.params をオブジェクトとして作る
msg.topic経由で値が入らない msg.payload の配列の要素数と、SQL 中の $ の個数が一致していない 個数をそろえる。確実に渡したい場合は事前定義文へ切り替える
SQL は正しいのに結果が空 参照しているデータベースファイルが想定と違う 設定ノードのパスを確認する。相対パスは Node-RED の起動時の作業ディレクトリ基準になるため、絶対パスにする
再起動したらデータが消えた データベース名に :memory: を指定している ファイルパスに変更する
行を消したのにファイルが小さくならない SQLite は削除領域を再利用するため 空き容量に余裕のあるときに VACUUM; を実行する
ノードのステータスが出ない、ログに接続失敗が続く ファイルを開けず、再接続を繰り返している パスと権限を直す。再接続の間隔は settings.js に sqliteReconnectTime: 20000,（ミリ秒）を書いて変更できる
ノードのステータス表示
sqlite ノードの下には、接続中のモード（RWC、RW、RO）が緑の点とともに表示される。ここが出ていなければ、設定ノードが選ばれていないか、ファイルを開けていない。
