Node-RED プロジェクト機能の使い方ガイド

🖥️ ローカル/ラズパイ 環境とは？

📖 このページの前提プロジェクト機能が有効になっていること。有効にする手順は settings.js 設定ガイド「2. プロジェクト機能の有効化」にあります。コミットやブランチという言葉に不安があれば、先に Git バージョン管理 超入門を読んでおくと迷いません。

🎯 得られるものエディターの画面だけで、フローの変更を記録し、履歴を見比べ、GitHub などへ保存し、別の Node-RED（ラズパイなど）へ同じフローを持っていけるようになります。

🖥️ 環境Git が入った自分のパソコンかラズパイの Node-RED が必要です。settings.js を書き換えられない共有環境では使えません。

1. プロジェクト機能でできること

プロジェクト機能を使うと、フローを Git で管理できます。1 つのプロジェクトは 1 つの Git リポジトリで、フローのファイルと、使っているノードの一覧などをまとめて持ちます。

プロジェクト機能を使わない場合との違いは次のとおりです。

やりたいことプロジェクト機能なしプロジェクト機能あり
昨日の状態に戻したいフローを書き出したファイルを自分で取っておくコミットの履歴から、いつ何を変えたかを見比べられる
別の案を試したいタブを複製するか、別の Node-RED を用意するブランチを作って切り替える
ラズパイに同じフローを入れたいフローを書き出して読み込み、足りないノードを手で入れるリモートからクローンし、足りないノードは一覧からインストールする
複数の用途のフローを使い分けたい1 つの Node-RED には 1 組のフローだけプロジェクトを作り分けて切り替える（同時に動くのは 1 つ）

2. 最初のプロジェクトを作る

プロジェクト機能を有効にして初めてエディターを開くと、プロジェクトを作るための案内が自動で表示されます。画面は次の順に進みます。

  1. ようこそ画面：プロジェクトの作成、プロジェクトのクローン、既存のプロジェクトを開く、後にする から選びます。新しく始めるときは プロジェクトの作成 を選びます。後にする を選んでも、あとでメニューの プロジェクト → 新規 から作れます。
  2. バージョン管理クライアントの設定：コミットに記録する ユーザ名 と Email を入れます。本名でなくても構いません。
  3. プロジェクトの作成：プロジェクト名（英数字と _ - だけ）と 説明（任意）を入れます。
  4. プロジェクト関連ファイルの作成：フローファイル の名前を決めます（既定は flows.json）。認証情報ファイルの名前は自動で決まります（flows_cred.json）。それまで使っていたフローと認証情報は、ここでプロジェクトにコピーされます。
  5. 認証情報ファイルの暗号化設定：パスワードやトークンを保存する認証情報ファイルを暗号化するかどうかと、その暗号化キーを決めます。
  6. 完了：プロジェクト作成 を押すと、プロジェクトができます。以降はこれまでどおりフローを編集できます。

暗号化キーは必ず控えておく

暗号化キーはプロジェクトのファイルとは別に保存され、Git の履歴にもリモートにも入りません。別の Node-RED でこのプロジェクトを使うときや、Node-RED を入れ直したときに同じキーが必要になります。キーが分からなくなると、保存してあるパスワードなどの認証情報は読み出せず、設定し直すことになります。公開するリポジトリに置くなら、暗号化は有効にしてください。

3. プロジェクトの中身

プロジェクトは、Node-RED のユーザーディレクトリの下の projects/プロジェクト名/ に作られます。ラズパイの標準的な導入なら /home/ユーザー名/.node-red/projects/プロジェクト名/ です。作成直後のファイルは次のとおりです。

ファイル中身
flows.jsonフローそのもの。デプロイするたびに書き換わる
flows_cred.jsonパスワードなどの認証情報。暗号化を有効にしていれば中身は読めない
package.jsonプロジェクトの名前と説明、使っている追加ノードの一覧（依存関係）、フローファイルの名前
README.mdプロジェクトの説明文。エディターから編集できる
.gitignoreGit で管理しないファイルの指定。作成時は *.backup（Node-RED が作るバックアップ）だけが入っている

このフォルダはふつうの Git リポジトリなので、中にほかのファイル（設計メモや画像など）を置いて一緒に管理することもできます。

4. 操作する場所

プロジェクト機能の操作は、エディターの次の 4 か所に分かれています。

場所できること
メニュー → プロジェクト新規（作成またはクローン）、開く（切り替えと削除）、設定（プロジェクト設定を開く）
サイドバーの 情報 タブいま有効なプロジェクトの名前が出る。横のボタンで プロジェクト設定を表示
サイドバーの 履歴 タブ変更の確認、ステージング、コミット、コミット履歴、ブランチの切り替え、プッシュとプル
メニュー → 設定 → Git設定 タブコミッター（ユーザ名とメールアドレス）、ワークフロー（手動か自動か）、SSH キー

プロジェクト設定 の画面には 3 つのタブがあります。

タブ内容
プロジェクト説明（README.md）の表示と編集
依存関係フローで使っている追加ノードの一覧。package.json に載っていないノードは プロジェクトへ追加、使っていないノードは プロジェクトから削除、入っていないノードは インストール で揃える
設定ファイル（フローファイル、認証情報の暗号化キー）、ブランチ の一覧と削除、Gitリモート の追加と削除

5. 変更を記録する（コミット）

ふだんの流れは、「フローを直す、デプロイする、コミットする」の繰り返しです。デプロイするまでファイルは書き換わらないので、デプロイ前の変更は履歴タブに出てきません。

  1. フローを編集して デプロイ します。
  2. サイドバーの 履歴 タブを開きます。ローカルの変更 の ステージングされていない変更 に flows.json が出ています。ファイル名をクリックすると、何が変わったかの差分が表示されます。
  3. ファイルの ＋（変更をステージング）を押して、ステージングされた変更 に移します。全部まとめて移すときは見出しの横の 全ての変更をステージング を使います。
  4. コミット を押し、何を変えたかが分かるメッセージ（例：「温度の閾値を 30℃ に変更」）を入れて、もう一度 コミット を押します。
  5. 下の コミット履歴 に 1 件増えていれば記録できています。

デプロイのたびに自動でコミットする

メニュー → 設定 → Git設定 の ワークフロー を 自動 にすると、デプロイするたびに自動でコミットされます。既定は 手動 です。自動にすると記録し忘れはなくなりますが、試しにデプロイした途中の状態もすべて履歴に残り、メッセージも自分では付けられません。まとまった単位で記録したい場合は手動のままにします。

デプロイした変更を取り消す（変更を戻す）

まだコミットしていない変更を捨てたいときは、ステージングされていない変更 のファイルの 変更を戻す ボタンを押します。ファイルは最後にコミットした状態に戻ります。この操作は元に戻せません。

6. 履歴を見る、元に戻す

履歴 タブの コミット履歴 には、これまでのコミットが新しい順に並びます。コミットをクリックすると、そのコミットで変わったファイルと差分が表示されます。いつ、何を変えたかを探すときに使います。

過去のコミットの状態に戻すボタンはない

エディターの画面でできるのは、履歴を見ることと、まだコミットしていない変更を捨てることまでです。コミット済みの過去の状態にフローを戻す操作は、画面には用意されていません。戻したいときは、プロジェクトのフォルダでコマンドの Git を使うか、差分を見ながらフローを直してデプロイし、新しいコミットとして記録します。コマンドで戻す考え方は Git 超入門「3. 基本機能は5つ」を参照してください。

7. ブランチを使う

ブランチを使うと、いまの本流（通常は main や master）を残したまま、別の案を試せます。

  1. 履歴 タブの コミット履歴 の上にある、ブランチ名のボタン（ブランチ:）を押します。
  2. ブランチの検索または作成 の欄に新しい名前を入れると、そのブランチを作って切り替えられます。既存の名前を選べば、そのブランチに切り替わります。
  3. 切り替えると、フローはそのブランチの内容に入れ替わります。

切り替える前にコミットしておく

デプロイしていない変更は切り替えで失われます。コミットしていない変更がブランチの内容とぶつかる場合は、切り替えが止まり、先にコミットするか元に戻すよう求められます。

作ったブランチの一覧と削除は、プロジェクト設定 の 設定 タブの ブランチ にあります。試した案を本流に取り込む操作（ローカルのブランチ同士のマージ）は画面にはありません。取り込むときは、リモートに両方のブランチをプッシュして GitHub のプルリクエストでマージし、本流をプルするか、コマンドの Git で git merge します。

8. GitHub などのリモートと同期する

リモートを使うと、プロジェクトをサーバーにも保存でき、別の機械と同じフローを共有できます。リモートの利用は任意で、ローカルだけでもコミットと履歴は使えます。

リモートを登録する

  1. GitHub などで空のリポジトリを作っておきます（README なども付けない、中身が空のもの）。
  2. メニュー → プロジェクト → 設定 → 設定 タブの Gitリモート で リモートを追加 を押します。
  3. リモート名（ふつうは origin）と、リポジトリの URL を入れます。URL は https:// か ssh://（GitHub の git@github.com:… 形式も可）です。URL にユーザー名やパスワードを含めてはいけません。

認証の方法

方式準備注意
HTTPSプッシュやプルのときに聞かれるユーザー名とパスワードを入れるGitHub はアカウントのパスワードでは受け付けない。パスワード欄には個人アクセストークンを入れる
SSHメニュー → 設定 → Git設定 の SSH キー で キーを追加 し、名前を付けて キーを生成。公開鍵をクリップボードにコピー して GitHub のアカウント設定に登録する生成したキーは ~/.node-red/projects/.sshkeys/ に置かれる。初めて接続するサーバーで「ホストキーの検証に失敗」と出たら、セクション 13 を参照

プッシュとプル

  1. コミット履歴 の上にある、リモートの状態を表すボタン（リモートブランチの管理）を押します。
  2. 初回は、送り先のリモートブランチ（例：origin/main）を選ぶか新しく作り、アップストリームとして設定する にチェックを入れます。以後はこのブランチと同期します。
  3. プッシュ でローカルのコミットをリモートへ送り、プル でリモートのコミットを取り込みます。

リモートとの差は、「リモートより 2 コミット進んでいます」（プッシュできる）や「遅れています」（プルできる）のように表示されます。

プッシュが断られたら、先にプル

別の機械からリモートに新しいコミットが入っていると、プッシュは失敗します。先に プル して取り込み、それからプッシュします。プルで同じ部分がぶつかった（コンフリクト）場合は、マージされていない変更 にファイルが出るので、コンフリクトの解決 の画面で、ぶつかった箇所ごとにローカルとリモートのどちらを採るかを選び、コミットして完了させます。やめるときは マージ中止 を押します。

9. 別の Node-RED でクローンして使う

パソコンで作ったフローをラズパイで動かす、という使い方がプロジェクト機能のいちばんの利点です。

  1. 元の Node-RED でコミットしてプッシュしておきます。
  2. ラズパイの Node-RED でもプロジェクト機能を有効にし、メニュー → プロジェクト → 新規 → プロジェクトをクローン を選びます（初回の案内画面なら プロジェクトのクローン）。
  3. プロジェクト名、GitリポジトリのURL、認証（HTTPS のユーザー名とトークン、または SSH キー）を入れます。
  4. 認証情報の暗号化キー に、元のプロジェクトと同じキーを入れます。
  5. クローンできたら、プロジェクト設定 の 依存関係 タブを開き、入っていないノードを インストール します。
  6. フローの内容を確認して デプロイ します。

機械ごとに違う値は、フローに直接書かない

ブローカーのアドレスやシリアルポート名など、機械によって変わる値をフローに書き込むと、クローン先で書き換えることになり、その変更がまた履歴に載ります。こうした値は環境変数にしておくと、同じフローのまま機械ごとに値を変えられます。ラズパイで環境変数を設定する方法は 本番運用ガイド「5. 別の機械への引っ越し」を参照してください。

10. プロジェクトの切り替えと削除

メニュー → プロジェクト → 開く で、プロジェクトの一覧が出ます。選んで開くと、動いているフローがそのプロジェクトのものに入れ替わります。同時に動かせるプロジェクトは 1 つだけです。

  • 切り替えの画面の プロジェクトを切り替る際にコンテキストを初期化 は、既定でチェックが入っています。前のプロジェクトのコンテキスト変数を引き継ぎたくないときはそのままにします。
  • デプロイしていない変更は、切り替えると失われます。
  • 削除は、一覧でプロジェクトにマウスを載せると出るごみ箱のボタンで行います。いま有効なプロジェクトは削除できません。削除するとローカルのフォルダごと消えます（リモートには残ります）。

11. 画面ではできないこと

エディターの画面は、よく使う Git の操作だけに絞ってあります。次の操作は、プロジェクトのフォルダでコマンドの Git を使います。

操作画面での扱い
過去のコミットの状態に戻すなし（履歴と差分の表示まで）
ローカルのブランチ同士のマージなし（プルに伴うマージとコンフリクトの解決はできる）
リベース、強制プッシュなし
Git の認証情報ヘルパーの利用非対応（HTTPS は画面で入力するか SSH キーを使う）

コマンドで操作したあとは、エディターの 履歴 タブで 変更を更新 または コミット履歴を更新 を押して表示を最新にします。フローのファイルを書き換えた場合は、Node-RED を再起動するか、プロジェクトを開き直して読み込ませます。

12. 演習

演習1：変更を記録して見比べる（初級）

  1. プロジェクト practice を作ります。
  2. inject ノードと debug ノードをつないでデプロイし、「最初のフロー」というメッセージでコミットします。
  3. inject ノードの payload を文字列 hello に変えてデプロイし、コミットします。
  4. コミット履歴 で 2 つ目のコミットをクリックし、差分に payload の変更が出ていることを確かめます。

成功の条件：コミット履歴に 2 件が並び、2 件目の差分に hello が見えること。

演習2：ブランチで別の案を試す（中級）

  1. 演習1の続きで、ブランチ try-delay を作って切り替えます。
  2. inject と debug のあいだに delay ノードを入れてデプロイし、コミットします。
  3. ブランチを元のブランチ（main など）に戻し、delay ノードが消えることを確かめます。

成功の条件：ブランチを切り替えるたびに、ワークスペースのフローが入れ替わること。

演習3：GitHub を通して別の Node-RED へ持っていく（上級）

  1. GitHub に空のリポジトリを作り、演習1のプロジェクトにリモートとして登録してプッシュします。
  2. 別の Node-RED（ラズパイ、または同じパソコンの別のユーザーディレクトリで起動した Node-RED）でプロジェクト機能を有効にし、そのリポジトリをクローンします。
  3. クローン先で inject ノードを押し、debug サイドバーに hello が出ることを確かめます。

成功の条件：クローン先のエディターに同じフローが表示され、デプロイ後に同じ結果が出ること。

13. トラブルシューティング

症状原因と対処
メニューに プロジェクト が出ない。起動ログに Projects disabledプロジェクト機能が無効か、Git が見つからない。settings.js 設定ガイドの有効化手順と、Windows なら Git for Windows インストールガイドのパスの設定を確認する
「Gitクライアントのユーザ名/emailが設定されていません。」コミッターが未設定。メニュー → 設定 → Git設定 で ユーザ名 と メールアドレス を入れる
デプロイしたのに ローカルの変更 に何も出ないワークフローが 自動 で、すでにコミットされている。コミット履歴 を確認する。表示が古いだけのときは 変更を更新 を押す
プッシュが失敗する（リモートに新しいコミットがある）先に プル してからプッシュする（セクション 8）
プルが失敗する（ステージングされていないローカルの変更が上書きされる）ローカルの変更を先にコミットするか、変更を戻す で捨ててからプルする

「ホストキーの検証に失敗」接続先のサーバーが known_hosts に登録されていない。Node-RED を動かしているユーザーで一度コマンドから ssh -T git@github.com のように接続し、サーバーを登録してから再試行する
クローンしたら、ノードの設定にパスワードなどが入っていない暗号化キーが元と違う。プロジェクト設定 の 設定 タブで正しいキーを設定する。キーが分からない場合は、認証情報を入れ直す
クローンしたフローに「不明なノード」が出る追加ノードが入っていない。依存関係 タブで インストール する

14. まとめと関連ガイド

  • 1 つのプロジェクトは 1 つの Git リポジトリ。フロー、認証情報、依存関係を一緒に持つ。
  • ふだんは「編集、デプロイ、ステージング、コミット」を 履歴 タブで繰り返す。
  • 別の案はブランチで試し、共有と持ち運びはリモートへのプッシュとクローンで行う。
  • 暗号化キーはリポジトリに入らない。控えておき、クローン先で同じものを入れる。
  • 過去の状態に戻す操作やローカルのマージは、コマンドの Git で行う。
