📖 1. 概要

UDP（User Datagram Protocol）は、コネクションレスの軽量プロトコルです。TCPと異なり、接続の確立や再送制御を行わないため、高速で軽量な通信が可能です。

📮 郵便に例えると：UDPは「はがき」のようなものです。送ったら終わり。届いたかどうかの確認はしません。一方TCPは「書留郵便」で、相手に届いたことを確認します。

UDPの特徴

  • コネクションレス：接続確立なしに即座に送信
  • 軽量・高速：オーバーヘッドが少ない
  • 信頼性なし：パケット損失や順序逆転の可能性
  • ブロードキャスト可能：同じネットワーク（サブネット）の全機器に一斉送信
  • マルチキャスト対応：特定グループに送信

⚖️ 2. UDP vs TCP の違い

特性 UDP TCP
接続 コネクションレス（接続不要） コネクション型（接続確立必要）
信頼性 なし（パケットロスあり得る） あり（再送制御）
順序保証 なし あり
速度 高速 比較的遅い
オーバーヘッド 小さい（8バイト） 大きい（20バイト〜）
ブロードキャスト 可能 不可
用途例 DNS、動画配信、ゲーム、センサーデータ Web、メール、ファイル転送

💡 使い分けのポイント:

  • UDP を選ぶ場合：リアルタイム性重視、多少のデータロスが許容できる、ブロードキャストしたい
  • TCP を選ぶ場合：確実にデータを届けたい、順序が重要、双方向のやり取りが必要

🔢 Buffer と文字列の違い

上の図で、送り手は文字の "ON" を送っています。ところが受け側の debug には <Buffer 4f 4e> と表示されます。中身は同じものです。4f が「O」、4e が「N」の文字コードを16進で表しています。

  • Buffer（バイナリバッファ）：文字に読み替える前の、バイト（0〜255の数）の並びのまま保持したもの
  • 文字列：そのバイトの並びを、文字コード（「文字列」を選んだときは UTF-8）で文字に読み替えたもの

なぜ Buffer で届くのか

UDP が運ぶのはバイトの並びだけです。送られたデータが文字なのか、数値なのか、文字ならどの文字コードなのかという情報は、データに付いてきません。そのため UDP In ノードは、受け取ったバイトを読み替えずに、そのまま Buffer として渡します。

なぜ既定が「バイナリバッファ」なのか

「文字列」を選ぶと、ノードは届いたバイトを UTF-8 の文字として読み替えます。この読み替えは、次の場合にデータを壊します。Buffer のままなら、どちらの場合も1バイトも失われません。

  • 文字ではないデータ（バイナリ）：数値を文字に直さずに、数のままバイトにして送るデータです（下の例）。UTF-8 として読めないバイトは「�」に置き換わり、元に戻せません
  • UTF-8 ではない文字：古い機器には Shift_JIS で日本語を送るものがあります。UTF-8 として読むと文字化けします

バイナリの例として、温度 25.3℃ を送る2つの方法を比べます。センサーや計測機器の多くは小数を扱わず、10倍した整数の 253 にして送ります（スケーリング）。

送り方送るバイト「文字列」で受けると
文字で送る32 35 2e 33（「2」「5」「.」「3」の4文字）"25.3" と正しく読める
数のまま送る（253 を2バイトで）00 fd（253 は16進で fd）画面に出ない文字（00）と「�」になる。バイトに戻しても 00 ef bf bd になり、253 は取り出せない

数のまま送る方法は、0〜65535 のどの値でも2バイトで送れるため、機器どうしの通信でよく使われます。00 fd は文字として読むためのバイトではありません。Buffer のまま受けて、buffer-parser ノードなどで数として読み取ります。

相手が UTF-8 のテキスト（"ON" のようなコマンドや、JSON の文字列など）を送ってくると分かっているときは、「文字列」を選びます。UDP は送った1回分（データグラム）を1つの msg にして、まとめて文字列に読み替えます。そのため、TCP の「文字列」で起こる、文字の途中で切れて化ける問題は起こりません。

バイトと文字コードの関係（1文字が何バイトになるか など）は、変数ガイド Part 1「6. バイナリデータとBuffer」で詳しく扱っています。

「ポート」と「ローカルポート」の違い

UDP Out の画面には、ポート番号を決める場所が2つあります。「送信」の右の「ポート」は相手の番号で、アドレスの下のドロップダウンで決める「ローカルポート」は自分の番号です。手紙にたとえると、「アドレス」と「ポート」が宛先、「ローカルポート」が差出人にあたります。

ポート番号は、PC ごとに別々に持っている番号です。データは相手の PC の「ポート」の番号へ届き、自分の「ローカルポート」の番号は差出人として一緒に届きます。受けた UDP In は、この差出人の番号を msg.port に入れます。

データを送るだけなら、差出人の番号は決めなくても届くので、既定の「ローカルポートをランダムに使用」のままで構いません。番号を決める必要があるのは、返信を受け取るときです。相手は差出人の番号（msg.port）へ返信するので、自分の UDP In が待ち受けている番号を差出人にしておきます。

ポートローカルポート
何の番号か 送り先（相手）の番号 送り元（自分）の番号
空のとき msg.port の番号へ送る。msg.port も無いと、警告を出して送らない 番号を自動で決める（例外は下の補足を参照）
msg で変えられるか 欄が空のときだけ msg.port で指定できる 変えられない。画面の注釈にある msg.port は、送り先の番号のこと
設定が要るとき 常に（欄か msg.port のどちらか） 返信を UDP In で受けたいとき（演習5のBさん）と、受けたのと同じ番号から返信したいとき（パターン4、演習2）

ドロップダウンの細かい動き（Node-RED 5.0.7 で確認）:

  • 「ランダム」の番号は、送るたびには変わりません。デプロイでノードが作り直されるまで、同じ番号を使います。
  • 同じ Node-RED の中に、「ポート」と同じ番号の UDP In があると、UDP Out はそのソケットを使い回します。このときはランダムのままでも、差出人はその番号になります。たとえば公式サンプル（localhost の 1881 番へ送り、UDP In :1881 で受ける）では、msg.port は 1881 です。
  • 「ローカルポートを使用」を選んで右の欄を空のまま閉じると、ランダムと同じ扱いになり、開き直すと表示も「ローカルポートをランダムに使用」に戻ります。
  • 「送信」がブロードキャストかマルチキャストのときは、「ローカルポートをランダムに使用」の文字が「指定したポートを使用」に変わります。文字が変わるだけで、番号は自動で決まります。

⚠️ 動作確認方法:

サンプルフローをデプロイしたら、UDPでデータを送受信してみて動作を確認できます。初心者の方は、まず「Node-RED内」の方法から試すのがおすすめです。

  • Node-RED内（追加ツール不要）: 公式サンプルフローと応用フローの inject のボタンを押すと、UDP Out が自分自身の UDP In へ送り、届いたものが debug サイドバーに表示されます（無効にしてある「3秒ごと」を除きます）。
  • Mac・Linux: netcat（nc）: ターミナルからUDP通信を手軽に試せるコマンドラインツールです。Mac と多くの Linux に入っています。
  • Windows: PowerShell: Windows には nc が入っていません。PowerShell に下の関数を貼り付けると、何もインストールせずに送信と返信の確認ができます。コマンドプロンプトでは使えません。
  • socat: netcatより高機能な通信テストツールです。netcatでうまく送受信できない場合の代替として使えます。
  • Python（任意）: Pythonのsocketモジュールでテスト用スクリプトを自作する方法です。プログラミング経験がある場合に。

Mac・Linux: netcat でのテスト例

ターミナルを開いて以下のコマンドを実行すると、応用フローのUDP Inへ送れます。[Node-REDのホスト] は、お使いのNode-REDエディタを開いているアドレスに置き換えてください（ローカル環境なら 127.0.0.1）。

# UDP送信（「UDP In :8000」へ。届いた内容は debug サイドバーで確かめる） echo "Hello UDP" | nc -u -w1 [Node-REDのホスト] 8000 # 返信を受ける（「UDP In :8002」のエコーが [ECHO] Hello を返す） echo "Hello" | nc -u -w1 [Node-REDのホスト] 8002
  • localhost ではなく 127.0.0.1 と書く: nc は localhost を IPv6 の ::1 として送ることがあります。UDP In は既定で IPv4 で待ち受けるため、届きません。UDP には接続がないので、届かなくてもエラーは出ません
  • -w1: Mac の nc では、1秒間何も届かなければ nc を終わらせます。付けないと、返信が来たあとも nc が終わらないので、Ctrl+C で止めます。Linux の nc は種類によってオプションの意味が違い、-w1 を付けても終わらないことがあります。そのときも Ctrl+C で止めます
  • Node-RED が待ち受けているポートを nc で待ち受けない: たとえば nc -ul 8000 は、「UDP In :8000」と同じポートを取り合います。起動できないか、起動できても届いたデータは Node-RED 側に渡り、nc には表示されません

Windows: PowerShell でのテスト例

スタートメニューで「PowerShell」と検索して開きます。次の関数をコピーして PowerShell の画面に貼り付け、Enter キーを押します。画面に何も表示されなければ、関数を作れています。関数は PowerShell の画面を閉じるまで使えるので、開き直したときはもう一度貼り付けます。

function Send-UdpText { param([int]$Port, [string]$Text, [switch]$Wait, [string]$HostName = "127.0.0.1") # UDP で Text の末尾に改行を付けて1回送る（nc に echo で渡したときと同じ） # 送り先の既定は 127.0.0.1（Node-RED の UDP In の既定は ipv4 のため） $udp = New-Object System.Net.Sockets.UdpClient try { $bytes = [System.Text.Encoding]::UTF8.GetBytes($Text + "`n") [void]$udp.Send($bytes, $bytes.Length, $HostName, $Port) if ($Wait) { # -Wait を付けたときは、3秒まで返信を待って、UTF-8 の文字列にして表示する $udp.Client.ReceiveTimeout = 3000 $remote = New-Object System.Net.IPEndPoint([System.Net.IPAddress]::Any, 0) $reply = $udp.Receive([ref]$remote) [System.Text.Encoding]::UTF8.GetString($reply) } } finally { $udp.Close() } }

使い方は Send-UdpText ポート番号 "送る文字" です。応用フローの「UDP In :8000」へは、次のように送ります。

Send-UdpText 8000 "Hello UDP"

Node-RED が別のパソコン（Raspberry Pi など）で動いているときは、最後に -HostName で送り先の IPv4 アドレスを指定します。指定しないと、PowerShell を開いているパソコン自身（127.0.0.1）へ送ります。

Send-UdpText 8000 "Hello UDP" -HostName 192.168.1.20

UDP は送りっぱなしなので、送るだけのときは PowerShell の画面に何も表示されません。届いたかは、Node-RED の debug サイドバーで確かめます。返信を待つときは、最後に -Wait を付けます（例: Send-UdpText 8002 "Hello" -Wait）。-Wait を付けたときの表示の意味は次のとおりです。

表示意味
返信の文字成功。送った文字が届き、返信が戻った
「既存の接続はリモート ホストに強制的に切断されました」を含む赤いエラーそのポートで待ち受けているものが無い。フローをデプロイしたか、ポート番号が合っているかを確かめる
「一定の時間を過ぎても正しく応答しなかった」を含む赤いエラー3秒以内に返信が無かった。返信する側の UDP Out のアドレスとポートが空欄（msg.ip と msg.port を使う）になっているかを確かめる
「言語モード」を含む赤いエラー（「この言語モードでは、コア型のみがサポートされています」など）会社のパソコンなどで、PowerShell の機能が制限されている。演習に付けた「動作確認用フロー」で確かめる

エラーの文言は、Windows の言語の設定によって英語で表示されることがあります（待ち受け無し: forcibly closed、時間切れ: failed to respond、制限: Only core types are supported in this language mode）。

使用パターン

応用フローの6つの部分を、パターンごとに紹介します。

パターン1: 基本UDP送受信

用途: UDPメッセージの送受信

応用フローの「1. 受信（ポート8000）」「2. ユニキャスト送信」を参照してください。

ユニキャスト送信 → UDP Out (localhost:8000)
UDP In :8000 → 受信データ → 送信元情報をまとめる → 送信元情報

ポイント:

  • UDP In: 受信時に msg.ip, msg.port が設定される
  • UDP Out: 宛先アドレスとポートを指定
  • change ノードの JSONata {"ip": ip, "port": port, "data": payload, "timestamp": $now()} で、送り元の情報を1つのオブジェクトにまとめる

パターン2: ブロードキャスト送信

用途: 同一ネットワークへの一斉送信

応用フローの「3. ブロードキャスト送信」を参照してください。

ブロードキャスト送信 → UDP Broadcast

ポイント:

  • アドレス: 255.255.255.255 または サブネットのブロードキャスト（192.168.1.255）
  • 同じサブネットの全デバイスにデータを一斉配信
  • 送った自分の「UDP In :8000」にも届く。送り元（msg.ip）は 127.0.0.1 ではなく、自分の PC の LAN の IP アドレスになる

パターン3: JSONデータの送受信

用途: JSON形式データの送受信

応用フローの「4. JSON データの送受信（ポート8001）」を参照してください。

送る側:

JSON送信 → UDP Out :8001

受ける側:

UDP In :8001 (JSON) → 文字列→オブジェクト → 受信時刻と送信元を足す → JSON データ

受ける側（JSON として読めなかったとき）:

JSON として読めない → JSON として読めなかったもの

ポイント:

  • UDP で送れるのは文字（バイト）だけなので、オブジェクトは JSON の文字列にして送る。サンプルの inject は、JSON の文字列 {"sensor":"temp","value":25.5,"unit":"C"} を種類「文字列」で送る
  • 受信時: json ノードでオブジェクトに戻す
  • JSON として読めない文字が届くと、json ノードがエラーを出す。catch ノードでそのエラーを受け取る（「JSONでない文字を送る」のボタンで試せる）

パターン4: 受信元への返信（エコー）

用途: 受信した送信元へのエコー返信

応用フローの「5. 受信元への返信（エコー）（ポート8002）」を参照してください。

返信する側:

UDP In :8002 → [ECHO] を付ける → UDP Reply (msg.ip/port) → エコー送信

試す側（8012 番から送り、8012 番で返信を受ける）:

エコーを頼む → 8012番から localhost:8002 へ
UDP In :8012（返信を受ける） → クライアント側: エコーの返信

ポイント:

  • UDP Out のアドレス/ポートを空にすると msg.ip, msg.port を使用
  • 受信したパケットの送信元に返信可能。UDP In が付けた msg.ip と msg.port は、change ノードを通っても残る
  • UDP Out の「ローカルポート」（アドレスの下のドロップダウン）を「ローカルポートを使用」にして、UDP In と同じ番号を入れると、返信を受けたのと同じポートから送る。既定の「ローカルポートをランダムに使用」では、送り元のポートが自動で決まり、UDP In の待ち受けポートとは別になる。返信を受ける側（nc や多くの機器）は、送った先と同じポートからの返信しか受け取らないことが多い
  • 試す側も同じ考え方で、送る UDP Out のローカルポートを 8012 にし、8012 番の UDP In で返信を受ける（図で説明しています）

⚠️ 同じポートの UDP In と UDP Out は、1つのソケットを使い回す

UDP Out の「ローカルポートを使用」に UDP In と同じ番号を入れると、UDP Out は UDP In のソケットをそのまま使います。デプロイの種類を「変更したノード」にしていて、どちらか片方だけを変えてデプロイすると、片方だけが作り直され、UDP In が受信しなくなったり、返信が送られなくなったりします。デプロイボタンの右の ▼ で「全て」か「変更したフロー」を選んでデプロイします（Node-RED の既定は「全て」）。止まってしまったときは、同じメニューの「フローを再起動」で戻ります。

パターン5: 定期的なセンサーデータ送信

用途: センサーデータの定期送信

応用フローの「6. 定期的なセンサーデータ送信（ポート8003）」を参照してください。

⚠️ inject「3秒ごと」は、無効の状態で読み込まれます

繰り返しを設定した inject は、デプロイした時点で動き始め、ボタンを押さなくても送り続けます。Node-RED を再起動しても再開し、止めるまで送信が続きます。そのため、このサンプルでは inject を無効にしてあります。試し方は次のとおりです。

  1. 「3秒ごと」をダブルクリックし、編集画面の左下にある「無効」のボタンを押して「有効」に切り替え、「完了」を押す
  2. デプロイする。debug サイドバーに「送信データ」と「受信側: センサーデータ」が3秒ごとに表示される
  3. 試し終わったら、同じ手順で「無効」に戻してデプロイする

無効のままボタンを押すと、「ノードのアクションは無効になっています」と通知され、送信されません。

💡 送り先は自分の PC（localhost）です。ブロードキャストで定期的に送ると、社内 LAN などの同じサブネットの全機器へ届き続けるため、このサンプルでは使いません。ブロードキャストは、1回ずつ送れる「3. ブロードキャスト送信」で試せます。
3秒ごと
(最初は無効) → センサーデータを作る → UDP Out (localhost:8003) → 送信データ
UDP In :8003 → 受信側: センサーデータ

ポイント:

  • Inject の repeat 設定で定期実行
  • change ノードの JSONata で乱数の値を作り、$string(...) で JSON の文字列にして localhost へ送る

演習5: 2人でUDP通信する（社内LAN） 上級

📋 課題: 2人1組になり、片方が受けて返信する側、もう片方が送って返信を受ける側を作って、社内LAN越しにUDPで通信してください。ここまでの演習は1台のNode-REDの中で完結していましたが、この演習では相手のNode-REDへ、実際にネットワークを越えて送ります。

💼 使いどころ: 別の機器（センサーや装置、別のパソコンで動くNode-REDなど）へUDPでデータを送り、その機器からの返事を受け取る場面で使います。

作る範囲:

Bさんが作る
Bさんの Node-RED
送る側
9005番から相手の9004番へ送り
9005番で返信を待ち受ける
(AさんのIP):9004 へ "こんにちは、Bです" →
← (BさんのIP):9005 へ "Aさんが受け取りました: こんにちは、Bです"

UDP には接続がありません。TCP のように、送った接続の上で返信が戻ってくるわけではないので、返信を受け取るには、Bさんも自分のポート（9005番）で待ち受けておきます。

🎯 要求仕様:

  • 受けて返信する担当（Aさん）: UDP In でポート 9004 を待ち受ける。受け取った文字の前に「（自分の名前）が受け取りました: 」を付け、送ってきた相手（msg.ip と msg.port）へ UDP Out で返す。返信は、受けたのと同じ 9004 番から送る（演習2と同じ）
  • Aさんは、受け取った文字と、送ってきた相手のIPアドレス（msg.ip）をデバッグパネルで確かめられるようにする
  • 送る担当（Bさん）: Inject でトリガーし、UDP Out で（AさんのIPアドレス）のポート 9004 へ送る。送り元のポートは 9005 にする
  • Bさんは UDP In でポート 9005 を待ち受け、届いた返信を Debug に表示する
  • 通信できたら、Aさんが自分のタブ（「演習5 受けて返信する側」）を無効にしてデプロイし、Bさんがもう一度送って、何が起きるかを確かめる
  • 最後に役割を入れ替え、両方を体験する

✅ 成功の条件:

  • Bさんのデバッグパネルに、「Aさんが受け取りました: こんにちは、Bです」のように、Aさんの名前が付いた返信が表示される
  • Aさんのデバッグパネルに Bさんが送った文字が表示され、debug ノードの下に BさんのIPアドレスが表示される
  • Aさんのタブを無効にしたあと Bさんが送ると、Bさんの画面にはエラーが出ず、返信も来ない（AさんのPCはLANにつながったまま、タブを無効にしただけの場合）。UDP は届いたかを確かめないので、送った側は相手が受け取ったかどうかを知らないことを説明できる
  • 役割を入れ替えても同じように通信できる
⚠️ 注意: この演習で開くポートには、認証も暗号化もありません。IPアドレスとポート番号を知っていれば、同じLANにいる誰でも送れます。Aさんのフローは、届いたものに返信するため、送り元を偽ったデータにも返信してしまいます。社内LANでの学習に限って行い、終わったら両方のフローを削除するか無効にしてデプロイし、ポートを閉じてください。
💡 ヒント

自分のIPアドレスの調べ方: Windows は ipconfig の「IPv4 アドレス」、ラズパイ・Linux は hostname -I。Mac の hostname には -I が無いため、「システム設定」の「ネットワーク」で、使っている接続（Wi-Fi など）の「詳細」を開き、「TCP/IP」の「IPアドレス」を見ます。詳しくはローカル/ラズパイ演習ガイドの共通の準備を参照してください。

待ち受けるアドレスの設定は不要: UDP In は、アドレスを限らずにポートを開きます。そのため設定を変えなくても、他のPCから届きます。

ファイアウォール: Windows では Defender ファイアウォールが受信をブロックすることがあります。初回の待ち受け時に出る許可ダイアログで許可するか、受信するポートを許可してください（Windows編）。UDP では、Aさん（9004番）だけでなく、返信を受けるBさん（9005番）も受信側になります。

受けて返信する担当（Aさん）のノード:

  • UDP In: ポート 9004、出力「文字列」
  • Change: msg.payload を「値の代入」で設定し、型は JSONata 式、式は "Aさんが受け取りました: " & msg.payload。msg.ip と msg.port はそのまま残る
  • UDP Out: アドレスとポートは空欄（msg.ip と msg.port を使う）。アドレスの下のドロップダウンを「ローカルポートを使用」にして、右の欄に 9004
  • Debug: 「ノードステータス」に msg.ip を表示すると、送ってきた相手のIPアドレスがノードの下に出る

送る担当（Bさん）のノード:

  • UDP Out: アドレス（AさんのIPアドレス）、ポート 9004。アドレスの下のドロップダウンを「ローカルポートを使用」にして、右の欄に 9005
  • UDP In: ポート 9005、出力「文字列」

Bさんの UDP Out の送り元を 9005 にするのは、Aさんの返信の宛先（msg.port）が 9005 になるようにするためです。既定の「ローカルポートをランダムに使用」のままだと、送り元のポートが自動で決まり、返信はBさんの UDP In（9005番）に届きません。

どちらの PC でも、同じ番号の UDP In と UDP Out は1つのソケットを使います。片方だけを変えて「変更したノード」でデプロイすると止まります（パターン4の注意を参照）。

つながらないときの切り分け順:

  1. Aさん自身が、自分のPCから送って返信を得られるか。Mac・Linux では echo "Hello" | nc -u -w1 127.0.0.1 9004、Windows の PowerShell では Send-UdpText 9004 "Hello" -Wait。返信が得られなければAさんのフロー側の問題（デプロイ忘れ、ポート番号の違い、UDP Out のアドレスとポートが空欄でない、ローカルポートが 9004 でない）。
  2. Bさんが自分のPCから、Aさんへ送って返信を得られるか。Mac・Linux では echo "Hello" | nc -u -w1 （AさんのIP） 9004、Windows の PowerShell では Send-UdpText 9004 "Hello" -HostName （AさんのIP） -Wait。返信が得られなければ、ネットワークかAさん側のファイアウォールの問題。PowerShell の表示の意味はWindows: PowerShell でのテスト例の表を参照してください。
  3. 端末からは返信が得られるのに、Bさんの Node-RED にだけ届かないなら、Bさんの UDP Out のローカルポートが 9005 になっているか、UDP In が 9005 番か、Bさん側のファイアウォールが 9005 番の受信を止めていないかを確かめる。Aさんのデバッグパネルに届いていれば、行きの経路は通じている。

✅ 7. まとめ

🎯 重要ポイント:

  • コネクションレス：接続確立不要で即座に送信可能
  • 信頼性なし：パケットロスや順序逆転の可能性があることを考慮
  • ブロードキャスト：255.255.255.255 または サブネットのブロードキャストアドレス（例 192.168.1.255）
  • 返信：msg.ip と msg.port を使って送信元に返信可能
  • 用途：センサーデータ、発見プロトコル、リアルタイム通信

⚠️ 注意事項:

  • 信頼性が必要な場合はTCPを使用
  • ブロードキャストは同一サブネット内でのみ有効
  • ファイアウォール設定でUDPポートを開放
  • パケットサイズ：MTU（通常1500バイト）を超えると分割される

📘 10. 用語集（UDP 固有の用語）

UDP はシンプルなプロトコルですが、配信形態（ユニキャスト / マルチキャスト / ブロードキャスト）や信頼性の用語で混乱しやすい点があります。データグラム・パケット・ソケット・ポートなどは 通信の基礎ガイドの用語集 を参照してください。

📭 コネクションレス（connectionless）

「接続を張らずに、いきなり荷物を投げる」方式。TCP の「電話をかけてから話す」のと対照的に、UDP は「はがきを投函する」イメージです。

  • 事前の ハンドシェイクなし（送信側はすぐ送信を開始できる）
  • 状態を持たないので、サーバー側も軽量（少ないリソースで大量送信先を扱える）
  • 逆に、相手が受信できる状態かどうか送信側は知らない

🎯 ベストエフォート配信（best-effort）

UDP は 「届くか届かないか保証しない、順番もずれる、重複する可能性もある」方針。これらを保証するのは TCP の役割であり、必要ならアプリ側で実装します。

  • 届かない（再送なし）：1 通失われても気づかれない
  • 順番が入れ替わる：後から送った方が先に着くことがある
  • 重複する：同じデータグラムが 2 回届くことがある

こうした「不確実さ」を承知の上で、速度・軽さ・1 対多配信のために UDP を選びます。

📡 ユニキャスト / マルチキャスト / ブロードキャスト（3 つの配信形態）

形態送信先例典型用途
ユニキャスト（unicast）特定の 1 台に送る192.168.1.10 宛て通常の 1 対 1 通信
ブロードキャスト（broadcast）同じサブネット内の全員に送る192.168.1.255（サブネット）/ 255.255.255.255（限定）サービス発見、DHCP、機器探索
マルチキャスト（multicast）「このグループに加入している人」だけに送る224.0.0.0 〜 239.255.255.255 の範囲動画/音声のストリーミング配信、産業制御
💡 マルチキャストはブロードキャストとユニキャストの中間です。ブロードキャストのように「興味ない人にも届いて負荷をかける」ことなく、ユニキャストのように「同じデータを N 回コピー送信する」非効率もなく、受信したい人だけが受け取れます。
⚠️ クラウド／インターネット越しでは届かない: ブロードキャストとマルチキャストは ルーターを跨ぐと伝わらないのが原則です。同一サブネット（同じ LAN セグメント）内でのみ有効と考えてください。クラウド共有環境ではほぼ動きません。

📏 MTU（Maximum Transmission Unit）と分割（fragmentation）

1 回で送れるIP パケットの最大サイズ。物理ネットワークごとに決まっており、Ethernet では 通常 1500 バイトです。

  • UDP データグラムが MTU を超えると、IP 層で複数のフラグメント（断片）に分割される
  • 分割されたフラグメントのうち 1 つでも失われると、データグラム全体が無効になる（UDP には再送がない）
  • そのため UDP では 1 データグラムを MTU 以下に収めるのが鉄則。安全圏は 1472 バイト（1500 − IP ヘッダ 20 − UDP ヘッダ 8）
  • 大きなデータを送りたい場合は、アプリ側で自前で分割・再構成する必要がある（または TCP を使う）

✅ チェックサム（checksum）

UDP ヘッダとペイロードの誤り検出用の 16 bit 値。受信側で計算し直して送信時と一致しなければそのデータグラムを破棄します。

  • IPv4 では任意（0 にすれば未使用扱い）
  • IPv6 では必須（IPv6 自身がチェックサムを持たないため）
  • これはあくまで誤り「検出」であって、誤り訂正や再送はしない（再送が欲しければ TCP かアプリ層で実装）

🔁 ポート再利用（SO_REUSEADDR）

UDP では「同じポートに複数のプロセスが Bind（＝ポートを予約して使えるようにすること）したい」状況がよくあります（マルチキャスト受信や、サーバー再起動時の即時再 Bind など）。

  • SO_REUSEADDR オプションで「このポートを他と共有してよい」と OS に伝える
  • Node-RED の UDP In ノードは内部で適切にこのオプションを設定するため、明示的な設定は通常不要
  • 「ポートがすでに使われています」エラーが出るときは、別のプロセス（別の Node-RED フローや netcat 等）が同じポートを占有していないかを確認
