1. TLS は何のためにあるか

TLS（Transport Layer Security）は、ネットワーク上のやり取りを第三者から守るための仕組みです。URL の https://、wss://、MQTT の mqtts:// に付いている「s」は、どれも「TLS で守られた通信」を表します。

TLS が何を守るのかは、守られていない通信で何が起きるかを見ると分かります。通信は、送り手と受け手のあいだにある Wi-Fi のアクセスポイント、ルーター、プロバイダの設備などを経由して届きます。そのどこかに悪意のある第三者がいると、次の3つが起こり得ます。

① 盗み見（盗聴）

TLS なし
Node-RED→温度 25.3℃→サーバー
👀 途中で中身を読まれる
TLS あり
Node-RED→x9#Qk2...→サーバー
👀 途中では読めない

② 書き換え（改ざん）

TLS なし
Node-RED→停止→✂→運転→機器
途中で「運転」に差し替えられ、機器は気づかない
TLS あり
Node-RED→停止→✂→機器
改ざんを検出して、そのデータを捨てる

③ なりすまし

TLS なし
Node-RED→パスワード→🎭 偽サーバー
相手が本物か確かめられず、パスワードを渡してしまう
TLS あり
Node-RED→身分証を見せて→🎭 偽サーバー
正しい証明書を出せないので、接続しない

TLS は、この3つをそれぞれ別の道具で防ぎます。郵便にたとえると、TLS なしの通信ははがきです。配達の途中で誰でも読めますし、書き足すこともでき、差出人の名前は自由に書けます。TLS は、はがきを次の3つの道具に置き換えます。

守るもの 郵便のたとえ TLS での仕組み
盗み見を防ぐ（機密性） 中身の見えない封筒に入れる 通信内容を暗号化する。鍵を持つ送り手と受け手しか読めない
書き換えを防ぐ（完全性） 開けると跡が残る封印をする データごとに検査用の値を付ける。1 ビットでも変わると受け手が検出する
なりすましを防ぐ（真正性） 窓口で身分証を確認してから渡す サーバーが証明書を提示し、クライアントが本物かを確かめる

3つのうち、最も誤解されやすいのが3つ目です。暗号化だけなら、偽のサーバーとのあいだでも成立してしまいます。封筒に入れて封印しても、渡した相手が偽物なら中身は読まれます。そのため TLS では、相手が本物かどうかの確認が暗号化と同じくらい大切になります。このガイドの大半が証明書の話なのはそのためです。

SSL と TLS：SSL は TLS の前身の古い規格で、現在は使われていません。ただし「SSL/TLS」「SSL証明書」のように古い呼び名が残っており、Node-RED のエディターにも「SSL/TLS接続を有効化」という欄があります。いずれも TLS を指すと読んで差し支えありません。

2. TLS の位置：通信に被せる「暗号の層」

TLS は、HTTP や MQTT とは別の独立した層です。TCP でつながった通信路の上に TLS の層を被せ、その中で HTTP や MQTT がふだんどおりに会話します。HTTP や MQTT から見ると、自分の下に暗号の層が1枚挟まっただけで、話す内容は変わりません。

HTTP
WebSocket
MQTT
SMTP
TLS
暗号化、改ざん検出、相手の確認
TCP
データを順番どおり確実に届ける

この構造のため、TLS を被せた通信は元のプロトコル名に「s」を付けて呼ばれます。暗号化しない通信と同じポートでは待ち受けず、別のポート番号を使うのが一般的です。

暗号化なし TLS あり 既定のポート Node-RED での主な場面
http:// https:// 80 → 443 http request で Web API を呼ぶ、エディターを https で開く
ws:// wss:// 80 → 443 websocket ノードでクラウドのサービスとつなぐ
mqtt:// mqtts:// 1883 → 8883 AWS IoT Core などのクラウドブローカーへ送る
SMTP（25） SMTPS（465）／STARTTLS（587） 465 または 587 email ノードでメールを送る

STARTTLS は、最初は暗号化なしで接続し、会話の途中で TLS に切り替える方式です。メールで使われます。詳しくは Email ガイドを参照してください。

3. 接続のはじめに起きること

TLS の通信は、データを送る前にハンドシェイク（握手）と呼ばれる準備の手順を踏みます。細部を省くと、流れは次のとおりです。

（Node-RED）
ハンドシェイク
サーバー
（ブローカー等）
①
「TLS で話したい。接続先は broker.example.com」
「これが私の証明書です」
②
③
証明書を検証する（発行元、名前、有効期間）
④
⇄ 検証に通ったら、暗号化の鍵を2者で取り決める
⑤ 以降の HTTP や MQTT のデータは、すべて暗号化されて流れる

①で接続先の名前を伝えるのは、1台のサーバーが複数の名前（ドメイン）を受け持つことがあるためです。サーバーは、伝えられた名前に合う証明書を選んで②で返します。この名前を伝える仕組みを SNI（Server Name Indication）と呼びます。

エラーの大半は③で起きます。検証に失敗すると④に進まず、接続そのものが切られます。そのため、証明書に問題があると「データの中身がおかしい」ではなく「つながらない」という症状になります。③で何を確かめているかは、証明書の仕組みを見たあとセクション 5 で扱います。

4. 証明書のしくみ

公開鍵と秘密鍵

証明書の土台には、公開鍵と秘密鍵という2つで1組の鍵があります。片方で処理したものは、もう片方でしか確かめたり元に戻したりできない関係になっています。

  • 公開鍵：誰に渡してもよい鍵。証明書の中に入っていて、接続してきた相手に配られる
  • 秘密鍵：持ち主だけが持つ鍵。サーバーの中から外に出さない

秘密鍵は本人だけが持つ印鑑、公開鍵は印鑑証明に載っている印影にたとえられます。秘密鍵で押した印（署名）は、公開鍵と照らし合わせれば本物かどうか分かります。しかし公開鍵から秘密鍵は作れないので、公開鍵を持っていても同じ印は押せません。ハンドシェイクでサーバーは、秘密鍵を持っていることを署名で示します。証明書をコピーしただけの偽サーバーは秘密鍵を持たないため、この段階で失敗します。

秘密鍵は外に出さない：秘密鍵が漏れると、誰でもそのサーバーになりすませます。.key ファイルをメールやチャットで送ったり、Git リポジトリに入れたりしないでください。フローを共有する場合の扱いはセクション 9 で説明します。

証明書の中身

公開鍵だけでは、それが誰の鍵なのか分かりません。そこで公開鍵に「これは broker.example.com の鍵です」という情報を添え、信頼できる第三者が署名したものが証明書です。たとえると、公開鍵が顔写真、証明書が公的機関の発行した身分証にあたります。

項目 内容 身分証のたとえ
サブジェクト代替名（SAN） この証明書が有効な名前の一覧。DNS:broker.example.com や IP Address:192.168.1.10 氏名
サブジェクト（CN） 持ち主の名前。名前の確認には SAN が使われるため、新しく作る証明書では接続に使う名前を必ず SAN にも書く 通称
発行者（Issuer） この証明書に署名した CA の名前 発行した役所
有効期間 使い始めの日時（notBefore）と期限（notAfter） 有効期限
公開鍵 持ち主の公開鍵 顔写真
署名 発行者が秘密鍵で付けた署名。改ざんすると署名が合わなくなる 役所の公印

CA と信頼の連鎖

証明書に署名する機関をCA（Certificate Authority、認証局）と呼びます。身分証が信用されるのは、発行した役所が信用されているからです。証明書も同じで、署名した CA を信頼できるかどうかで決まります。

実際には、CA は階層になっています。最上位のルート証明書は自分自身で署名しており、その下の中間証明書を経由して、サーバーの証明書に署名します。この連なりを証明書チェーンと呼びます。

ルート証明書（ルート CA）
自分で自分に署名。クライアント側にあらかじめ入っている
▼ 署名
中間証明書（中間 CA）
サーバーが自分の証明書と一緒に送る
▼ 署名
サーバー証明書
SAN に broker.example.com。サーバーが送る

クライアントは、受け取ったサーバー証明書から署名を1段ずつたどり、手元にあるルート証明書まで行き着ければ「信頼できる」と判断します。手元にあるルート証明書の一覧をルート証明書ストアと呼びます。

Node-RED はどのルート証明書を信頼するか：Node-RED が動く Node.js は、Mozilla が管理するルート証明書の一覧を内蔵しており、既定ではそれを使います。OS やブラウザに追加した証明書は、既定では使われません。このため「ブラウザでは開けるのに Node-RED からはつながらない」ことが起こります。自作の CA や社内の CA を信頼させるには、TLS設定ノードの「CA証明書」で指定します（セクション 9）。

5. 証明書の検証で確かめる3つのこと

ハンドシェイクの③で、クライアントは次の3点を確かめます。1つでも満たさなければ、接続は失敗します。エラーメッセージもこの3種類にほぼ対応するため、原因を切り分けるときの出発点になります。

確かめること 失敗する例 主なエラー
発行元：署名をたどって、信頼するルート証明書に行き着くか 自作の証明書（自己署名、自作 CA）をそのまま使った。サーバーが中間証明書を送っていない self-signed certificate
self-signed certificate in certificate chain
unable to verify the first certificate
unable to get local issuer certificate
名前：接続に使った名前が SAN に載っているか 証明書は raspberrypi.local 用なのに、IP アドレスで接続した Hostname/IP does not match certificate's altnames
有効期間：今の日時が有効期間の中にあるか 更新を忘れて期限が切れた。機器の時計がずれている certificate has expired
certificate is not yet valid

名前の確認は、接続先の URL やブローカー設定に書いた名前で行われます。mqtts://192.168.1.10 と IP アドレスで指定したなら、SAN に IP Address:192.168.1.10 が載っていなければなりません。

有効期間の確認は、クライアントの時計で行われます。ラズパイには電池で動く時計（RTC）が無いため、ネットワークから時刻を合わせる前は、時計が過去の日時のまま動いていることがあります。その間に接続すると、正しい証明書でも certificate is not yet valid（まだ有効期間に入っていない）になります。

6. 証明書ファイルの形式

証明書や鍵のファイルには、中身の書き方（形式）がいくつかあります。拡張子は慣習にすぎず、同じ .crt でも中身の形式が違うことがあります。形式はファイルをテキストエディターで開くと見分けられます。

形式 見分け方 よくある拡張子 TLS設定ノードでの扱い
PEM テキストで開ける。-----BEGIN CERTIFICATE----- や -----BEGIN PRIVATE KEY----- で始まる .pem .crt .cer .key 「個別ファイル」でそのまま使える
DER バイナリで、テキストで開くと文字化けする。PEM と同じ内容をバイナリで書いたもの .der .cer PEM に変換してから使う
PKCS#12 バイナリ。証明書と秘密鍵（と中間証明書）を1つにまとめ、パスワードで保護したもの .pfx .p12 「pfxまたはp12ファイル」で使う

PEM のファイルには、証明書を複数つなげて入れられます。サーバー証明書のあとに中間証明書を続けたファイルは fullchain.pem などと呼ばれ、サーバー側でよく使います。

証明書の中身は openssl コマンドで確かめられます。ラズパイや macOS には最初から入っています。

openssl x509 -in server.crt -noout -subject -issuer -dates -ext subjectAltName

セクション 7 で作るサーバー証明書なら、次のように表示されます（日時は作った日によって変わります）。

subject=CN=localhost issuer=CN=My Local CA notBefore=Sep 24 23:53:53 2026 GMT notAfter=Dec 27 23:53:53 2028 GMT X509v3 Subject Alternative Name: DNS:localhost, DNS:raspberrypi.local, IP Address:127.0.0.1

発行者（issuer）、有効期間（notBefore と notAfter）、名前（Subject Alternative Name）がセクション 5 の3点に対応します。PEM でないファイルを読ませると、Could not find certificate などのエラーになります。DER は次のコマンドで PEM に変換できます。

openssl x509 -inform der -in cert.der -out cert.pem

7. 証明書の入手方法と自作の手順

サーバー証明書の入手方法は3通りあります。Node-RED から公開サービスへ接続するだけなら、証明書を用意する必要はありません。証明書が要るのは、自分でサーバーやブローカーを立てるときと、次のセクションのクライアント証明書を使うときです。

方法 信頼のされ方 向いている場面 注意点
公的な CA から発行を受ける（Let's Encrypt など） ブラウザや Node.js に最初から信頼されている インターネットに公開するサーバー ドメイン名が必要。有効期間が短く、自動更新が前提になる
自己署名証明書 誰からも信頼されない。使う側で1枚ずつ信頼を登録する 一時的な動作確認 サーバーごとに登録が要り、台数が増えると管理できない
プライベート CA（自作の CA）で発行する CA 証明書を配った相手からだけ信頼される 工場や社内 LAN の機器、IoT の検証環境 CA の秘密鍵を厳重に保管する。漏れると、その CA を信頼する相手に対して何にでもなりすませる

LAN の中で使う機器には、プライベート CA が扱いやすい方法です。CA 証明書を1枚配っておけば、あとから増えたサーバーの証明書もすべて信頼されます。以下では、プライベート CA を作り、サーバー証明書とクライアント証明書を発行します。演習2と演習3でもこのファイルを使います。

コマンドはラズパイ（Raspberry Pi OS）のターミナルで実行する想定です。macOS のターミナルでも同じように動きます。Windows では、ラズパイ上で作ったファイルを使うか、WSL の Ubuntu などで実行してください。

手順1：作業フォルダを作る

mkdir -p ~/certs cd ~/certs

手順2：CA を作る

openssl req -x509 -new -newkey rsa:2048 -nodes -keyout ca.key -out ca.crt -days 3650 -subj "/CN=My Local CA"

CA の秘密鍵 ca.key と、CA 証明書 ca.crt ができます。-days 3650 は有効期間（約10年）です。ca.crt は配ってよいファイル、ca.key は証明書を発行するときだけ使う、外に出さないファイルです。

手順3：サーバー証明書を発行する

openssl req -new -newkey rsa:2048 -nodes -keyout server.key -out server.csr -subj "/CN=localhost" printf "subjectAltName=DNS:localhost,DNS:raspberrypi.local,IP:127.0.0.1\n" > server.ext openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out server.crt -days 825 -extfile server.ext

1行目でサーバーの秘密鍵 server.key と、署名を依頼する申請書 server.csr を作ります。2行目で SAN（このサーバーに接続するときに使う名前）を書いたファイルを作り、3行目で CA が署名して server.crt を作ります。

SAN には、クライアントが接続に使う名前をすべて並べます。上の例は、同じラズパイの中から localhost で、LAN の別の PC から raspberrypi.local で接続する場合です。ホスト名を変えている場合や、IP アドレスで接続する場合は、DNS: や IP: の値を実際の名前に合わせてください。

手順4：クライアント証明書を発行する（演習3で使う）

openssl req -new -newkey rsa:2048 -nodes -keyout client.key -out client.csr -subj "/CN=device-001" printf "extendedKeyUsage=clientAuth\n" > client.ext openssl x509 -req -in client.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out client.crt -days 825 -extfile client.ext

手順は同じで、SAN の代わりに「クライアントの身分証として使う」という用途（clientAuth）を書いています。CN=device-001 は機器を見分ける名前です。

手順5：確かめる

openssl verify -CAfile ca.crt server.crt client.crt
server.crt: OK client.crt: OK

両方に OK が出れば成功です。OK 以外（error 20 など）が出た場合は、手順3か手順4で指定した CA のファイル名を確かめてください。ls で、ca.crt、ca.key、server.crt、server.key、client.crt、client.key がそろっていることも確認します（.csr、.ext、.srl は作業用で、以後は使いません）。

最後に、3つの秘密鍵が自分だけ読める権限になっていることを確かめます。すでにそうなっていても、次のコマンドを実行して問題はありません。

chmod 600 ca.key server.key client.key ls -l *.key

3つとも行頭が -rw------- になっていれば完了です。Node-RED は同じユーザーで動いていれば、このままクライアントの秘密鍵を読めます。

8. 相互TLS（クライアント証明書）

ここまでの TLS では、身分証を見せるのはサーバーだけでした。クライアントは、必要ならユーザー名とパスワードなどで別に名乗ります。これに対し、クライアントも証明書を提示する方式を相互TLS（mTLS）と呼びます。

（Node-RED）

①
②
クライアント証明書（秘密鍵を持っている証明つき）
③
お互いに、相手の証明書を自分が信頼する CA で検証する
③
④ 双方の確認が済んでから、暗号化した通信が始まる

相互TLS では、パスワードの代わりに「秘密鍵を持っていること」で機器を識別します。パスワードのように人が入力したり、使い回されたりすることがありません。機器ごとに証明書を発行しておけば、1台が盗まれたときにその証明書だけを無効にできます。このため、IoT のクラウドサービスでよく採用されています。

例：AWS IoT Core

AWS IoT Core の MQTT ブローカーには、相互TLS で接続します。機器（モノ）を登録すると、次のファイルを受け取れます。TLS設定ノードの欄との対応は次のとおりです。

AWS から受け取るもの TLS設定ノードの欄 役割
デバイス証明書（…-certificate.pem.crt） 証明書 Node-RED の身分証
プライベートキー（…-private.pem.key） 秘密鍵 身分証の持ち主であることを示す鍵。発行時にしかダウンロードできない
Amazon ルート CA（AmazonRootCA1.pem） CA証明書 ブローカーの証明書を検証するためのルート証明書

MQTT ブローカー設定では、サーバに AWS が示すエンドポイント（xxxxxxxx-ats.iot.ap-northeast-1.amazonaws.com のような名前）、ポートに 8883 を指定し、「TLSを使用」をオンにして上の TLS設定を選びます。証明書のほかに、AWS 側で接続や送信を許可するポリシーを証明書に付ける必要があります。

ネットワークの都合で 8883 番ポートが使えない場合、AWS IoT Core は 443 番ポートでも MQTT を受け付けます。このとき、同じ 443 番で https と区別するために、TLS設定ノードの「ALPNプロトコル」に x-amzn-mqtt-ca を指定します。ALPN は、ハンドシェイクの中で「この接続でどのプロトコルを話すか」を伝える仕組みです。

9. TLS設定ノードの設定項目

Node-RED では、証明書の指定をノードごとに書くのではなく、TLS設定（tls-config）という設定ノードにまとめます。http request、MQTT ブローカー、WebSocket クライアント、TCP の各ノードは、この TLS設定を選んで共有します。設定を開くには、各ノードの「TLS設定」欄の鉛筆ボタンを押します。

エディターの欄は、最初の「証明書の種類」で切り替わります。以下はその選択肢ごとに、上から表示順に並べています。

証明書の渡し方を選ぶ欄

設定項目 説明 備考

証明書はどこに保存されるか

アップロードとパス指定では、証明書の保存場所が違います。フローを書き出して共有するときに影響します。

  • アップロードした場合：ファイルの中身は、パスワードなどと同じ資格情報（credentials）として、Node-RED の flows_cred.json に保存される。フローを書き出しても証明書と秘密鍵は含まれないため、読み込んだ側でアップロードし直す
  • パスを指定した場合：フローにはパスだけが保存され、Node-RED の起動時とデプロイ時にファイルを読む。フローを別のコンピューターに読み込むと、そのパスにファイルが無ければエラーになる。証明書を更新したら、再デプロイか再起動で読み直させる
  • 環境変数の場合：フローには環境変数の名前だけが保存される。コンテナなど、秘密情報を環境変数で渡す運用に向く

このガイドのサンプルフローと演習の解答は、証明書を含めずに共有できるよう、パス指定で書いています。

「サーバ証明書を確認」をオフにしてつなぐ前に：証明書のエラーは、この欄をオフにすると消えます。しかしオフにすると、セクション 1 の3つのうち「なりすまし」を防げなくなります。暗号化はされますが、相手が偽サーバーでも気づかずにデータやパスワードを渡します。環境変数 NODE_TLS_REJECT_UNAUTHORIZED=0 で Node.js 全体の検証を止める方法も同じで、影響は Node-RED のすべての通信に及びます。
オフにしてよいのは、一時的な切り分けで「証明書以外に問題が無いか」を確かめるときだけです。正しい対処は、自作 CA や社内 CA の証明書を「CA証明書」に指定することです。

10. 各ノードでの使い方

TLS設定を選ぶ欄は、ノードによって置き場所と名前が異なります。

ノード TLS を使う設定 補足
http request URL を https:// で書く。証明書を指定する場合は「SSL/TLS接続を有効化」をオンにし、「TLS設定」を選ぶ 公的な CA の証明書を使うサイトなら、URL を https にするだけでよい。TLS設定を選んでいないときに限り、msg.rejectUnauthorized で検証の有無を指定できる
mqtt in / mqtt out ブローカー設定（mqtt-broker）の「接続」タブで「TLSを使用」をオンにし、「TLS設定」を選ぶ ポートは多くの場合 8883。公的な CA のブローカーでも「TLSを使用」はオンにする
websocket in / out（クライアント接続） URL を wss:// で書き、必要なら「TLS設定」を選ぶ。「TLS設定」欄は URL が wss:// で始まるときだけ表示される Node-RED が待ち受ける WebSocket（サーバー側）は、Node-RED 本体の https 設定に従う
tcp in / tcp out / tcp request 「SSL/TLS接続を有効化」をオンにし、「TLS設定」を選ぶ tcp in の待ち受け（サーバー）で使う場合は、TLS設定の「証明書」と「秘密鍵」にサーバー証明書を指定する
e-mail ノード自身の SSL/TLS と STARTTLS の設定を使う（TLS設定ノードは使わない） Email ガイドを参照
Node-RED エディター、http in settings.js の https に証明書と秘密鍵を書く settings.js ガイドを参照
MQTT は失敗の理由を表示しない：http request は、証明書のエラーを具体的なメッセージで出力します。一方、MQTT ブローカーへの接続は、ログに Connection failed to broker と出るだけで、TLS のどこで失敗したかは表示されません。この場合の調べ方はセクション 15 にまとめています。

12. 演習用の Mosquitto を TLS で動かす

演習2と演習3では、ラズパイに MQTT ブローカーの Mosquitto を入れ、セクション 7 で作った証明書で TLS を有効にします。Node-RED と同じラズパイで動かす想定です。ここでは次の2つの窓口を用意します。

  • 8883 番：サーバー証明書だけを使う TLS（演習2）
  • 8884 番：クライアント証明書も要求する相互TLS（演習3）

手順1：インストールする

sudo apt update sudo apt install -y mosquitto mosquitto-clients

手順2：証明書を Mosquitto 用の場所へコピーする

sudo cp ~/certs/ca.crt ~/certs/server.crt ~/certs/server.key /etc/mosquitto/certs/ sudo chown mosquitto: /etc/mosquitto/certs/server.key sudo chmod 600 /etc/mosquitto/certs/server.key

Mosquitto はユーザー mosquitto の権限で動くため、サーバーの秘密鍵をそのユーザーだけが読めるようにしています。ca.key はコピーしません。ブローカーに要るのは CA 証明書だけです。

手順3：設定ファイルを作る

sudo nano /etc/mosquitto/conf.d/tls.conf

次の内容を書いて保存します。

listener 8883 cafile /etc/mosquitto/certs/ca.crt certfile /etc/mosquitto/certs/server.crt keyfile /etc/mosquitto/certs/server.key listener 8884 cafile /etc/mosquitto/certs/ca.crt certfile /etc/mosquitto/certs/server.crt keyfile /etc/mosquitto/certs/server.key require_certificate true allow_anonymous true

require_certificate true が、8884 番でクライアント証明書を要求する設定です。cafile の CA が発行したクライアント証明書だけが受け入れられます。allow_anonymous true はユーザー名とパスワードなしでの接続を許す設定で、演習を簡単にするためのものです。

1883 番について：Mosquitto 2 系は、listener を1つでも書くと、それまで既定で開いていた 1883 番（localhost のみ）を開かなくなります。暗号化なしの 1883 番も使い続けたい場合は、設定ファイルに listener 1883 localhost を追記してください。

手順4：再起動して確かめる

sudo systemctl restart mosquitto systemctl status mosquitto --no-pager

Active: active (running) と表示されれば起動しています。failed と表示された場合は、sudo journalctl -u mosquitto -n 30 --no-pager で理由を確認します。ファイルのパスの誤りや、秘密鍵を読めない権限の問題が多い原因です。

続いて、Node-RED を使う前に、コマンドでブローカーの TLS を確かめます。

openssl s_client -connect localhost:8883 -CAfile ~/certs/ca.crt < /dev/null 2>&1 | grep "Verify return code"

Verify return code: 0 (ok) が出れば、ブローカーの証明書は自作 CA で検証できています。0 以外の番号が出た場合は、番号の後ろの説明文がセクション 5 のどれにあたるかを見てください。何も表示されない場合は、ブローカーに接続できていません。手順4の起動状態を確認してください。

14. まとめ

論点 要点
TLS の役割 盗み見、書き換え、なりすましの3つを防ぐ。https・wss・mqtts の「s」
位置 TCP と、HTTP や MQTT とのあいだに被せる層。上のプロトコルの中身は変わらない
証明書 公開鍵に持ち主の名前を添えて、CA が署名したもの。秘密鍵とは対で、秘密鍵は外に出さない
検証 発行元（信頼するルートまでたどれるか）、名前（SAN）、有効期間の3点。エラーもこの3種類に分かれる
Node-RED の信頼 Node.js 内蔵のルート証明書を使う。自作 CA や社内 CA は TLS設定の「CA証明書」で指定する
相互TLS クライアントも証明書と秘密鍵を出す。AWS IoT Core などの IoT クラウドで使う
検証をオフにする設定 なりすましを防げなくなる。切り分けの一時的な確認にとどめる

エラーメッセージ（エラーコード） 原因 対処
self-signed certificate
（DEPTH_ZERO_SELF_SIGNED_CERT）		 相手が自己署名証明書を1枚だけ送ってきた その証明書自体を TLS設定の「CA証明書」に指定する。長く使うならプライベート CA で発行し直す
self-signed certificate in certificate chain
（SELF_SIGNED_CERT_IN_CHAIN）		 相手はルートまで含むチェーンを送ってきたが、そのルートを信頼していない。自作 CA や社内 CA の典型 そのルートの CA 証明書を「CA証明書」に指定する
unable to get local issuer certificate
（UNABLE_TO_GET_ISSUER_CERT_LOCALLY）		 チェーンの途中までは届いたが、それを発行したルート証明書が手元に無い。社内ネットワークのプロキシが通信を中継している場合にも起きる ルート証明書を入手して「CA証明書」に指定する。社内プロキシが原因なら、情報システム部門に社内 CA の証明書を確認する。Node-RED 全体で信頼させたい場合は、環境変数 NODE_EXTRA_CA_CERTS に CA 証明書のパスを指定して Node-RED を起動する
unable to verify the first certificate
（UNABLE_TO_VERIFY_LEAF_SIGNATURE）		 サーバーが自分の証明書だけを送り、中間証明書を送っていない。または発行元の CA を信頼していない 自分のサーバーなら、中間証明書をつなげた fullchain を設定する。自作 CA なら「CA証明書」に指定する
Hostname/IP does not match certificate's altnames
（ERR_TLS_CERT_ALTNAME_INVALID）		 接続に使った名前（ホスト名や IP アドレス）が、証明書の SAN に無い SAN に載っている名前で接続する。自分で発行した証明書なら、SAN に名前を追加して発行し直す。メッセージの altnames: の後ろに、証明書に載っている名前が表示される
certificate has expired
（CERT_HAS_EXPIRED）		 証明書の有効期限が切れている。または機器の時計が未来にずれている 証明書を更新する。date コマンドで機器の時刻を確かめる
certificate is not yet valid
（CERT_NOT_YET_VALID）		 機器の時計が過去にずれている。RTC の無いラズパイが、起動直後にまだ時刻を合わせていない場合に起きる timedatectl で「System clock synchronized: yes」になっているか確かめる。時刻の同期を待ってから接続する

症状 原因 対処
MQTT が「接続中」のまま「接続済」にならず、ログは Connection failed to broker だけ MQTT ノードは TLS の失敗理由を表示しない Node-RED が動くコンピューターで openssl s_client -connect ホスト:8883 -CAfile ca.crt を実行し、Verify return code を見る。自分のブローカーなら、ブローカー側のログも確認する

用語 意味
TLS 通信の暗号化、改ざんの検出、相手の確認を行う仕組み。SSL は前身の古い呼び名
ハンドシェイク TLS の通信を始める前に、証明書の確認と暗号の鍵の取り決めを行う手順
公開鍵、秘密鍵 2つで1組の鍵。公開鍵は配ってよく、秘密鍵は持ち主だけが持つ。秘密鍵の署名は公開鍵で確かめられる
証明書 公開鍵に持ち主の名前と有効期間を添え、CA が署名したもの
CA（認証局） 証明書に署名する機関。公的な CA と、自分で作るプライベート CA がある
ルート証明書、中間証明書 CA の階層の最上位と途中の証明書。ルート証明書は自分自身で署名している
証明書チェーン サーバー証明書からルート証明書までの署名の連なり
自己署名証明書 CA を通さず、自分の秘密鍵で自分に署名した証明書
SAN（サブジェクト代替名） 証明書が有効な名前（ホスト名、IP アドレス）の一覧。名前の確認はここで行う
SNI ハンドシェイクの最初に、クライアントが接続先の名前をサーバーに伝える仕組み
ALPN ハンドシェイクの中で、その接続で使うプロトコルを伝える仕組み
相互TLS（mTLS） サーバーだけでなく、クライアントも証明書を提示して身元を示す TLS
PEM、DER、PKCS#12 証明書や鍵のファイル形式。PEM はテキスト、DER はバイナリ、PKCS#12（.pfx / .p12）は証明書と秘密鍵をまとめたもの
CSR 証明書署名要求。CA に署名を依頼するための申請書で、公開鍵と名前を含む
