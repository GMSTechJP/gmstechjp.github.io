1. 概要

Link ノードは、フロー内やフロー間で「仮想的なワイヤー」を作成するノードです。物理的なワイヤーを引かずにノード同士を接続でき、複雑なフローを整理するのに役立ちます。

内線電話に例えると、Link ノードは会社の内線電話システムのようなものです。離れた部署（別のフロータブ）にいる人でも、内線番号（Link名）を使えば直接つながることができます。

Link ノードを使うメリット:

  • ワイヤーの交差を減らしてフローを見やすくする
  • 異なるタブ（フロー）間でメッセージを送受信
  • 共通処理を再利用可能にする
  • サブルーチンのような呼び出しが可能（Link Call）

動作を図で見る

link ノードは、線を引かずに msg を別の場所へ渡します。link out に入った msg は、つながっている link in から出てきます。

link call を使うと、共通の処理を呼び出して、結果を受け取れます。

2. 3種類のLinkノード

📥 Link In

Link In

役割: メッセージの受信口

特徴:

  • Link Out または Link Call からメッセージを受け取る
  • 複数の Link Out から受信可能

📤 Link Out

Link Out

役割: メッセージの送信口

特徴:

  • Link In にメッセージを送信
  • 複数の Link In に同時送信可能

📞 Link Call

Link Call

役割: サブフローを呼び出して結果を受け取る

特徴:

  • Link In を呼び出し、Link Out（return）で結果を受け取る
  • 関数呼び出しのような動作

Link Out と Link Call の違い

特徴Link Out（通常モード）Link Call
動作送りっぱなし（Fire and Forget）結果を待って受け取る
戻り値なしあり（Link Out return経由）
用途通知、ログ記録、分岐共通処理の呼び出し
接続先Link InLink In（return用Link Out必須）

3. 設定詳細

Link In プロパティ

受信口の Link In で設定できる欄は名前だけです。名前の下には、このノードへつながる Link Out や Link Call を選ぶ一覧が並びます（この一覧にラベルはありません）。

設定項目説明既定値
名前このリンクの識別名。Link Out や Link Call の接続先一覧に、この名前が表示される（なし）

Link Out プロパティ

送信口の Link Out は、モードでノードの役割を切り替えます。モードの下に、接続先の Link In を選ぶ一覧が表示されます（この一覧にラベルはありません）。

設定項目説明既定値
モードノードの役割を選ぶ。選択肢は下表の2つ接続された全てのlinkノードへ送信
名前このリンクの識別名（なし）

モードの選択肢:

選択肢意味
接続された全てのlinkノードへ送信通常の送信口。選んだ Link In すべてへメッセージを送る（送りっぱなし）
link callノードへ返却Link Call から呼ばれた処理の戻り口にする。呼び出し元の Link Call へ結果を返す

Link Call プロパティ

Link Call は Link In を呼び出し、戻り口（「link callノードへ返却」モードの Link Out）からの結果を待ちます。「対象を固定で指定」のときは、リンクの種類の下に表示される一覧から呼び出す Link In を選びます。

設定項目説明既定値
タイムアウト呼び出し先からの応答を待つ上限。これを超えるとエラーになる30（秒）
リンクの種類呼び出し先の決め方を選ぶ。選択肢は下表の2つ対象を固定で指定
名前ノードの識別名（なし）

リンクの種類の選択肢:

選択肢意味
対象を固定で指定設定画面で呼び出す Link In を選んでおく
対象を動的に指定 (msg.target)受信したメッセージの msg.target で呼び出し先を切り替える

サンプルフローのインポート方法:

フローの読み解き

読み込むと、「link」「TAB: 1st」「TAB: 2nd」の3つのタブが増えます。例は全部で5つあり、どれも「例N: 実行」（inject）のボタンで動かし、同じ番号の「例N: 結果」（debug）に結果が出ます。link in・link out・link call のノードには名前が付いていないものが多いので、ここでは種類の名前で呼びます。

例 場所と、comment ノードの見出し（意味） ノードの並びと設定 ボタンを押すと出るもの
例1 タブ「link」の上半分。Link output of inject node to input of debug node（inject の出力を、link で debug の入力へつなぐ） 上の行:「例1: 実行」→ link out。下の行: link in →「例1: 結果」。link out の接続先に、下の行の link in を選んである。2つのノードの間に配線は無い。「↓ connect to link in node」「↑ connect from link out node」の comment が、つながりの向きを示している 「例1: 結果」に Hello, World!
例2 タブ「TAB: 1st」と「TAB: 2nd」。Example: Link Node across tabs（タブをまたぐ link ノード） 「TAB: 1st」に「例2: 実行」→ link out、「TAB: 2nd」に link in →「例2: 結果」がある。link out の接続先は、別のタブの link in 「TAB: 1st」でボタンを押すと、「TAB: 2nd」の「例2: 結果」に Hello, World!
例3a タブ「link」の下半分。↓ call link (fixed target)（link を呼び出す。呼び出し先は固定） 「例3a: 実行」→ link call →「例3a: 結果」。link call の「リンクの種類」は「対象を固定で指定」で、呼び出し先に「subroutine-1」（link in）を選んである 「例3a: 結果」に Hello, from subroutine-1
例3b ↓ set msg.target（msg.target を入れる）、↓ call link in (target set by msg.target)（msg.target で決めた link in を呼び出す） 「例3b: 実行」→ link call →「例3b: 結果」。inject が msg.target に、呼び出す link in の名前（subroutine-1）を入れて送る。link call の「リンクの種類」は「対象を動的に指定 (msg.target)」 「例3b: 結果」に Hello, from subroutine-1
例3c ↓ call subroutine-1 from a function（function から subroutine-1 を呼び出す） 「例3c: 実行」→「call subroutine-1」（function）→「例3c: 結果」。function のコードが、node.linkcall('subroutine-1', msg, { timeout: 1000 }) で link in を呼び出し、返ってきた msg を次へ送る 「例3c: 結果」に Hello, from subroutine-1

例3a〜3c は、呼び出し方が違うだけで、呼び出す相手は同じです。相手は、タブ「link」のいちばん下にある、グループ「subroutine-1」です。

呼び出される側 ノードの並びと設定
グループ「subroutine-1」 「subroutine-1」（link in）→ change → link out。change が、msg.payload を文字列の Hello, from subroutine-1 に書き換える。link out は「モード」が「link callノードへ返却」で、呼び出した側へ msg を返す。この link out には、接続先を選んでいない（呼び出した相手へ返すため）。comment の「↑ link node "sunbroutine-1"」は、公式サンプルのつづりのままで、subroutine-1 のことである
  • link out と link in の線: link ノードどうしのつながりは、ふだんは表示されません。link out か link in を1回クリックして選ぶと、相手との間に破線が表示されます。別のタブにある相手は、タブの名前が付いた小さな箱で示されます。
  • 例2の結果が見えないとき: デバッグサイドバーの絞り込みが「現在のフロー」になっていると、開いているタブの debug ノードの出力しか表示されません。「全てのフロー」にするか、「TAB: 2nd」のタブを開いてください。
  • 例1・例2と、例3の違い: 例1・例2の link out は、送ったら終わりです。例3の link call は、呼び出した先から msg が返ってくるまで待ち、返ってきた msg を自分の出力から送ります。返ってこないまま「タイムアウト」（例3a・3b は 30 秒、例3c のコードでは 1000 ミリ秒）を過ぎると、エラーになります。

フローの読み解き

応用フローは、3つの部分に分かれています。各部分の先頭にある comment ノードの名前が、下の表の「部分」に当たります。

部分 ノードの並び 設定と、ボタンを押すと出るもの パターン
基本: Link Out → Link In 「送信」（inject）→「送信口」（link out）、「受信口」（link in）→「受信確認」（debug） 「送信口」の接続先は「受信口」。「送信」を押すと、「受信確認」に Hello via Link! が出る。公式サンプルの例1と同じ作りで、ノードに名前を付けてある パターン1
Link Call（サブルーチン呼び出し）と、その下の【共通処理】2倍にする 呼び出す側:「数値入力」（inject）→「2倍処理を呼び出し」（link call）→「結果: 10」（debug）。呼び出される側:「2倍処理入口」（link in）→「×2」（function）→「結果を返す」（link out） link call の呼び出し先は「2倍処理入口」。「×2」が msg.payload を2倍にし、「結果を返す」（「モード」は「link callノードへ返却」）が呼び出した側へ返す。「数値入力」（5 を送る）を押すと、「結果: 10」に 10 が出る。公式サンプルの例3a と違い、渡した値を使って計算した結果が返る パターン2
複数の送信先 「イベント発生」（inject）→「複数送信」（link out）、「ログ処理」（link in）→「📝 ログ記録」（debug）、「通知処理」（link in）→「🔔 通知送信」（debug） 「複数送信」の接続先に、「ログ処理」と「通知処理」の2つを選んである。「イベント発生」を押すと、「📝 ログ記録」と「🔔 通知送信」の両方に、同じ {"event":"button_click","time":"2024-01-15"} が出る パターン3

パターン4（共通検証処理の再利用）のフローは、公式サンプルにも応用フローにも含まれていません。同じ共通処理を2か所から呼び出す形は、演習4で作ります。

パターン1: 基本的な Link Out → Link In

応用フローの「基本: Link Out → Link In」を参照してください。

用途: ワイヤーを交差させず離れた場所へメッセージを送信

Inject → Link Out - - - Link In → Debug

ポイント: ワイヤーの交差を避けたり、離れた場所にメッセージを送る

パターン2: Link Call（サブルーチン呼び出し）

応用フローの「Link Call（サブルーチン呼び出し）」を参照してください。

用途: 共通処理を呼び出して結果を取得

Inject → Link Call → 結果
【呼び出し先】 2倍処理入口 → ×2 → 結果を返す

ポイント:

  • Link Call は呼び出し先から結果が返るまで待機
  • Link Out のモードを「link callノードへ返却」に設定すると結果を返せる

パターン3: 複数の送信先

応用フローの「複数の送信先」を参照してください。

用途: 1つの送信元から複数の受信先へ同時に送信

Link Out - - -受信A - - -受信B

ポイント: 1つの Link Out から複数の Link In に送信可能

パターン4: 共通検証処理の再利用

このパターンのフローは、サンプルフローには含まれていません。

用途: 同じ検証処理を複数箇所から呼び出して再利用

テストA → 検証呼出 → 結果
テストB → 検証呼出 → 結果

ポイント: 同じ検証ロジックを複数箇所から呼び出して再利用

演習1: 基本的なLink接続 初級

課題:Link Out と Link In を使って、ワイヤーを引かずにメッセージを送信するフローを作成してください。

💼 使いどころ: ワイヤーの交差を避けて離れた場所へメッセージを送りたい場面で使います。

成功の条件:

  • Inject と Link Out の間、Link In と Debug の間のみワイヤーで接続されており、Link Out と Link In の間にワイヤーが引かれていない
  • Injectボタンをクリックすると、デバッグサイドバーにメッセージが表示される（Linkを経由してメッセージが届いている）
  • Link Out の設定を開くと、接続先の Link In ノードが選択されている
  • Debugノードのステータス欄にも受信したメッセージが表示される
💡 ヒント

1. Link Out ノードの設定で、接続先の Link In を選択します

2. 名前を分かりやすくつけると管理しやすくなります

課題:Link Call を使って「入力値を3倍にする」共通処理を作成し、呼び出すフローを作ってください。

2. 呼び出し側: Inject → Link Call → Debug

演習4: 再利用可能な検証処理 上級

課題:「入力値が正の数かどうかを検証する」共通処理を Link Call で作成し、複数箇所から呼び出せるようにしてください。

💼 使いどころ: 複数箇所から同じ検証処理を呼び出し、ロジックを1箇所にまとめたい場面で使います。

要求仕様:

  • 正の数: msg.valid = true, msg.payload = 元の値
  • 負の数または0: msg.valid = false, msg.error = "正の数を入力してください"

成功の条件:

  • 「正の数: 10」ボタンをクリックすると、デバッグサイドバーに msg.valid = true、msg.payload = 10 を含む結果が表示される
  • 「負の数: -5」ボタンをクリックすると、msg.valid = false、msg.error = "正の数を入力してください" を含む結果が表示される
  • 両方のInjectボタンが同じLink Call（同じ検証共通処理）を呼び出しており、検証ロジックが1箇所に集約されている
  • Debugノードのステータス欄に msg.valid の値（true / false）が表示される
💡 ヒント

Switch ノードで条件分岐を行い、出力ごとに Change ノードで結果を msg に設定して返します。

  • Switch: プロパティ msg.payload、ルール1「>」（数値 0）、ルール2「その他」
  • 1つ目の出力の Change: 「値の代入」で msg.valid に「真偽」の true
  • 2つ目の出力の Change: 「値の代入」で msg.valid に「真偽」の false、msg.error に文字列「正の数を入力してください」
  • 2つの Change は、どちらも同じ Link Out（「link callノードへ返却」）につなぐ

6. まとめ

重要ポイント:

  • Link Out → Link In: ワイヤーなしでメッセージを送信（一方向）
  • Link Call: サブルーチン呼び出しのように結果を受け取れる
  • 異なるタブ間でもメッセージを送受信可能
  • 複雑なフローを整理してメンテナンス性を向上

注意事項:

  • Link Call を使う場合、呼び出し先に Link Out（返却モード）が必要
  • 循環参照（A→B→A）を作らないよう注意
  • タイムアウト設定を適切に行う（デフォルト30秒）
  • 名前を分かりやすくつけて管理しやすくする
