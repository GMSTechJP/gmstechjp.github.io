1. 2台のコンピュータをつなぎたい

コンピュータの中のデータは、すべて 0 と 1 の並びです。文字も数値も画像も、最終的には 0 と 1 の列になっています。2台のあいだでデータを渡すには、この 0 と 1 を相手へ運べばよいことになります。

困った

0 と 1 を、線の向こうの相手にどう伝えればよいか分からない。こちらが勝手に決めた伝え方では、相手が読み取れない。

→
生まれた ケーブルと信号の規格

どんな線を使い、電圧や光の変化をどう 0 と 1 に対応させるかを、送る側と受ける側で共通に決めた。

たとえば電圧が高いときを 1、低いときを 0 と決めておけば、電圧の変化で 0 と 1 を送れます。実際にはもっと工夫された方式を使いますが、考え方は同じです。運び手になるものは用途によって違います。

運び手0 と 1 の表し方身近な例
銅線（LAN ケーブル）電気信号の変化パソコンやラズパイの LAN ポートに挿すケーブル
光ファイバ光の点滅建物に引き込む光回線
電波電波の変化Wi-Fi、携帯電話の回線

コネクタの形、ケーブルの種類、信号の速さまで含めて規格として決めておくことで、別々の会社が作った機器どうしでもつながるようになりました。ここで決めているのは「0 と 1 を運ぶ」ところまでです。運んだ 0 と 1 がどういう意味を持つかは、この後の技術が決めていきます。

2. たくさんのコンピュータをつなぎたい（Ethernet）

2台がつながると、次は3台、10台とつなぎたくなります。ここで最初の問題にぶつかります。

困った

全員を 1 対 1 のケーブルで結ぶと、本数が爆発する。10台なら 45 本、100台なら 4950 本になる。

→
生まれた 共有の通り道

1本の線（のちに中継機器）に全員をつなぎ、みんなで同じ通り道を使う。

全員が同じ通り道につながると、誰かが送った信号は全員に届きます。すると、すぐに次の問題が出てきます。

誰宛てか分からない

困った

全員に信号が届くので、受け取ったデータが自分宛てなのか、他の誰か宛てなのか区別できない。

→
生まれた MAC アドレスとフレーム

機器ごとに重ならない番号を付け、データの先頭に「宛先」と「送信元」を書いた決まった形で送る。

MAC アドレスは、ネットワークにつなぐ部品（LAN ポートや Wi-Fi の部品）に割り当てられた番号です。00:1a:2b:3c:4d:5e のように、16 進数 12 桁（48 ビット）で書きます。前半 6 桁が製造した会社を表し、後半を会社が重ならないように割り当てます。基本的には工場出荷時に決まっている番号です。

データは、宛先と送信元を書き込んだ決まった形にして送ります。この 1 回分のまとまりをフレームと呼びます。受け取った機器は宛先の MAC アドレスを見て、自分宛てでなければ捨てます。

宛先 MAC 送信元 MAC データ（1 回に最大 1500 バイト程度） 誤り検出用の値
フレームのおおまかな形。末尾の値で、途中でデータが壊れていないかを受け手が確かめる

1 回に送れるデータの量に上限があるのは、1 台が長いデータを流し続けると、そのあいだ他の機器が通り道を使えなくなるためです。大きなデータは小分けにして、複数のフレームで送ります。

同時に話すとぶつかる

困った

1本の通り道を共有しているので、2台が同時に送ると信号が混ざって壊れる（衝突）。

→
生まれた 送る前に様子を見る決まり

誰も送っていないのを確かめてから送り、衝突したら少し待って送り直す（CSMA/CD）。

会議で発言するときに、誰も話していないのを確かめてから話し始め、2人が同時に話し始めたら一度やめて譲り合うのと同じです。待つ時間を機器ごとにばらつかせることで、何度も同じ相手とぶつかるのを避けます。

全員に届くのは無駄

困った

台数が増えると、自分に関係ないデータまで全員に届き、衝突も増える。通り道が混み合って遅くなる。

→
生まれた スイッチ

どの差し込み口の先に、どの MAC アドレスの機器がいるかを覚え、宛先の機器がいる口にだけフレームを送る中継機器。

初期の中継機器（ハブ）は、受け取った信号をすべての差し込み口へそのまま流していました。スイッチは、流れてきたフレームの送信元 MAC アドレスを見て「3 番の口の先には …:4d:5e がいる」と覚えていきます。この対応表を MAC アドレステーブルと呼びます。以後はその機器宛てのフレームを 3 番の口にだけ送るので、関係ない機器にはデータが届きません。

スイッチは送信元 MAC アドレスから「どの口に誰がいるか」を学んで使う

現在の有線 LAN では、機器とスイッチを 1 本ずつのケーブルで結び、送信と受信を同時に行えるつなぎ方（全二重）で通信します。このつなぎ方では衝突そのものが起きないため、上の「様子を見てから送る」決まりは実際にはほとんど働いていません。困りごとが別の技術で解決され、古い解決策が出番を失った例です。

ここまでをまとめて Ethernet：ケーブルと信号の規格、MAC アドレス、フレームの形、スイッチによる中継。これらをまとめた LAN の規格が Ethernet（イーサネット）です。Wi-Fi は運び手が電波になりますが、MAC アドレスで相手を区別する考え方は同じです。

3. ネットワーク同士をつなぎたい（IP とルーター）

Ethernet で、1つの建物や1つのフロアの機器はつながりました。次は、工場と事務所、会社と会社、そして世界中のネットワークをつなぎたくなります。

困った

世界中を1つの大きな Ethernet にすると破綻する。スイッチは世界中の機器を覚えきれず、全員宛ての連絡が世界中に流れる。しかも MAC アドレスは製造番号なので、番号を見ても相手がどこにいるのか分からない。

→
生まれた IP アドレスとルーター

ネットワークを小さく分け、分けたネットワーク同士を中継機器でつなぐ。相手の「場所」を表す番号を別に用意する。

場所を表す番号：IP アドレス

MAC アドレスが「生まれたときに付いた名前」だとすると、IP アドレスは「今いる場所の住所」です。192.168.1.10 のように 4 つの数字（それぞれ 0〜255）で書きます。

住所に「都道府県、市区町村」と「番地」があるように、IP アドレスも前半がどのネットワークか、後半がそのネットワークの中のどの機器かを表します。どこまでが前半かは、192.168.1.10/24 の /24（先頭から 24 ビット、つまり最初の 3 つの数字）や、255.255.255.0 というサブネットマスクで示します。

IP アドレスネットワーク部（/24 の場合）ホスト部住所のたとえ
192.168.1.10192.168.110「〇〇町 1 丁目」の「10 番地」
192.168.1.25192.168.125同じ町内の「25 番地」
192.168.2.10192.168.210隣の町の「10 番地」

MAC アドレスは機器を持ち運んでも変わりませんが、IP アドレスはつなぐネットワークが変われば変わります。ノートパソコンを会社から自宅へ持ち帰ると、IP アドレスが変わるのはこのためです。

ネットワークの境目をつなぐ：ルーター

ルーターは、複数のネットワークの境目に立つ中継機器です。受け取ったデータの宛先 IP アドレスのネットワーク部を見て、「そのネットワークへ行くには、次にどのルーターへ渡せばよいか」を表（ルーティングテーブル）で調べ、次へ渡します。

郵便にたとえると、ルーターは各地の郵便局です。どの郵便局も世界中の家を知っているわけではありません。「この町宛てなら、あちらの局へ回す」ということだけを知っていて、局から局へ手渡ししていくうちに、最終的に宛先の町の局に届きます。こうしてネットワークからネットワークへ渡していくことをルーティングと呼びます。

自分のネットワークの外へ出すデータを最初に預ける先をデフォルトゲートウェイと呼びます。家庭や工場の LAN では、ふつうは出入口のルーターがこれにあたります。ラズパイのネットワーク設定に出てくる「ゲートウェイ」の欄はこれです。

迷子のデータを消す仕組み：ルーターの設定の誤りで、データが同じところを回り続けることがあります。そのため IP のデータには「あと何回中継してよいか」を表す数（TTL）が付いていて、ルーターを通るたびに 1 ずつ減り、0 になったら捨てられます。

IP と MAC の役割分担

困った

宛先の IP アドレスは分かった。でも実際に線の上でデータを運ぶのは Ethernet で、Ethernet は MAC アドレスしか分からない。隣の機器の MAC アドレスをどう知るか。

→
生まれた ARP

「IP アドレスが 192.168.1.1 の機器は、MAC アドレスを教えて」と同じネットワークの全員に呼びかけ、本人だけが答える仕組み。

ここで、IP と Ethernet の役割がはっきり分かれます。IP アドレスは最終的な宛先を表し、途中で変わりません。MAC アドレスは「次の中継先まで」の宛先を表し、ルーターを通るたびに書き換わります。

区間宛先 MAC（次に渡す相手）宛先 IP（最終的な相手）
ラズパイ → 自宅のルーター自宅のルーターサーバー
自宅のルーター → プロバイダのルータープロバイダのルーターサーバー
……（いくつものルーター）次のルーターサーバー
最後のルーター → サーバーサーバーサーバー
宅配便の伝票（IP）はそのままで、区間ごとに運ぶトラック（Ethernet）の行き先だけが変わる

住所が足りない

困った

いまの IP アドレス（IPv4）は 32 ビットで、全部で約 43 億個しかない。パソコン、スマートフォン、IoT 機器のすべてに配るには足りない。

→
生まれた プライベート IP アドレスと NAT、そして IPv6

建物の中だけで使う番号を決め、外へ出るときだけ出入口で外向きの番号に付け替える。あわせて、番号の桁数を大きく増やした新しい版も作った。

次の範囲はプライベート IP アドレスと決められていて、どの組織でも自由に使えます。そのかわり、インターネット上では宛先として使えません。家庭や工場でよく見る 192.168.x.x はこれです。

範囲よく見る場面
10.0.0.0 〜 10.255.255.255大きな組織の LAN、クラウドの仮想ネットワーク
172.16.0.0 〜 172.31.255.255組織の LAN、Docker の内部ネットワーク
192.168.0.0 〜 192.168.255.255家庭や小規模な事業所の LAN

LAN の中の機器がインターネットへ出るとき、出入口のルーターが送信元をルーター自身の外向きの IP アドレス（グローバル IP アドレス）に付け替えます。これを NAT と呼びます。1 つのグローバル IP アドレスを LAN の中の何台もの機器で共有できるので、アドレスの不足を大きく和らげました。代表電話番号から各部署の内線へつなぐ仕組みに似ています。

その結果として、インターネット側から LAN の中の機器へ直接つなぎにいくことは、ふつうはできません。ラズパイの Node-RED に外から直接アクセスできないのはこのためです。一方、ラズパイから AWS IoT Core のようなクラウドへ接続しにいくことは問題なくできます。IoT 機器が「外で待ち受ける」のではなく「クラウドへつなぎにいく」形をとることが多いのは、この事情によります。

根本的な解決策として、アドレスを 128 ビットに増やした IPv6 も作られ、普及が進んでいます。2001:db8::1 のように 16 進数とコロンで書きます。

住所を配る手間も減らした：機器をつなぐたびに IP アドレス、サブネットマスク、ゲートウェイを手で設定するのは大変で、番号の重複も起きます。そこで、つないだ機器に空いている番号を自動で貸し出す DHCP が生まれました。ルーターが担当していることが多く、ラズパイを LAN につなぐだけで IP アドレスが付くのはこのためです。センサーを集める機器のように、番号が変わると困る機器は、固定の番号を設定するか、ルーター側で同じ番号を割り当て続けるように設定します。

4. 確実に、アプリまで届けたい（TCP、UDP、ポート番号）

IP のおかげで、世界中のどの機器にもデータを送れるようになりました。しかし IP は、届けるための努力はするものの、届いたことまでは保証しません。

困った

途中のルーターが混み合うと、データは捨てられることがある。経路が変わると、後から送ったデータが先に着くこともある。大きなデータを小分けにして送ると、欠けたり順番が入れ替わったりして、元に戻せない。

→
生まれた TCP

送る前に相手と接続を確立し、データに通し番号を付けて送る。受け手は受け取ったことを知らせ、返事がなければ送り手が送り直す。

TCP は、IP の上で次の工夫をして「欠けずに、順番どおりに届く」ことを実現します。

工夫解決する困りごとたとえ
接続の確立（3 ウェイハンドシェイク）相手が受け取れる状態か分からないまま送ってしまう「もしもし」「はい、聞こえます」「では話します」
通し番号（シーケンス番号）順番が入れ替わる、どこが欠けたか分からない荷物に「3 箱中の 2 箱目」と書く
受け取り確認（ACK）と再送途中で消えたことに気づけない書留の受領印。届かなければ再発送
流量の調整受け手や途中の経路の処理が追いつかず、あふれる相手が「少し待って」と言えるようにする

3 ウェイハンドシェイクは、送り手が接続を申し込み（SYN）、受け手が承諾と申し込みを返し（SYN+ACK）、送り手が承諾する（ACK）3 回のやり取りです。この 3 回が終わってから、データを流し始めます。

どのアプリ宛てか分からない

困った

1 台のコンピュータの中では、Web サーバー、MQTT ブローカー、Node-RED など、いくつものアプリが同時に通信している。IP アドレスで機器までは届いても、どのアプリに渡せばよいか分からない。

→
生まれた ポート番号

機器の中の窓口に 0〜65535 の番号を付け、アプリはそれぞれ決まった窓口で待ち受ける。

IP アドレスが建物の住所なら、ポート番号は建物の中の部屋番号です。よく使う番号は用途ごとに決まっていて、Web は 80（https なら 443）、MQTT は 1883、Modbus TCP は 502 です。Node-RED のエディターを開く http://localhost:1880 の 1880 もポート番号です。

送る側も、自分側のポート番号を送信元として書き込みます。こちらは OS が空いている番号を自動で選びます。そのため、同じブラウザで同じサーバーに複数のタブからつないでも、返事がどのタブ宛てかを区別できます。

確認を待つ時間がもったいない

困った

TCP は確実だが、接続の確立や受け取り確認に時間がかかる。映像や音声、次々に送られてくるセンサー値のように、少し欠けても最新のデータが早く届く方がよい用途には重すぎる。

→
生まれた UDP

接続の確立も受け取り確認も再送もしない。ポート番号だけを付けて、送りっぱなしにする。

UDP は、TCP から「確実に届ける工夫」を取り除いた軽い方式です。欠けても送り直さない代わりに、待ち時間がありません。欠けたときにどうするかは、UDP を使うアプリ側で決めます。

TCPUDP
接続の確立するしない
欠けたときの再送するしない
順番の保証するしない
速さ、軽さやや重い軽い
上で動く代表例HTTP、MQTT、Modbus TCP、SMTPDNS の問い合わせ、映像や音声の配信、機器の発見
Node-RED のノードtcp in / tcp out / tcp requestudp in / udp out

5. 数字の住所を覚えられない（DNS）

ここまでで、IP アドレスとポート番号さえ分かれば、世界中のアプリと確実に通信できるようになりました。ただし、使う人間にとっては別の問題が残ります。

困った

203.0.113.5 のような数字は覚えられない。サーバーを引っ越して IP アドレスが変わると、使う側が全員、番号を書き換えなければならない。

→
生まれた 名前と番号の対応表（hosts ファイル）

「この名前はこの IP アドレス」という対応表を各機器に置き、名前で指定できるようにした。

初期のインターネットでは、全機器の名前と IP アドレスの対応表を 1 か所で管理し、各機器が定期的にその表を取り寄せていました。この名残が、今も OS の中にある hosts ファイルです。

困った

つながる機器が増えると、1 つの表では管理しきれない。追加や変更のたびに全員が表を取り寄せ直すのも追いつかない。

→
生まれた DNS

名前を階層に分け、階層ごとに担当するサーバーを分散させる。問い合わせを受けたサーバーは、上の階層から順にたどって答えを見つける。

DNS（Domain Name System）では、api.example.com のような名前（ドメイン名）を、右から左へ大きな区分から小さな区分へと読みます。それぞれの区分に担当のサーバーがいて、自分の担当範囲だけを知っています。

ラズパイ「api.example.com の IP アドレスは？」問い合わせ担当の DNS サーバー
①ルートサーバー「.com なら、あちらのサーバーへ」
②.com の担当「example.com なら、あちらのサーバーへ」
③example.com の担当「api.example.com は 203.0.113.5」
ラズパイ「203.0.113.5 です」（答えは一定時間覚えておく）問い合わせ担当の DNS サーバー
①〜③は問い合わせ担当の DNS サーバーが代わりにたどる。電話帳を 1 冊にせず、地域ごとの電話帳と「どの地域の電話帳を見ればよいか」の案内に分けた形

機器が最初に問い合わせる先は、DHCP で配られた DNS サーバー（多くは家庭や工場のルーターか、プロバイダのサーバー）です。このサーバーが①〜③を代わりにたどり、答えを返します。一度調べた答えは、決められた時間（TTL）だけ覚えておき、同じ問い合わせにはすぐ答えます。そのため、サーバーの IP アドレスを変えても、古い答えが消えるまで一部の利用者は古い番号へつなぎにいくことがあります。

LAN の中の名前：raspberrypi.local：家庭や工場の LAN には、ふつう自分の機器を登録した DNS サーバーがありません。そこで、「raspberrypi.local の人はいますか」と LAN の全員に呼びかけ、本人が答える仕組み（mDNS）が使われます。パソコンからラズパイへ、IP アドレスを調べなくても raspberrypi.local という名前でつなげるのはこのためです。末尾の .local が、DNS ではなくこの仕組みを使う目印です。

6. 途中で覗かれたくない（TLS）

インターネットは、多くの組織のルーターを経由してデータを運びます。ここまでの技術は、どれも「届けること」を目的にしていて、途中で誰かに見られることは想定していません。

困った

途中の機器を通るデータは、そのままでは誰でも読める。書き換えられても気づけない。偽のサーバーに誘導されても、相手が本物か確かめられない。

→
生まれた TLS

TCP の接続の上に暗号の層を被せ、中身を暗号化し、改ざんを検出し、証明書で相手が本物かを確かめる。

TLS も、いくつかの困りごとを順に解決して組み上がっています。

困った生まれた郵便のたとえ
中身を読まれる共通の鍵による暗号化。送り手と受け手が同じ鍵を持ち、その鍵がなければ読めない形にする中身の見えない封筒
その共通の鍵を、盗み見される通り道でどう相手に渡すか鍵交換。互いに見られてもよい値だけをやり取りし、両者の手元で同じ鍵を作り出す鍵そのものは運ばず、両者が同じ鍵を組み立てられる材料だけを送る
途中で書き換えられるデータごとに検査用の値を付け、1 ビットでも変わると受け手が検出する開けると跡が残る封印
相手が偽物かもしれない証明書と認証局。信頼できる第三者が「このサーバーは本物」と署名した証明書を、サーバーが提示する公的機関が発行した身分証

暗号化と相手の確認は、両方がそろって意味を持ちます。暗号化だけなら偽のサーバーとのあいだでも成立してしまい、封筒に入れて渡した相手が偽物なら中身は読まれるからです。

URL の https://、wss://、MQTT の mqtts:// の「s」は、TLS で守られた通信であることを表します。TLS は HTTP や MQTT の中身を変えず、その下に 1 枚挟まる層として働きます。証明書の検証の仕組み、ファイル形式、Node-RED での設定は TLSと証明書ガイドで詳しく扱います。

7. 積み重なった結果：TCP/IP の階層

ここまでの技術を、生まれた順に下から積み上げると、次の形になります。下の層は上の層の中身を気にせずに運び、上の層は下の層がどう運んでいるかを気にせずに使えます。この分担を、使われている代表的な 2 つのプロトコルの名前をとって TCP/IP の階層（4 階層モデル）と呼びます。

アプリケーション層
HTTP、MQTT、Modbus TCP、SMTP、DNS など。アプリ同士が何を話すか（通信の型）。TLS はこの層と下の層のあいだに挟まる
トランスポート層
TCP、UDP。どのアプリ宛てか（ポート番号）、確実に届けるか
インターネット層
IP、ルーター。どのネットワークのどの機器か（IP アドレス）
リンク層
Ethernet、Wi-Fi。隣の機器まで運ぶ（MAC アドレス、ケーブルと信号）
層解決した困りごと宛先を表すもの中継する機器
アプリケーション層アプリ同士の話し方をそろえたいURL のパス、MQTT のトピックなど（アプリ自身）
トランスポート層確実に、アプリまで届けたいポート番号（両端の機器だけが扱う）
インターネット層ネットワーク同士をつなぎたいIP アドレスルーター
リンク層たくさんの機器をつなぎたいMAC アドレススイッチ

封筒の入れ子（カプセル化）

送るときは、上の層から順に、自分の層に必要な宛先情報（ヘッダー）を付けて下の層へ渡します。封筒を封筒で包んでいくのと同じです。受け取った側は外側から順に開け、それぞれの層が自分宛ての情報だけを読んで、中身を上の層へ渡します。この包み方をカプセル化と呼びます。

Ethernet ヘッダー（宛先 MAC、送信元 MAC）
IP ヘッダー（宛先 IP、送信元 IP、TTL）
TCP ヘッダー（宛先ポート 443、送信元ポート、通し番号）
TLS（ここから内側は暗号化されている）
HTTP：GET /weather/tokyo ……（アプリのデータ）
https で送るデータの包まれ方。スイッチは一番外側、ルーターは IP ヘッダーまでを見て運ぶ

この形になっているおかげで、途中の機器は必要なところだけを見れば済みます。スイッチは外側の MAC アドレスだけを、ルーターは IP アドレスまでを見て運びます。TLS で暗号化された内側は、途中の機器からは読めません。それでも宛先の IP アドレスとポート番号は外側に書かれているので、データは問題なく運ばれます。

OSI 参照モデルとの関係：ネットワークの教科書では、層を 7 つに分けた OSI 参照モデルもよく登場します。こちらは通信を説明するための整理の枠組みで、実際のインターネットは 4 階層の TCP/IP で動いています。対応はおおむね、OSI の 1〜2 層（物理層、データリンク層）がリンク層、3 層（ネットワーク層）がインターネット層、4 層（トランスポート層）がトランスポート層、5〜7 層がアプリケーション層です。「L2 スイッチ」「L3 スイッチ」のように製品名に出てくる番号は、この OSI の層の番号です。

8. 通しで見る：Node-RED が https の API を呼ぶまで

ラズパイの Node-RED で、http request ノードが https://api.example.com/weather/tokyo を呼ぶ場面を例に、これまでの技術がどの順で働くかを並べます。

  1. DNSURL から名前 api.example.com を取り出し、DNS サーバーに問い合わせて IP アドレス（例：203.0.113.5）を得る。
  2. IP宛先 203.0.113.5 のネットワーク部を自分のものと比べ、LAN の外だと判断する。データはデフォルトゲートウェイ（ルーター）へ預けることにする。
  3. ARPルーターの MAC アドレスをまだ知らなければ、ARP で問い合わせる。
  4. TCPスキームが https なので宛先ポートは 443。サーバーと 3 ウェイハンドシェイクを行い、接続を確立する。
  5. TLSTLS のハンドシェイクを行う。サーバーの証明書を検証し、鍵交換で暗号化の鍵を取り決める。
  6. HTTP暗号化された通り道の中で、HTTP のリクエスト GET /weather/tokyo を送る。
  7. ルーターデータは、いくつものルーターに手渡しされながらサーバーへ届く。途中で MAC アドレスは区間ごとに書き換わり、IP アドレスは変わらない。
  8. HTTPサーバーがレスポンスを同じ経路の逆向きで返し、http request ノードが msg.payload として次のノードへ渡す。

Node-RED のフロー上では、1 つのノードを通過しただけに見えます。その裏では、ここまでに見てきた技術がすべて順に働いています。MQTT の場合も、手順 6 が MQTT の接続とメッセージの送信に変わるだけで、手順 1〜5 は同じです。

9. 「つながらない」を層で切り分ける

通信がうまくいかないとき、どの層で止まっているかが分かれば、確認する場所を絞れます。Node-RED のデバッグサイドバーやノードの状態表示に出るエラーの多くは、Node.js が報告するエラーコードです。代表的なものを、このページのどの段階の失敗かで分けると次のようになります。

よく見る表示止まっている段階意味まず確かめること
ENOTFOUND
EAI_AGAIN		5. DNS名前から IP アドレスを引けなかった名前のつづり、DNS サーバーの設定、インターネットへの接続

ETIMEDOUT3〜4. IP または TCP送ったが返事が来ないまま時間切れになった相手の電源、途中のファイアウォールによる遮断

404、401、500 などの数値アプリケーション層通信自体は成功し、HTTP のサーバーが結果として返したURL のパス、認証情報、サーバー側の状態（HTTP ガイド）

下の層ほど先に働くので、切り分けも下から順に見ていくと迷いません。たとえば ECONNREFUSED が出ているなら、DNS と IP の段階は通過して相手の機器には届いています。疑う範囲は「相手の機器の中で、そのポートのアプリが動いているか」まで絞れます。エラーの読み方全般は第0章のデバッグのガイドも参照してください。

「数値のステータスコードが返ってきた」は、通信の成功：404 や 500 が返ってきたなら、DNS、IP、TCP、TLS はすべて成功しています。サーバーまでたどり着き、サーバーが「そのページはない」「中で失敗した」と答えた状態です。ネットワークの設定を疑う前に、URL や送っている中身を確認します。

10. 用語集

このページに出てきた言葉を、登場した順に並べました。通信の基礎（ネットワーク入門）の用語集もあわせて参照してください。

用語ひとことで言うと生まれた理由
Ethernet有線 LAN の規格。ケーブルと信号、MAC アドレス、フレームの形などを決めているたくさんの機器を 1 つのネットワークにつなぐため
MAC アドレスネットワークの部品ごとに割り当てられた 48 ビットの番号（例：00:1a:2b:3c:4d:5e）共有の通り道で、誰宛てかを区別するため
フレームEthernet で送るデータ 1 回分のまとまり。宛先と送信元の MAC アドレスが付く宛先付きの決まった形で送るため
ハブ受け取った信号をすべての差し込み口へ流す、初期の中継機器複数の機器を 1 つの通り道につなぐため
スイッチMAC アドレスを学習し、宛先がいる差し込み口にだけ送る中継機器関係ない機器にまでデータが届く無駄をなくすため
IP アドレスネットワーク上の場所を表す番号（例：192.168.1.10）。前半がネットワーク、後半が機器を表すネットワーク同士をつないだとき、相手の場所を示すため
サブネットマスクIP アドレスのどこまでがネットワーク部かを示す値（例：255.255.255.0、/24）同じネットワークの相手かどうかを判断するため
ルーターネットワークの境目に立ち、宛先 IP アドレスを見て次の中継先へ渡す機器分けたネットワーク同士をつなぐため
ルーティングルーターからルーターへ手渡しして、宛先のネットワークまで運ぶこと世界中の経路を 1 台で知らなくても届けるため
デフォルトゲートウェイ自分のネットワークの外へ出すデータを最初に預けるルーター外への出口を 1 か所に決めるため
TTLIP では「あと何回中継してよいか」、DNS では「答えを覚えておいてよい時間」を表す値迷子のデータや古い答えが残り続けないようにするため
ARPIP アドレスから、同じネットワーク内の相手の MAC アドレスを調べる仕組みIP で決めた宛先へ、Ethernet で実際に運ぶため
プライベート IP アドレス組織の中だけで自由に使える IP アドレスの範囲（例：192.168.x.x）IPv4 アドレスの不足を補うため
グローバル IP アドレスインターネット上で重複しない IP アドレスインターネットで宛先として使うため
NATLAN から外へ出るとき、送信元のアドレスを出入口のルーターの外向きの番号に付け替える仕組み1 つのグローバル IP アドレスを複数台で共有するため
IPv4 / IPv6IP の版。IPv4 は 32 ビット（約 43 億個）、IPv6 は 128 ビットIPv6 は IPv4 のアドレス不足を根本から解決するため
DHCPつないだ機器に IP アドレスや DNS サーバーの情報を自動で貸し出す仕組み手作業の設定と番号の重複をなくすため
TCP接続を確立し、欠けずに順番どおりに届けるトランスポート層のプロトコルIP だけでは届いたことを保証できないため
3 ウェイハンドシェイクTCP が接続を始めるときの 3 回のやり取り（SYN、SYN+ACK、ACK）相手が受け取れる状態かを確かめてから送るため
シーケンス番号 / ACKデータに付ける通し番号と、受け取ったことを知らせる返事欠けや順番の入れ替わりに気づき、送り直すため
UDP接続も確認も再送もしない、軽いトランスポート層のプロトコル確実さより速さが大事な用途のため
ポート番号1 台の中の窓口番号（0〜65535）。アプリごとに待ち受ける番号を持つ機器の中のどのアプリ宛てかを区別するため
hosts ファイル名前と IP アドレスの対応を書いた、各機器の中のファイル数字ではなく名前で相手を指定するため
DNS名前から IP アドレスを調べる、階層に分かれて分散した仕組み1 つの対応表では管理しきれなくなったため
mDNSLAN の全員に呼びかけて名前を解決する仕組み。.local で終わる名前で使うDNS サーバーのない LAN でも名前でつなぐため
TLSTCP の上に被せて、暗号化、改ざん検出、相手の確認を行う層途中で覗かれたり、偽物につながされたりするのを防ぐため
証明書 / 認証局サーバーが本物であることを、信頼できる第三者（認証局）が署名で保証したもの暗号化の相手が本物かを確かめるため
TCP/IP（4 階層モデル）リンク層、インターネット層、トランスポート層、アプリケーション層に分けた、インターネットの層の分担各層が他の層の事情を気にせず役割を果たせるようにするため
OSI 参照モデル通信を 7 つの層に分けて説明する枠組み。「L2」「L3」の番号はここから来ている通信の機能を整理して説明するため
カプセル化上の層のデータを、下の層がヘッダーを付けて包んでいくこと途中の機器が、自分の層の情報だけを見て運べるようにするため

11. まとめ

  • 2 台をつなぐために、0 と 1 を運ぶケーブルと信号の規格が生まれた。
  • たくさんつなぐために、MAC アドレス、フレーム、スイッチが生まれ、まとめて Ethernet になった。
  • ネットワーク同士をつなぐために、場所を表す IP アドレスとルーターが生まれた。IP は最終的な宛先、MAC は次の中継先を表す。
  • 確実に届けるために TCP、アプリを区別するためにポート番号、速さを優先するために UDP が生まれた。
  • 名前で呼ぶために、対応表を階層に分けて分散させた DNS が生まれた。
  • 安全に送るために、暗号化と相手の確認を行う TLS が生まれた。
  • これらは下から順に積み重なった層になっていて、「つながらない」ときは下の層から順に切り分けられる。

HTTP や MQTT の各ガイドに出てくる「ポート」「ブローカーのアドレス」「TLS」といった設定欄は、どれもこのページのどこかの段階に対応しています。設定の意味に迷ったら、その欄がどの困りごとを解決するためのものかを思い出してください。
