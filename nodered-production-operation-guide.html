Node-RED 本番運用ガイド

このガイドの前提
扱う内容は Raspberry Pi OS や Ubuntu などの Linux 上で Node-RED を常時稼働させる運用である。OS のコマンドと systemd を扱うため、共有クラウド環境ではそのまま実行できない。コマンドの読み方は基本コマンドガイド、ディレクトリの意味はディレクトリ構成ガイドを参照。

1. 学習環境と本番環境は何が違うのか

手元で動いたフローを現場の機器に載せた時点で、前提が 3 つ変わる。人が見ていない、電源が落ちる、そして誰も再起動しに行けない。

観点 学習環境 本番環境
起動 使うときに自分で立ち上げる 電源投入だけで復帰する必要がある
異常 画面を見て気づく 誰も見ていない。気づく仕組みが要る
停止 いつ止めてもよい 電源が突然落ちる前提で作る
フローの変更 壊れたら作り直す 戻せる状態を常に保つ
寿命 考えない SD カードの書き込み回数に上限がある

以下は、この差を埋めるために現場投入前に済ませておく作業である。

2. 自動起動（systemd）

サービスとして登録する

Raspberry Pi 向けの公式インストールスクリプトで導入した場合、nodered.service という systemd のサービス定義が一緒に入る。ただし自動起動は既定で有効になっていない。次のコマンドで有効化する。

sudo systemctl enable nodered.service

解除する場合は disable を使う。

sudo systemctl disable nodered.service

起動、停止、状態確認

操作Raspberry Pi 用スクリプトsystemd の標準コマンド
起動node-red-startsudo systemctl start nodered
停止node-red-stopsudo systemctl stop nodered
再起動node-red-restartsudo systemctl restart nodered
フローの再読み込みnode-red-reloadsudo systemctl reload nodered
状態確認（なし）sudo systemctl status nodered
ログ表示node-red-logsudo journalctl -f -u nodered

node-red-restart と node-red-reload も、公式インストールスクリプトが /usr/bin に配置する。前者は再起動、後者は Node-RED を止めずにフローだけを読み込み直す。

node-red-log は内部で sudo journalctl -f -n 25 -u nodered -o cat を実行している。直近 25 行を出したあと、新しい行が出るたびに追記表示する。行数を変えたい場合は node-red-log -n 100 のように指定する。

サービス定義で押さえておく設定

公式の nodered.service には、運用に効く設定が最初から入っている。中身を知っておくと、異常時の切り分けが早くなる。

設定意味
Restart=on-failure異常終了したら自動で起動し直す
RestartSec=20再起動までの待ち時間は 20 秒
KillSignal=SIGINT停止時は中断信号を送り、Node-RED に後始末をさせる
User= と Group=実行する利用者。別の利用者で動かすならここを変える
NODE_OPTIONS=--max_old_space_size=使用メモリの上限（メガバイト）。大量のデータを扱って落ちる場合に見直す箇所
EnvironmentFile=-（ユーザーディレクトリ内の environment）環境変数を外部ファイルから読む。ファイルが無くても起動する
SyslogIdentifier=Node-REDログ上の識別名
値はインストール時に書き換えられる
公式リポジトリにある nodered.service は雛形であり、インストールスクリプトが実環境に合わせて次の値を書き換える。手元のファイルを見るときは、雛形の値ではなく実際に入っている値を確認する。
  • メモリ上限：搭載メモリ量に応じて 256 / 512 / 1024 / 2048 のいずれかに置き換わる（雛形の初期値は 512）
  • User と Group：インストールを実行した利用者に置き換わる（雛形は pi）
  • WorkingDirectory と EnvironmentFile：その利用者のホームディレクトリを基準に置き換わる
認証情報をフローに書かない手段
EnvironmentFile の指す ~/.node-red/environment に MQTT_PASSWORD=... のように書いておくと、フロー側からは環境変数として参照できる。フロー JSON に平文の認証情報を残さずに済むため、フローを Git で管理する場合に有効である。
編集したら再読み込みが要る
サービス定義（通常は /lib/systemd/system/nodered.service）を書き換えたときは、systemd に読み直させてから再起動する。
sudo systemctl daemon-reload sudo systemctl restart nodered

3. ログの見方と量の管理

必要な範囲だけ見る

journalctl は範囲を絞れる。全部流すと目的の行を見失う。

# 直近100行だけ sudo journalctl -u nodered -n 100 # 今日のぶんだけ sudo journalctl -u nodered --since today # 特定の時刻以降 sudo journalctl -u nodered --since "2026-08-09 08:00" # 前回の起動時のログ（再起動の原因を追うとき） sudo journalctl -u nodered -b -1

ログを出しすぎない

Debug ノードをサイドバー出力のまま放置すると、そのぶんログとメモリを消費する。現場に置くフローでは、常時流れる Debug ノードを無効化するか、必要なものだけ残す。

ログ量はディスクと SD カードの消費に直結する
1 秒ごとに 1 行出すだけで 1 日 86,400 行になる。journald の保存量には上限を設定できる（/etc/systemd/journald.conf の SystemMaxUse など）。何も設定しないと、空き容量に応じてログが増え続ける。

4. バックアップと復元

Node-RED の設定と作ったものは、すべてユーザーディレクトリ（通常は ~/.node-red）に入っている。バックアップの対象はこのディレクトリの一部である。

対象内容バックアップ
flows.jsonフロー本体必須
flows_cred.json認証情報（暗号化されている）必須
settings.js設定ファイル必須
package.json追加したノードの一覧必須
package-lock.json追加ノードの版の固定推奨
lib/ライブラリに保存したフローや関数使っていれば必須
.config で始まる隠しファイル実行時の内部設定。認証情報の復号鍵を自動生成した場合はここに入る後述の理由により必須
node_modules/追加ノードの実体不要（package.json から入れ直せる）
ユーザーディレクトリの外にあるデータを忘れない
バックアップの対象はユーザーディレクトリだけではない。フローが書き出したファイルやデータベースを別の場所に置いている場合、そこも含めなければフローと認証情報は戻るのに、蓄積したデータだけが失われる。

たとえば SQLite ガイドのサンプルはデータベースを /home/pi/data/sensor.db に置いている。この場合、~/.node-red を固めただけでは測定値が 1 件も残らない。

対処は 2 通りある。
  • 置き場所をユーザーディレクトリの中にそろえる（例：~/.node-red/data/sensor.db）。バックアップ対象が 1 か所になるので管理が楽になる
  • バックアップ対象に明示的に加える。SQLite の場合、*.db に加えて同名の *.db-wal と *.db-shm が存在すればそれらも含める
稼働中のデータベースを単純コピーしない
書き込みの最中にファイルをコピーすると、中途半端な状態のまま固めてしまうことがある。確実な方法は次の 2 つである。
  • Node-RED を停止してからコピーする（node-red-stop のあとにバックアップ、終わったら node-red-start）
  • 稼働させたまま取るなら、SQLite に整合性を保ったまま複製させる。sqlite3 コマンドが使える環境では VACUUM INTO が簡単である
sqlite3 /home/pi/data/sensor.db "VACUUM INTO '/home/pi/backup/sensor-$(date +%Y%m%d).db'"
認証情報が復元できない事故
flows_cred.json は暗号化されている。復号の鍵を settings.js の credentialSecret で明示していない場合、Node-RED は鍵を自動生成し、.config で始まる隠しファイルに保存する。flows.json だけをコピーして移設すると、この鍵が付いてこないため認証情報だけが復元できず、MQTT やメールの接続がすべて落ちる。

対策は 2 つある。どちらかを必ず行う。
  • settings.js に credentialSecret: "任意の文字列" を明示する（推奨。移設先でも同じ文字列を設定すれば復号できる）
  • 隠しファイルを含めてユーザーディレクトリごとバックアップする
設定ファイルの詳細はsettings.js ガイドを参照。

手動バックアップ

ユーザーディレクトリだけを固める場合は次のようになる。

cd ~ tar czf nodered-backup-$(date +%Y%m%d).tar.gz --exclude='.node-red/node_modules' .node-red

データベースなどを別ディレクトリに置いているなら、その場所も一緒に含める。

cd ~ tar czf nodered-backup-$(date +%Y%m%d).tar.gz --exclude='.node-red/node_modules' .node-red data

作った書庫は、機器の外（NAS、社内ファイルサーバー、別の PC）に置く。同じ SD カードの中に置いても、そのカードが壊れれば一緒に失われる。

復元できるかを試すまでがバックアップ
取得したつもりで中身が空だった、鍵が入っていなかった、という事故は復元時にしか分からない。別の機器か検証用の環境へ一度戻し、フローが動き、接続先につながることを確認しておく。手順はセクション 5 にある。

Git で管理する

フローの変更履歴を残したい場合は Git を使う。Node-RED にはプロジェクト機能があり、ユーザーディレクトリを Git リポジトリとして扱える。考え方はGit 超入門、Windows での準備はGit for Windows インストールガイドにまとめてある。

Git に載せるときの注意
flows_cred.json は暗号化されているとはいえ認証情報である。公開リポジトリには置かない。credentialSecret を書いた settings.js も同様に扱う。

5. 別の機械への引っ越し

検証機で作ったフローを本番機へ移す、あるいは故障した機器を入れ替える手順である。順番を守ると失敗が減る。

  1. 移行先に同じか近い版の Node.js と Node-RED を入れる
  2. 移行先の Node-RED を止める（node-red-stop）
  3. バックアップした settings.js を置く。credentialSecret が移行元と同じであることを確認する
  4. package.json を置き、cd ~/.node-red のあと npm install で追加ノードを入れ直す
  5. ネイティブモジュールを使うノード（SQLite など）があれば、この時点でビルドが走る。時間がかかるので待つ
  6. flows.json と flows_cred.json を置く
  7. Node-RED を起動し、ログにエラーが出ていないか確認する（node-red-log）
  8. エディターを開き、パレットに欠けているノードがないか確認する
  9. 接続先（MQTT ブローカー、データベース、機器の IP アドレス）が移行先の環境と合っているか確認する
IP アドレスやパスは環境変数にしておく
接続先を各ノードに直接書くと、引っ越しのたびに全ノードを開いて直すことになる。~/.node-red/environment に書いて環境変数から参照するようにしておけば、書き換えるのは 1 ファイルで済む。

6. SD カードの寿命と書き込み削減

Raspberry Pi で最も多い故障は SD カードの寿命である。フラッシュメモリには書き込み回数の上限があり、同じ場所に書き続けると先に寿命が来る。ログとデータベースが主な消費源になる。

書き込みを減らす

対象やること
Debug ノード常時流れるものを無効化する
ログjournald の保存量に上限を設ける
データベース記録周期を見直す。1 秒ごとが本当に要るのかを確認する
context 変数ファイル保存を使っている場合、保存間隔を延ばす
集計生データを貯め続けず、一定期間で集計して古い行を消す
周期を決める考え方
現場で本当に必要な粒度から逆算する。1 分平均で判断できる設備を 1 秒ごとに記録しても、判断は変わらないまま書き込み量だけが 60 倍になる。削除と集計の書き方はSQLite ガイドのセクション 7 にある。

媒体を変える

選択肢特徴
一般的な SD カード安いが寿命が読めない。検証用まで
高耐久 SD カード（産業用）書き込み耐性が高い製品がある。常時記録する用途ではこちらを選ぶ
USB 接続の SSD耐性と速度で有利。Raspberry Pi 4 以降は USB からの起動に対応している

7. 時刻の同期

時刻がずれた機器の記録は、あとから突き合わせられない。複数台のデータを比べるなら、時刻同期は記録そのものと同じくらい重要になる。

timedatectl status

System clock synchronized: yes と NTP service: active になっていれば同期している。工場内でインターネットに出られない場合は、社内の NTP サーバーを参照するよう設定する。

起動直後の記録がずれる問題
電源投入直後は時刻同期が終わっておらず、その間に記録した行だけ時刻がおかしくなることがある。公式の nodered.service には、時刻同期の完了を待ってから起動する設定がコメントアウトされた状態で用意されている。記録の正確さが重要な用途では、この行を有効にすることを検討する。
#ExecStartPre=/bin/bash -c '/bin/journalctl -b -u systemd-timesyncd | /bin/grep -q "systemd-timesyncd.* Synchronized to time server"'
先頭の # を外し、sudo systemctl daemon-reload を実行する。同期できない環境では起動しなくなるため、時刻源が確実にある環境でのみ使う。

8. 電源断への備え

工場では、装置の主電源とともにエッジ機器の電源も落ちる運用が珍しくない。Linux は書き込み途中に電源が切れるとファイルシステムが壊れることがあり、起動しなくなる形で表面化する。

対策内容
正しく停止する運用sudo shutdown -h now で停止してから電源を切る手順を現場に周知する
無停電電源（UPS）停電を検知して安全に停止する時間を稼ぐ。数分持てば足りる
書き込みを減らす書き込み中の確率が下がるため、破損の確率も下がる（セクション 6）
復旧手段を用意する設定済みの SD カードの複製を予備として保管しておく
再起動後に自動で戻るか確認する
現場に置く前に、電源を抜いて入れ直す試験を一度行う。自動起動が有効なら、そのままフローが動き出すはずである。ここで戻らなければ、現場では誰も戻せない。

9. 死活監視と自動復旧

systemd の Restart=on-failure は、Node-RED のプロセスが落ちた場合に復帰させる。しかし現場で多いのは「プロセスは生きているが、データが来ていない」という状態である。これは systemd では検知できない。フロー側で見張る必要がある。

ディスクの空き容量を監視する

flow context は再起動で消える
サンプルは flow.set を使っているため、Node-RED を再起動すると最終受信時刻が消える。再起動直後は「一度も受信していない」と判定され、実データが来るまで警告が出る。この扱いが困る場合は、判定の開始を起動から数分遅らせるか、記録先をデータベースにする。
通知は鳴らしすぎない
60 秒ごとの点検で異常が続けば、通知も 60 秒ごとに飛ぶ。Filter (RBE) ノードで状態が変化したときだけ通す、あるいは Trigger ノードで再通知の間隔を空けるといった調整を入れる。鳴り続ける通知は、やがて誰も見なくなる。

10. セキュリティの最低線

Node-RED のエディターは、既定では誰でも開ける。フローを書き換えられるということは、その機器で任意の処理を実行できるということでもある。現場に置く前に、少なくとも次を確認する。

項目内容
エディターの認証settings.js の adminAuth で利用者名とパスワードを設定する
作った Web 画面の認証httpNodeAuth で HTTP ノードやダッシュボードに認証をかける
待ち受け範囲外部に見せる必要がなければ uiHost で待ち受けを限定する
通信の暗号化社内 LAN の外を通るなら HTTPS を有効にする
インターネットへの直接公開行わない。必要なら VPN 越しにする
認証情報の置き場所フローに直接書かず、環境変数か認証情報欄を使う

各設定の書き方はsettings.js ガイドにまとめてある。

工場のネットワークに置く場合
制御系のネットワーク（設備が動いている側）と情報系のネットワークを直結しない。エッジ機器を両方につなぐ構成にするなら、通す通信を必要最小限に絞り、情報システム部門と事前に合意しておく。ネットワークの基礎は通信の基礎を参照。

11. 更新の運用

Raspberry Pi や Debian 系（Debian、Ubuntu、Raspberry Pi OS）では、公式の更新スクリプトで Node.js と Node-RED をまとめて更新できる。次は公式リポジトリ node-red/linux-installers の README が案内している形である。

bash <(curl -sL https://github.com/node-red/linux-installers/releases/latest/download/install-update-nodered-deb)

このコマンドは初回インストールにも更新にも使える。RPM 系（Fedora、RHEL など）は別のスクリプトが用意されているため、README で確認する。

順番やること
1バックアップを取る（セクション 4）
2更新を実行する
3ネイティブモジュールを使うノードを再ビルドする（cd ~/.node-red のあと npm rebuild）
4起動してログを確認する
5主要なフローが動くことを確認する
稼働中の設備で更新しない
更新には再起動が伴い、追加ノードの再ビルドで時間もかかる。設備を止めてよい時間帯に行う。可能なら、同じ構成の検証機で先に試す。

12. 本番投入前チェックリスト

起動と復帰

  • □ sudo systemctl enable nodered.service を実行した
  • □ 電源を抜き差しして、フローが自動で動き出すことを確認した
  • □ systemctl status nodered が正常を示す

データと復元

  • □ settings.js に credentialSecret を明示した
  • □ ユーザーディレクトリの外にあるデータ（データベース、出力ファイル）もバックアップ対象に入れた
  • □ バックアップを取得し、機器の外に保存した
  • □ バックアップから復元する手順を一度試した

寿命と容量

  • □ 常時流れる Debug ノードを無効化した
  • □ データの記録周期と保持期間を決めた
  • □ 古いデータを削除するフローを組んだ
  • □ ディスク使用率の監視を入れた

正確さと監視

  • □ timedatectl status で時刻同期を確認した
  • □ 無通信を検知する仕組みを入れた
  • □ 異常の通知先と、通知が鳴りすぎない調整を決めた

セキュリティ

  • □ エディターに認証をかけた
  • □ インターネットへ直接公開していない
  • □ 認証情報をフロー内に平文で書いていない

13. まとめ

論点結論
自動起動インストールしただけでは有効にならない。systemctl enable が必要
バックアップflows.json だけでは足りない。credentialSecret を明示し、ユーザーディレクトリの外に置いたデータベースも対象に含める
SD カード書き込み量が寿命を決める。記録周期と保持期間を先に決める
時刻ずれた記録は突き合わせられない。同期を確認する
監視プロセスの死活だけでは足りない。データが来ているかを見る
セキュリティエディターは既定で誰でも開ける。認証をかける
