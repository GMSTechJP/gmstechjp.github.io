このガイドで扱うノードについて

FTP と SFTP のノードは Node-RED の標準ノードに含まれていない追加パッケージである。使うのは次の2つ。

パッケージ 版（執筆時点） 提供するノード ライセンス
node-red-contrib-ftp v0.0.8（2022-06-20 公開） ftp in（FTP クライアント）
sftp in（SFTP クライアント）		 Apache
node-red-contrib-ftp-server v1.0.4（2022-03-19 公開） ftp server（FTP サーバー） MIT
  • GitHub: joeartsea/node-red-contrib-ftp（作者 Atsushi Kojo）
  • GitHub: biddster/node-red-contrib-ftp-server（作者 @biddster）

node-red-contrib-ftp は日本語の表示ファイルを同梱している。そのため設定項目は原則として日本語表示をそのまま示し、訳語が用意されていない項目だけ「English Label（日本語訳）」の形式で書く。node-red-contrib-ftp-server は日本語表示を持たないため、すべて英語ラベルに訳を添える。

免責： 本ガイドは上記バージョンでの動作を前提に書いている。どちらも 2022 年以降の更新がなく、Node-RED 本体や Node.js の更新で挙動が変わる可能性がある。導入前に最新の状況を確認してほしい。

SFTP サーバーのノードは存在しない：

Node-RED を SFTP のサーバーにするノードは、2026-08-13 時点で npm 上に見つからない。かつて候補だったパッケージは公開が取り下げられている。SFTP は SSH の機能の一つなので、サーバー側は OS の SSH デーモンで用意する。手順はセクション 8 で扱う。

1. 概要：ファイルを受け渡す4つの立ち位置

現場でファイル転送が必要になる場面は、たいてい次のどちらかである。計測器が日次の CSV を吐くので回収したい。ネットワークカメラが動体検知の画像を送りつけてくるので受け止めたい。前者は Node-RED が取りに行く側、後者は Node-RED が受ける側になる。

取りに行く側をクライアント、受ける側をサーバーと呼ぶ。これに暗号化の有無を掛け合わせると、立ち位置は4つになる。

立ち位置 何をするか 使うもの
FTP クライアント 相手の FTP サーバーへ接続し、ファイルを取得したり送ったりする ftp in ノード
SFTP クライアント 同じことを SSH の上で行う sftp in ノード
FTP サーバー Node-RED 自身が待ち受け、機器から送られたファイルを受け取る ftp server ノード
SFTP サーバー 同じことを暗号化して行う OS の OpenSSH（Node-RED のノードは無い）

どの立ち位置になるかは、相手の機器が決めることが多い。カメラや計測器の設定画面に「FTP サーバーのアドレス」を入れる欄があれば、機器がクライアントで Node-RED がサーバーである。逆に相手が置き場所を用意しているだけなら、Node-RED が取りに行く。

ファイルの中身を扱う手前の話：

転送したファイルを Node-RED の中で読み書きするのは、標準の file ノードの役目である。フォルダにファイルが増えたことを検知するのは watch ノードが担う。このガイドは「マシンの間でファイルを動かす」部分だけを扱う。

動作を図で見る

ftp in ノードは、msg を受け取ったときに、設定した操作（list、get、put など）をサーバーに対して行い、結果を msg.payload に入れて送り出します。

2. FTP と SFTP と FTPS の違い

名前が似ている3つを並べて整理する。

FTP FTPS SFTP
通信の暗号化 なし TLS SSH
既定のポート 21（制御用）とデータ用の別ポート 21 または 990 22
認証 ID とパスワード（平文で流れる） ID とパスワード ID とパスワード、または公開鍵
土台になる仕組み FTP という独立したプロトコル FTP に TLS をかぶせたもの SSH の機能の一つ
このガイドで扱う手段 ftp in と ftp server 扱わない sftp in と OS の OpenSSH

誤解されやすいのは SFTP の位置づけである。名前は FTP に S が付いた形だが、FTP を暗号化したものではない。SSH という別の仕組みの中に用意されたファイル転送機能であり、プロトコルもポートも FTP とは無関係である。FTP を暗号化したものは FTPS のほうで、こちらは名前が紛らわしいわりに現場で見かける機会が少ない。

平文 FTP の危険：

FTP はユーザー名とパスワードを暗号化せずに送る。同じネットワークを流れるパケットを見られる立場の相手には、そのまま読み取られる。ファイルの中身も同様である。

使ってよいのは、外部から到達できない LAN の中と検証環境に限る。インターネットを越えてファイルを運ぶ用途では SFTP か FTPS を選ぶ。古い機器が FTP しか話せない場合は、機器と Node-RED を同じ閉じたネットワークに置き、そこから先を SFTP で中継する構成にする。

パッシブモードとアクティブモード

FTP には、他のプロトコルにあまり無い癖がある。命令のやり取りとファイルの中身を、別々の接続で運ぶ。この2本目をどちらから張るかで2つのモードに分かれる。

パッシブ（PASV）モード クライアント ──接続──> サーバー （制御用、ポート 21） クライアント ──接続──> サーバー （データ用、サーバーが指定したポート） アクティブモード クライアント ──接続──> サーバー （制御用、ポート 21） クライアント <──接続── サーバー （データ用、クライアントが指定したポート）

アクティブモードはサーバーからクライアントへ接続を張るため、クライアント側にファイアウォールがあると弾かれる。そのため現在はパッシブモードが既定になっている。

サーバーを立てる側から見ると、パッシブモードでは制御用のポートに加えてデータ用のポートも開けておく必要がある。どのポートを使うかはサーバーが接続のたびに選ぶため、既定のままだと範囲が定まらずファイアウォールの設定を書けない。ftp server ノードの「Passive Mode Port Range」は、この範囲を固定するための欄である。

3. インストール方法

Node-RED エディターの「パレットの管理」から導入する。2つのパッケージを別々に入れる。

  1. エディター右上のメニュー（三本線）から「パレットの管理」を開く
  2. 「ノードを追加」タブを選ぶ
  3. 検索欄に node-red-contrib-ftp と入力し、「ノードを追加」ボタンを押す
  4. 続けて node-red-contrib-ftp-server を検索し、同じように追加する
  5. インストール後、パレットの「ストレージ」に ftp と sftp、「入力」に ftp server が現れる

コマンドラインから入れる場合は、Node-RED のユーザーディレクトリ（多くは ~/.node-red、Windows では %userprofile%\.node-red）で次を実行する。

npm install node-red-contrib-ftp node-red-contrib-ftp-server
SFTP も同じパッケージに入っている：

node-red-contrib-ftp というパッケージ名からは FTP だけに見えるが、中には sftp ノードも同梱されている。SFTP を使うために別のパッケージを探す必要はない。

メンテナンスの状況：

どちらのパッケージも 2022 年以降の更新がない。node-red-contrib-ftp が内部で使う ftp パッケージはさらに古い。動いているうちは問題ないが、Node.js や Node-RED を新しくしたときに壊れる可能性はある。

SFTP クライアントだけが必要で、更新の新しさを重視するなら node-red-contrib-sftp-ssh2（v0.1.4、2024-07-20）という別の選択肢もある。ただし設定項目の作りが異なるため、本ガイドの説明はそのまま当てはまらない。

4. ノード構成

5種類のノードが登場する。うち2つは接続先を保持するコンフィグノードで、フロー上には現れない。

ftp（コンフィグ）

接続先の FTP サーバーの住所と認証情報を持つ。複数の ftp in ノードから共有できる。

ftp in

FTP クライアント

メッセージを受けて一度だけ接続し、指定した操作を行って結果を出す。

sftp（コンフィグ）

接続先の SFTP サーバーの情報を持つ。パスワードのほか秘密鍵も指定できる。

sftp in

SFTP クライアント

ftp in と同じ操作を SSH の上で行う。一覧の絞り込みができる点が異なる。

ftp server

FTP サーバー

入力を持たず、指定ポートで待ち受ける。ファイルが届くと出力へ流す。

inject → ftp in（取りに行く） → debug
ftp server（待ち受ける） → file → debug

ftp in と sftp in は入力を持つ。inject や他のノードからメッセージが届いたときに、はじめて接続して転送を行う。常時つながっているわけではない。

6. 操作ごとの挙動

6つの操作それぞれについて、することと出力される msg.payload を整理する。

Operation すること 出力される payload
list ディレクトリの中身を一覧する ファイル情報の配列。名前、種別、サイズ、更新日時などを含む（各項目の意味は 10 章の「一覧の出力の読み方」）
get サーバーのファイルをローカルへ保存する Get operation successful. に続けてローカルのパスを並べた文字列
put ローカルのファイルをサーバーへ送る FTP は Put operation successful. という文字列。SFTP は転送結果の文字列
append サーバー側の既存ファイルの末尾へ書き足す Append operation successful. という文字列
delete サーバー側のファイルを削除する 実質的に空
mkdir サーバー側にディレクトリを作る。途中の階層も作られる FTP は mkdir operation successful. という文字列
get はファイルの中身を返さない：

最も間違えやすい点である。get は取得したファイルをローカルへ書き出すだけで、msg.payload に入るのは成功を伝える文字列にすぎない。中身を Node-RED の中で使いたいなら、get の後ろに file in ノードを繋いで、保存されたファイルを読み直す。

sftp in（get） → file in（保存先を読む） → debug
ftp in の get は、書き終わる前に次のノードへ進む：

上の図が sftp in なのには理由がある。sftp in の get は、ファイルを書き終えてから msg を送り出す。ftp in の get は、書き出しを始めた時点で msg を送り出す。そのため、ftp in のすぐ後ろに file in ノードを置くと、書き終わる前のファイルを読むことがある。

10 章の試験用サーバーにある 80,000 バイトの画像（/pub/example/WinFormClient.png）を ftp in で取得し、すぐ後ろの file in で読むと、読めたのは 0 バイトだった。379 バイトの /readme.txt は全部読めたので、小さいファイルで試すと気づけない。sftp in では、どちらも全部読めた（node-red-contrib-ftp 0.0.8、2026-11-26 確認）。

この動作は、ノードの説明には書かれていない。同じパッケージの sftp in とも食い違うので、仕様ではなく、ノードの不具合とみられる。配布元のリポジトリに、この件の報告は無い（2026-11-26 確認）。

ftp in で取得した中身を読むときは、間に delay ノードを挟んで待つ（上の画像は、3 秒待つと全部読めた）。必要な時間はファイルの大きさと回線の速さで変わるので、余裕を持たせる。サーバーが SFTP にも対応しているなら、sftp in を使うほうが確実である。

操作のあと、メッセージには実際に使われたパスが書き戻される。msg.filename と msg.localFilename は常にセットされ、SFTP ではこれに加えて msg.path と msg.pattern も付く。後段でログを残すときに使える。

失敗したときの振る舞い

接続できない、ファイルが見つからない、権限がない、といった失敗が起きると、ノードは出力へ何も流さずエラーを発生させる。ノードのステータスは赤くなり、エラーメッセージが表示される。

このエラーは catch ノードで捕まえられる。転送は相手のマシンやネットワークの状態に左右されるため、失敗したことに気づける経路を用意しておく。

ftp in ✗
catch → debug（通知）

7. FTP サーバーとして受け取る

ftp server ノードは入力を持たず、デプロイした時点でポートを開いて待ち受ける。出力は2つある。

出力 ラベル いつ流れるか メッセージの中身
1 upload file ファイルが送られてきたとき msg.topic にファイル名、msg.payload にファイルの中身（Buffer）
2 authenticate Username 欄が空のとき、接続のたび msg.payload に {username, password}、msg.authenticate に判定を返す関数
受け取ったファイルはディスクに残らない：

このノードはメモリ上の仮想ファイルシステムにファイルを書き、5秒後に消す。Raspberry Pi のような機器でメモリを使い切らないための作りである。

そのため、出力1をどこにも繋がなければファイルは失われる。保存したいなら file ノードへ繋いで自分で書き出す。「FTP サーバーを立てたのにファイルがどこにも見当たらない」という詰まり方は、ほぼこれが原因である。

動的認証モード

Username 欄を空にすると、ユーザー名とパスワードの判定をフロー側で行う。接続のたびに出力2へメッセージが流れるので、function ノードで msg.authenticate(true) または msg.authenticate(false) を呼んで返事をする。

// 出力2 に繋いだ function ノード // パッケージの公式ヘルプに載っている書き方に沿っている msg.authenticate( msg.payload.username === 'camera' && msg.payload.password === 'change-me' ); msg.payload = undefined; return msg;

この仕組みが役に立つのは、機器ごとに違うユーザー名を使い分けたいときや、認証情報を環境変数から読みたいときである。判定を返さないと接続は成立しないため、出力2を使う設定にした場合は必ず繋いでおく。

TLS には対応していない：

このノードのヘルプには、TLS 対応が今後の課題として挙がったまま残っている。つまり通信は平文である。カメラなどの機器から画像を受ける用途では、機器と Node-RED を同じ閉じたネットワークに置く。

8. SFTP サーバーは OS 側で立てる

Node-RED を SFTP サーバーにするノードは、2026-08-13 時点で npm 上に存在しない。もっとも、SFTP は SSH の機能の一つなので、SSH サーバーが動いていれば、それがそのまま SFTP サーバーになる。Raspberry Pi OS や Ubuntu なら OpenSSH がその役目を担う。追加のパッケージは要らない。

手順

Raspberry Pi OS を例に、受け取り専用のユーザーを作るところまでを示す。

# 1. SSH を有効にする（無効な場合） sudo systemctl enable --now ssh # 2. 受け取り専用のユーザーを作る（ログインシェルは与えない） sudo useradd -m -s /usr/sbin/nologin sensor-upload sudo passwd sensor-upload # 3. 受信フォルダを用意する sudo mkdir -p /var/spool/sensor-upload sudo chown sensor-upload:sensor-upload /var/spool/sensor-upload # 4. 別のマシンから接続を確認する sftp sensor-upload@192.168.1.20

ここまでで、機器や別のマシンから SFTP でファイルを置けるようになる。Node-RED 側は転送そのものに関わらず、置かれたファイルを見つけて処理する役に回る。

watch（フォルダを監視） → file in（読む） → function（処理）

watch ノードに /var/spool/sensor-upload を指定すると、ファイルが増えたときにメッセージが流れる。

役割を分けておく利点：

転送を OS が担うため、Node-RED を再起動してもファイルの受け取りは止まらない。フローの編集中に届いたファイルも、あとから watch ノードや file in ノードで拾える。Node-RED 内で待ち受ける構成に比べて、止められる範囲が狭い。

書き込み途中のファイルを読まないようにする：

watch ノードはファイルが作られた時点でも反応するため、転送の途中で読みに行くと中身が欠けたファイルを掴むことがある。送信側で「一時的な名前で送り、完了後に本来の名前へ変える」運用にするか、受信側で delay ノードを挟んで少し待つ。

受け取り専用ユーザーを自分のフォルダの外へ出したくない場合は、OpenSSH の設定ファイル /etc/ssh/sshd_config で ChrootDirectory を使って閉じ込められる。ただし閉じ込め先のフォルダは所有者が root で、かつ他者に書き込み権限がないことが求められるなど条件が細かい。SSH と Linux の権限まわりは Linux ディレクトリガイドと本番運用ガイドも参照してほしい。

9. セキュリティと運用の注意

認証情報の置き場所

コンフィグノードのパスワード欄に入れた値は、フローをエクスポートしても書き出されない。Node-RED はこれを flows_cred.json という別のファイルへ暗号化して保存する。

ただし暗号化の鍵は、設定していなければ Node-RED が自動生成したものになる。フローファイルと資格情報ファイルを一緒にバックアップして別のマシンへ置くと、鍵が違うため復号できない。settings.js の credentialSecret を自分で決めておくと、移行のときに困らない。詳しくは settings ガイドを参照してほしい。

ポートを開ける範囲

FTP サーバーを立てる場合、開けるポートは制御用とデータ用の両方になる。「Passive Mode Port Range」を 7022-7032 のように決めておくと、ファイアウォールの設定を書ける。

# ufw を使っている場合の例（LAN からのみ許可する） sudo ufw allow from 192.168.1.0/24 to any port 7021 proto tcp sudo ufw allow from 192.168.1.0/24 to any port 7022:7032 proto tcp

ここで from を付けずに開けると、ルーターの設定によっては外部から届くようになる。平文の FTP を外部へ晒すことになるため、範囲は絞っておく。

手段の選び方

状況 選ぶもの
同じ LAN 内の古い機器からファイルを受ける ftp server ノード。ポート範囲を絞り、LAN からのみ許可する
別拠点やクラウドとファイルをやり取りする SFTP。鍵認証にする
相手から Node-RED へ送りつけてもらう（暗号化あり） OS の OpenSSH と watch ノード
相手が FTPS しか話せない exec ノードから curl や lftp を呼ぶ

10. サンプルフロー

このパッケージには公式のサンプルフローが同梱されていないため、ここに載せるのは本サイトで作成したものである。

接続先のサーバー

FTP・SFTP のクライアントを試すには、接続先のサーバーが先に動いている必要がある。ftp ノードと sftp ノードは接続しに行く側で、相手がいないと失敗する（FTP では Timeout while connecting to server と出る）。失敗が分かるまでには、時間がかかることがある。FTP は接続タイムアウト（サンプルでは 10 秒）、SFTP は準備完了タイムアウト（サンプルでは 20 秒）まで待ち、SFTP はリトライの分だけさらに長くなる。その間は、ノードにも debug にも何も表示されない。

クライアントのサンプルフローは、接続先を公開の試験用サーバー test.rebex.net にしてある。Rebex 社が自社のライブラリの試験用に公開しているサーバーで、次の値で誰でも接続できる。

項目 値
ホスト test.rebex.net
ポート FTP は 21、SFTP は 22
ユーザー名 / パスワード demo / password（公開されている値）
置いてあるもの /readme.txt と /pub フォルダ

このサーバーは読み取り専用である。一覧（list）と取得（get）は成功するが、送信（put）などの書き込みは失敗する。サンプルフローでは、送信の失敗を「4. 転送の失敗を捕まえる」で受け取る例として使う。

他社が好意で公開しているサーバーなので、接続を確かめる程度の用途にとどめる。会社のネットワークでは、外向きの 21 番・22 番が塞がれていて接続できないことがある。自分のサーバーにつなぐときは、コンフィグノードのホスト名・ユーザー名・パスワードを書き換える。11 章の演習2も、この試験用サーバーにつなぐ。演習1はフォルダを作るので、読み取り専用のこのサーバーでは動かせない。代わりに、このあとの「サーバーとして受け取る」のサンプルフローを接続先にする。

📌 コンフィグノードにある "credentials" について

パスワードは、ふつうはフローをエクスポートしても書き出されない。本ガイドのフローでは、読み込んですぐ試せるよう、FTP・SFTP のコンフィグノードに試験用サーバーの公開パスワードを "credentials" として書いてある。自分のサーバーのパスワードを、このようにフローへ書いて人に渡してはいけない。

パスワードの要らない FTP サーバーにつなぐフローを人に渡すときも、FTP のコンフィグノードの "credentials" は消さず、空のパスワード（"credentials": {"password": ""}）を残す。これが無いと、パスワードを一度も保存していないコンフィグノードがデプロイ時に作れず、Cannot read properties of undefined (reading 'password') というエラーになる。node-red-contrib-ftp（v0.0.8）が、資格情報の無いコンフィグノードを想定していないためである。パスワードが空のときは anonymous@ が使われる。

一度読み込んでパスワードを書き換えたあとに、同じフローを「置き換え」で読み込み直すと、パスワードはフローに書いてある値に戻る。入れ直すか、「コピーを読み込み」を選ぶ。

ほかから手に入れたフロー（自分でエクスポートして別の Node-RED へ読み込んだものを含む）で同じエラーが出たら、FTP のコンフィグノードを開いて「更新」を押し、デプロイし直す。パスワード欄は空のままでもよい。編集画面で一度保存すれば、資格情報が保存される。

フローの読み解き

フローは4つの部分に分かれている。コメントノードの番号（1〜4）が、下の表の番号に当たる。1 と 2 の ftp in ノードは同じ FTP のコンフィグノード（test.rebex.net の 21 番）を使い、3 の sftp in ノードは SFTP のコンフィグノード（同じサーバーの 22 番）を使う。

部分 ノードの並び 設定と、その理由
1. 一覧 「一覧を要求」（inject）→「FTP list」（ftp in）→「一覧」（debug） Operation は list。「ファイル名」欄の / は、一覧するディレクトリ（サーバーの最上位）である。FTP の list は、対象のディレクトリをこの欄に書く。結果は msg.payload に配列で入る
2. 送信 「送信を要求」（inject）→「FTP put」（ftp in）→「送信の結果」（debug） Operation は put。「ローカルファイル名」の /tmp/reading.csv（Node-RED のマシンにあるファイル）を、「ファイル名」の /upload/reading.csv（サーバー側の保存先）へ送る。このサーバーは読み取り専用なので、送信は断られる。「送信の結果」には何も出ず、ノードの下に赤いステータスが出て、4 の経路へ進む
3. 取得 「取得を要求」（inject）→「SFTP get」（sftp in）→「保存先を読む」（file in）→「ファイルの中身」（debug） Operation は get。「ファイル名」の /readme.txt（サーバー側）を、「ローカルファイル名」の /tmp/readme.txt（Node-RED のマシン）へ保存する。get は中身を msg.payload に入れないので、後ろの file in ノードで、保存したファイルを読み直している。取得だけ sftp in を使うのは、sftp in の get がファイルを書き終えてから次へ進むためである。ftp in でも取得はできるが、書き終わる前に次へ進むので、すぐ後ろで読むと中身が欠けることがある（6 章）
4. 失敗を捕まえる 「転送エラー」（catch）→「エラー内容」（debug） ボタンは無い。1〜3 のどれかが失敗したときに動く。catch ノードは、対象を3つの転送ノードだけに絞ってある。debug は msg.error を表示するので、エラーの文と、失敗したノードの名前（source.name）が分かる

inject ノードは、どれも動かすきっかけとして置いてあるだけで、送っている値（時刻）は使われない。ファイル名は、すべて各ノードの設定欄に書いてある。フローの中でファイル名を決めたいときは、設定欄を空にして msg.filename などで渡す（演習1）。

フローの読み解き

このフローには inject ノードが無い。ftp server ノード「受信（ポート7021）」が待ち受けていて、外から接続が来ると動く。ftp server ノードの2つの出力から、2本の経路に分かれている。接続が来ると、先に出力2の経路（認証）が動き、許可されたあとでファイルが届くと、出力1の経路（保存）が動く。

経路 ノードの並び していることと、その理由
出力2：認証 「受信（ポート7021）」の出力2 →「接続を許可するか判定する」（function）→「認証の記録」（debug） ftp server ノードの Username 欄を空にしてあるので、接続のたびに、相手が名乗ったユーザー名とパスワードが出力2から出る（7 章の動的認証モード）。function ノードは、ユーザー名が camera、パスワードが change-me のときだけ msg.authenticate(true) を呼んで許可する。そのあと msg.payload をユーザー名と判定に置き換えているので、debug にパスワードは出ない
出力1：保存 「受信（ポート7021）」の出力1 →「保存先を組み立てる」（function）→「受信フォルダへ書き出す」（file）→「保存したパス」（debug） 出力1には、msg.topic にファイル名、msg.payload に中身（Buffer）が入って出る。function ノードは、ファイル名の末尾（最後の / より後ろ）だけを取り出し、/tmp/ftp-received/ の下のパスを msg.filename に入れる。file ノードは、保存先を msg.filename から受け取り、フォルダが無ければ作って、同じ名前のファイルは上書きする。ftp server ノードは受け取ったファイルを5秒後に消すので、この経路が無いとファイルは残らない

ftp server ノードの Port は 7021、Passive Mode Port Range は 7022-7032 にしてある。FTP は、ログイン用の接続とは別に、データを運ぶ接続を張る（2 章のパッシブモード）。その接続に使うポートの範囲が後者である。別のマシンから送るときは、両方をファイアウォールで開ける。

手元で試すには：

相手の機器がなくても、同じマシンから curl コマンドでファイルを送れば、動作を確かめられる。上のサーバーフローをデプロイしてから、ターミナル（Windows ではコマンドプロンプト）を開いて、次の 1〜4 を順に進める。

  1. 送るファイルを用意する。中身は何でもよい。次のコマンドは、hello と1行だけ書いた reading.csv というファイルを、ホームフォルダに作る。

    macOS と Linux：

    echo hello > ~/reading.csv

    Windows：

    echo hello > "%USERPROFILE%\reading.csv"

    何も表示されずに入力待ちに戻れば、作れている。すでにある自分のファイルを送るときは、この手順を飛ばしてよい。

    ~ と %USERPROFILE% は、どちらも自分のホームフォルダを表す。%USERPROFILE% は Windows の環境変数（OS が値を覚えている、名前の付いた設定）で、ホームフォルダのパス（多くは C:\Users\ユーザー名）が入っている。コマンドプロンプトは、% で囲んだ名前を、実行する前にその値へ置き換える。" で囲んでいるのは、ユーザー名に空白があっても、パスが途中で切れないようにするためである。置き換わるパスは、次のコマンドで確かめられる（確かめなくても、先へ進める）。

    echo %USERPROFILE%

    C:\Users\taro のように、自分のホームフォルダのパスが表示される。%USERPROFILE% という文字がそのまま表示されたときは、PowerShell で実行している。下の「PowerShell で実行する場合」の書き方を使う。

  2. ファイルを置いたフォルダへ移る。3 のコマンドは、今いるフォルダからファイルを探す。1行目でホームフォルダへ移り、2行目でファイルがあることを確かめる。

    macOS と Linux：

    cd ~ ls reading.csv

    Windows：

    cd /d "%USERPROFILE%" dir /b reading.csv

    reading.csv と表示されれば、ファイルはこのフォルダにある。ファイルが無いときは、macOS と Linux では No such file or directory、Windows では「ファイルが見つかりません」と表示される。そのときは 1 に戻る。自分のファイルを送るときは、~ や %USERPROFILE% の代わりに、そのファイルを保存したフォルダを書く。

  3. ファイルを送る。-T の後ろに、送るファイルの名前を書く。
    curl -T reading.csv ftp://localhost:7021/ --user camera:change-me

    -T reading.csv が送るファイルである。自分のファイルを送るときは、reading.csv をそのファイルの名前に書き換える。ftp://localhost:7021/ は送り先で、このマシンのポート 7021、つまり上のサーバーフローを指す。--user camera:change-me は、ユーザー名とパスワードを : でつないだものである。

    macOS には ftp コマンドが入っていないため、curl を使う。Windows 10（バージョン 1803 以降）と Windows 11 にも curl が入っているので、コマンドプロンプトでは同じ行がそのまま動く。

  4. 届いたことを確かめる。まず、画面の表示を2か所で見る。
    • ターミナル：% Total で始まる進み具合の表が出る。curl: で始まる行は出ずに、入力待ちに戻る
    • Node-RED の debug サイドバー：「認証の記録」にユーザー名 camera と判定「許可」が出る。続けて、「保存したパス」に /tmp/ftp-received/reading.csv が出る

    次に、保存されたファイルの中身を表示する。

    macOS と Linux：

    cat /tmp/ftp-received/reading.csv

    Windows：

    type C:\tmp\ftp-received\reading.csv

    1 で書いた hello が表示されれば、送信から保存まで動いている。自分のファイルを送ったときは、コマンドの reading.csv をその名前に書き換える。表示されるのは、そのファイルの中身である。

    ファイルが見つからないというエラーが出たときは、debug サイドバーに「保存したパス」が出ているかを確かめる。出ていなければ、3 に戻って、ターミナルに curl: で始まる行が出ていないかを見る。出ているのに見つからないときは、探している場所が違う。Windows では、Node-RED を起動したドライブを確かめ、C 以外なら C: をそのドライブに書き換える。Node-RED を Docker や別のマシンで動かしているときは、ファイルはその中に保存されている。

うまくいかないとき：3 のあとに curl: で始まる行が出たら、送信は失敗している。行の中身から、どこを確かめればよいかが分かる。

  • curl: Can't open 'reading.csv'：送るファイルを開けない。多くは、今いるフォルダにその名前のファイルが無い。2 に戻って、フォルダとファイル名を確かめる
  • curl: (7) Failed to connect to localhost port 7021：ポート 7021 に接続できない。まず、サーバーフローを読み込んで、デプロイしたかを確かめる
  • curl: (67) Access denied: 530：ユーザー名かパスワードが違う。camera:change-me のつづりを確かめる。このとき、debug の「認証の記録」には判定「拒否」が出る

PowerShell で実行する場合：1〜3 を次のように書く。

echo hello > "$HOME\reading.csv" cd $HOME dir reading.csv curl.exe -T reading.csv ftp://localhost:7021/ --user camera:change-me

PowerShell は %USERPROFILE% という書き方を読み替えないので、ホームフォルダは $HOME と書く。3行目は、ファイルがあれば reading.csv の行を含む一覧を表示し、無ければ赤いエラーを表示する。curl は curl.exe と書く。Windows PowerShell では、curl という名前が PowerShell 独自の別のコマンド（Invoke-WebRequest）に割り当てられていて、-T を付けるとエラーになる。curl.exe と拡張子まで書くと、本来の curl が呼び出される。4 の中身の表示（type）も、同じ PowerShell で行う。Windows PowerShell が > で作るファイルは文字コードが UTF-16 で、PowerShell の type はそれを読める。

Windows での保存先：/tmp/ftp-received/ は、Node-RED を起動したドライブの直下の \tmp\ftp-received\（多くは C:\tmp\ftp-received\）になる。フォルダは、無ければ file ノードが作る。debug に出るパスは /tmp/ftp-received/reading.csv のままである。

クライアントのサンプルフローの接続先には使えない：ノードは接続のたびに空のファイルシステムを作り直すため、一覧は常に空になり、取得もできない。

演習3：受け取ったファイルを種類ごとに振り分ける上級

ネットワークカメラが画像を、計測器が CSV を、同じ FTP サーバーへ送ってくる。届いたファイルを拡張子で見分け、画像は /tmp/inbox/images/ へ、それ以外は /tmp/inbox/others/ へ保存するフローを組んでほしい。

作る処理のイメージ:

💼 使いどころ: 同じ場所に届くファイルを種類ごとに振り分けて保存したい場面で使います。

作るもの:

動作の確かめ方: フローをデプロイしたあと、ターミナル（Windows ではコマンドプロンプト）で、次の 1〜2 を順に進める。

  1. 送るファイルを2つ用意して、そのフォルダへ移る。振り分けはファイル名だけで決まるので、photo.JPG は本物の画像でなくてよい。次のコマンドは、ホームフォルダに ftp-test というフォルダを作り、その中に、hello と1行だけ書いたファイルを2つ作る。新しいフォルダの中に作るのは、ホームフォルダにある同じ名前の自分のファイルを上書きしないためである。ftp-test というフォルダを既に使っていて、その中に同じ名前のファイルがあるときは、上書きされる。そのときは、コマンドの ftp-test を別の名前に書き換える。

    macOS と Linux：

    mkdir -p ~/ftp-test cd ~/ftp-test echo hello > photo.JPG echo hello > reading.csv

    Windows：

    mkdir "%USERPROFILE%\ftp-test" cd /d "%USERPROFILE%\ftp-test" echo hello > photo.JPG echo hello > reading.csv

    どの行も、何も表示されずに入力待ちに戻れば、できている。Windows でやり直したときは、1行目で、フォルダが既に存在するという表示が出る。そのまま2行目へ進んでよい。

  2. 2つのファイルを、1つずつ送る。
    curl -T photo.JPG ftp://localhost:7021/ --user camera:change-me curl -T reading.csv ftp://localhost:7021/ --user camera:change-me

PowerShell で実行する場合：1〜2 を次のように書く。%USERPROFILE% の代わりに $HOME と書き、curl は curl.exe と書く（理由は 10 章の「手元で試すには」）。

PowerShell では、1行目の mkdir だけ、作ったフォルダの情報（Directory: で始まる表）が表示される。それで正常である。

うまくいかないとき：curl: で始まる行が出たら、送信は失敗している。行の中身から、どこを確かめればよいかが分かる。

  • curl: Can't open 'photo.JPG'：送るファイルを開けない。1 のコマンドでファイルを作ったかと、今いるフォルダが ftp-test かを確かめる
  • curl: (7) Failed to connect to localhost port 7021：ポート 7021 に接続できない。この演習のフローをデプロイしたかを確かめる。待ち受けていれば、ftp server ノードの下に、:7021 - IDLE で終わる青いステータスが出ている
  • curl: (67) Access denied: 530：ユーザー名かパスワードが違う。ftp server ノードの Username と Password が、camera と change-me になっているかを確かめる

演習4：2人でファイルを送る（社内 LAN）上級

2人1組になり、Aさんが FTP サーバーでファイルを受け取って保存し、Bさんが FTP クライアントで Aさんへファイルを送るフローを、それぞれ組んでほしい。演習1〜3の相手は、同じ PC の中か、インターネット上の試験用サーバーだった。この演習では、社内 LAN にある相手の Node-RED へ、実際にネットワークを越えてファイルを送る。

作る処理のイメージ:

💼 使いどころ: LAN の中の機器（カメラ、計測器、別の PC の Node-RED など）からファイルを受け取る場面と、LAN の中の FTP サーバーへファイルを送る場面で使います。

社内 LAN での学習に限って行う：

FTP は、ユーザー名とパスワードも、ファイルの中身も、暗号化せずに送る（2 章）。同じ LAN にいる人には読み取られうるので、パスワードには演習用の値（change-me）だけを使い、ふだん使っているパスワードを入れない。Aさんが開けたポートには、ユーザー名とパスワードを知っていれば、同じ LAN の誰でもファイルを送れる。終わったら、Aさんはフローを削除するか、タブを無効にしてデプロイし、ポートを閉じる。

自分の IP アドレスの調べ方: Aさんが、自分の PC で調べる。

Windows（コマンドプロンプト）：

ipconfig

使っている接続（Wi-Fi やイーサネット）の「IPv4 アドレス」の行が、IP アドレスである。

ラズパイと Linux：

hostname -I

Mac は、「システム設定」の「ネットワーク」で、使っている接続（Wi-Fi など）の「詳細」を開き、「TCP/IP」の「IPアドレス」を見る。詳しくはローカル/ラズパイ演習ガイドの共通の準備にある。

ftp server ノードの下に出るアドレス: デプロイすると、Aさんの ftp server ノードの下に 192.168.1.10:7041 - IDLE のような表示が出る。先頭は、ノードが自動で選んだ、この PC の IP アドレスである。VPN や仮想のネットワークがある PC では、社内 LAN のものと違うアドレスが出ることがある。そのときは、ノードの「IP」の欄に、上で調べた社内 LAN の IP アドレスを入れて、デプロイし直す。

ファイアウォール: FTP は、ログイン用の 7041 番のほかに、ファイルを運ぶための 7042〜7052 番も使う（2 章のパッシブモード）。Windows では、Defender ファイアウォールが受信をブロックすることがある。初回の待ち受けのときに出る許可のダイアログで許可するか、7041 番と 7042〜7052 番の両方の受信を許可する（Windows 編）。Mac でファイアウォールをオンにしているときは、初回に出るダイアログで許可する。ラズパイや Linux で ufw を使っているときは、9 章の「ポートを開ける範囲」の例にならって、7041 番と 7042〜7052 番を許可する。

Aさんのノード:

  • ftp server：Port、Passive Mode Port Range、Username、Password を上の値にする。Username を入れると、ノードが自分でログインを判定するので、出力2は配線しなくてよい
  • Change：届いたファイルの名前は msg.topic に入る。msg.filename に、「JSONata式」型の "/tmp/ftp-lan/" & $split(topic, "/")[-1] を設定して、保存先のパスを作る
  • file（書き込み）：「ファイル名」を msg.filename にし、「ディレクトリが存在しない場合は作成」をオンにする
  • file in（読み出し）：保存したファイルを読み直すと、中身を文字として debug に出せる。ftp server の出力の msg.payload はバイナリ（Buffer）なので、そのままでは読みにくい

Bさんのノード:

  • file（書き込み）：「ファイル名」を /tmp/ftp-send/from-b.txt にし、「ディレクトリが存在しない場合は作成」をオンにする
  • ftp in：Operation を put にする。「ローカルファイル名」は、Bさんの PC にある送るファイル（/tmp/ftp-send/from-b.txt）、「ファイル名」は、Aさんの側での名前（/from-b.txt）である
  • FTP の接続設定：ホストに Aさんの IP アドレス、ポートに 7041、ユーザ名に guest、パスワードに change-me を入れる

Windows では、/tmp/ftp-send/ と /tmp/ftp-lan/ は、Node-RED を起動したドライブの直下の \tmp\ftp-send\ と \tmp\ftp-lan\（多くは C ドライブ）になる。

12. まとめ

要点：
  • 立ち位置は4つある。取りに行くなら ftp in か sftp in、受けるなら ftp server か OS の OpenSSH
  • SFTP は FTP の暗号化版ではなく、SSH の機能の一つである。ポートも 22 で別物
  • get はファイルの中身を payload に返さない。ローカルへ保存するだけなので、中身を使うなら file in で読み直す
  • ftp server が受け取ったファイルはディスクに残らない。file ノードへ繋いで自分で保存する
  • SFTP のサーバー側は OS の OpenSSH が担う。Node-RED は watch ノードで置かれたファイルを拾う
  • 平文 FTP は LAN の中と検証用に限る。外へ出すなら SFTP を選ぶ

次に読むとよいガイド

  • file ノードガイド：転送したファイルを読み書きする
  • watch ノードガイド：フォルダに置かれたファイルを見つける
  • exec ノードガイド：FTPS や rsync など、ノードで足りない転送を外部コマンドで行う
  • 本番運用ガイド：受信フォルダの肥大化と保持期間の管理
  • Linux ディレクトリガイド：パスと権限の読み方
