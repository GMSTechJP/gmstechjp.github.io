1. 通信は成功しているのに値が合わない

MODBUS の設定が正しく通り、debug ノードに数値が並んだ。ところが表示器が 25.3℃ を示しているのに、Node-RED には 253 が届く。冷えていて −1.3℃ のはずの場所が 65523 になる。温度が小数で来るはずの機器から 2.34e-41 という見たこともない値が返る。

これらはいずれも通信の失敗ではない。数値は正しく届いている。届いた数値をどう解釈するかが決まっていないだけである。

レジスタは型を持たない。1つのレジスタは 16 個のビットが並んだ箱でしかなく、その中身が温度なのか、カウンタの下半分なのか、16 個のスイッチの状態なのかは、箱を見ても分からない。解釈のしかたは機器の仕様書に書いてあり、それを読む側が設定する。

解釈のずれは4種類に絞れる。符号、ワード順、倍率、詰め込み方である。この4つを順に確かめれば、値の食い違いはたいてい解ける。アドレスの指定そのものが誤っている場合は、この4つでは直らない。

2. レジスタという器

PLC やインバータの内部は、番号のついた小さな箱が並んだ構造になっている。この箱1つがレジスタで、大きさは 16 ビット（2バイト）と決まっている。

単位 大きさ そのまま入る値の範囲 使われ方
ビット 1 bit 0 か 1 運転中や異常ありといった ON/OFF
ワード 16 bit（レジスタ1個） 0 〜 65535 温度、圧力、設定値などの整数
ダブルワード 32 bit（レジスタ2個） 0 〜 4294967295 積算カウンタ、小数を含む実数

16 ビットで表せるのは 0 から 65535 までである。これより大きい値、負の値、小数を含む値は、この箱にそのままでは入らない。そこで機器のメーカーは、何らかの工夫をして押し込む。その工夫が、読む側から見た「解釈のしかた」になる。

コイルとレジスタの区別： MODBUS には ON/OFF 専用の入れ物（Coil・Discrete Input）と、16 ビットの入れ物（Input Register・Holding Register）の4種類がある。このガイドが扱うのは後者2つで、4種類の使い分けは MODBUS ノードガイドの「データモデル」で説明している。

Node-RED にはどう届くか

MODBUS ノードでレジスタを読むと、msg.payload には数値の配列が入る。読み出し個数を3個に指定したなら、要素が3つの配列になる。

msg.payload = [253, 65523, 40000] ↑ ↑ ↑ アドレス+0 +1 +2

この配列の各要素が、上の表の「ワード」に相当する。値はすべて 0 〜 65535 の範囲で届く。負の数や小数がここに現れることはない。届いた時点では、まだ何の解釈もされていない生の値である。

3. 症状から原因を引く

値が合わないとき、症状を見れば原因はおおよそ絞れる。

症状 疑う原因 参照
桁だけが違う（25.3 が 253、12.34 が 1234） 倍率が掛かっている 6. スケーリング
負のはずの値が 65000 台の大きな数になる 符号ありの値を符号なしで読んでいる 4. 符号
正のはずの値が突然マイナスになる 符号なしの値を符号ありで読んでいる 4. 符号
2.34e-41 や 20 億のような極端な値になる 32bit 値のワード順が逆 5. ワード順
小数のはずが整数しか出ない、値が飛び飛びになる 32bit の値を 16bit として読んでいる 5. 2レジスタに跨る値
表示器の 1234 が 4660 として届く BCD 形式 7. BCD
0 か 1 のはずが 5 や 13 になる 1つのレジスタに複数のビットが詰まっている 7. ビットの取り出し
値がまったく変化しない、常に 0 アドレスがずれている（解釈の問題ではない） MODBUS ガイドの 0 始まり問題

4. 符号ありと符号なし

16 ビットの箱には 0 〜 65535 しか入らない。ではマイナス 13 をどう表すか。上位半分（32768 以上）を負の数の領域として割り当てる方法が使われる。これを符号あり（signed）といい、−32768 〜 32767 の範囲を表せる。

符号なし (unsigned) : 0 ─────── 32767 │ 32768 ─────── 65535 符号あり (signed) : 0 ─────── 32767 │ -32768 ─────── -1 ↑ 同じビットの並びを、境界の先でどう読むかが違う

境界より下では両者は一致する。食い違うのは 32768 以上に入ったときだけである。

届いた値 16進 符号なしとして 符号ありとして 0.1 倍したとき
253 00 FD 253 253 25.3
65523 FF F3 65523 −13 −1.3
65535 FF FF 65535 −1 −0.1
40000 9C 40 40000 −25536 −2553.6

65523 と −13 は、同じビットの並びである。どちらが正しいかはデータの意味で決まる。

どちらで読むかの見分け方

  • 仕様書に「signed」「符号付き」「−32768〜32767」とあれば符号あり
  • 負の値がありうる量（温度、電流の向き、偏差、傾き）は符号ありが多い
  • 負になりえない量（積算値、回転数、圧力）は符号なしが多い
  • 普段は小さい正の値なのに、ある条件で急に 65000 台に跳ぶなら符号あり

40000 の行に注意： 符号ありとして読むと −25536 になる。もし積算流量のような「負にならない量」でこの値が出たなら、符号なしで読むのが正しい。逆に、温度が突然 −25536℃ になったら符号の取り違えを疑う。値の妥当性が判断材料になる。

Node-RED での変換

MODBUS ノードから届く配列は、すべて符号なしの値である。符号ありとして扱うには変換が要る。境界を超えていたら 65536 を引く、という処理になる。

const raw = msg.payload[0]; const signed = raw > 32767 ? raw - 65536 : raw; msg.payload = signed; return msg;

5. 32bit の値は2つのレジスタに跨る

積算カウンタや小数を含む実数は、16 ビットに収まらない。そこでレジスタ2個を1組にして 32 ビットとして使う。ここで問題になるのが、2つのレジスタのどちらが上位かである。

まず、跨いでいることに気づく

32 ビットの値を 16 ビットとして読むと、上半分か下半分だけが見えることになる。

積算カウンタ 100000 = 0x000186A0 レジスタに入っている姿 : [1, 34464] 上位のレジスタだけ読むと : 1 ← 「値が 1 のまま増えない」 下位のレジスタだけ読むと : 34464 ← 「65535 を超えると 0 に戻ってしまう」

カウンタが増えないように見える、あるいは 65535 で一周してしまう場合は、2レジスタ組で読むべき値を1つだけ読んでいる可能性が高い。

ワード順とバイト順

32 ビットは4バイトからなる。この4バイトを、上位から順に A B C D と呼ぶ約束が、PLC の仕様書では広く使われる。機器がどの順で送ってくるかは、この4文字の並びで表記される。

表記 仕様書での呼ばれ方 何が入れ替わるか
ABCD Big Endian / High word first 入れ替えなし。MODBUS の標準的な並び
CDAB Word Swap / Low word first ワード（2バイト）の順が逆。最も多い食い違い
BADC Byte Swap 各ワードの中のバイトが逆
DCBA Little Endian 4バイトが完全に逆順

バイト順とワード順が別々に入れ替わる仕組みそのものは、buffer-parser ガイドの「基礎知識：バイト順とワード」で図解している。ここでは、この4通りが実際の値としてどう見えるかに絞る。

4通りで読むとどうなるか

温度 12.5℃ を 32 ビットの小数（float）で送る機器を例にする。12.5 のバイト列は 41 48 00 00 で、これがレジスタ配列 [16712, 0] として届いたとする。この配列を4通りに解釈すると、次のようになる。

解釈 並べ替え後のバイト列 読み取れる値
ABCD（そのまま） 41 48 00 00 12.5
CDAB（ワード入れ替え） 00 00 41 48 2.3418e-41
BADC（ワード内で入れ替え） 48 41 00 00 197632
DCBA（完全に逆） 00 00 48 41 2.5920e-41

意味の通る値は 12.5 だけである。よってこの機器は ABCD だと判断できる。

逆に、同じ 12.5℃ をワード順が逆の機器から受け取ると、配列は [0, 16712] になる。このときは CDAB として読んだ場合だけが 12.5 になり、そのまま読むと 2.3418e-41 が出る。

float の取り違えは見分けやすい。ワード順を間違えた float は、e-41 のような極端に小さい値か、桁が大幅に違う値になる。温度や圧力としてありえない値が出たら、まずワード順を疑えばよい。

32bit 整数の取り違えは見分けにくい： float と違い、整数はワード順を間違えても「それらしい大きな数」になる。100000 のワード順を逆に読むと 2258632705 になり、一見すると単に大きなカウンタに見える。値を動かしながら、増え方が滑らかかどうかで確かめる必要がある。

メーカーによって違う

ワード順は MODBUS の規格で決められていない。同じ float であっても、メーカーごと、機種ごと、さらには同じ機種でも設定によって変わる。仕様書では「Word Order」「Byte Order」「Data Format」「32bit register order」といった見出しで書かれていることが多い。

複数メーカーの機器を1つのフローで扱う場合、機器ごとに別々の解釈を用意することになる。

6. 生値と実際の値（スケーリング）

整数のレジスタで小数を表す方法として、あらかじめ 10 倍や 100 倍した値を入れておく方式が広く使われる。25.3℃ なら 253 を、12.34 kW なら 1234 を格納する。

実際の値 = 生値 × 係数 + オフセット 25.3℃ ← 253 × 0.1 12.34kW ← 1234 × 0.01 -13℃ ← 65523 を符号ありにして -13、× 1.0

仕様書では「分解能 0.1℃」「単位 0.01kW」「スケール 1/10」といった書き方をされる。倍率だけの食い違いは、値の桁を見ればすぐ分かる。表示器の数字と届いた数字を並べ、小数点の位置だけがずれているなら倍率である。

仕様書の記述 掛ける数 例
分解能 0.1℃ / 単位 0.1℃ 0.1 253 → 25.3
1/100 単位 / 0.01kW 0.01 1234 → 12.34
×10 倍値で格納 0.1 1005 → 100.5

オフセットが要る場合

0 から始まらない量を扱う機器では、下限値がオフセットとして加わる。たとえば 4〜20mA の信号を 0〜65535 の範囲に割り当てて、その両端に 0〜100% を対応させる機器がある。

実際の値 = 生値 × (最大値 - 最小値) / 65535 + 最小値 生値 32768 、範囲 0〜100% のとき → 32768 × 100 / 65535 + 0 ≒ 50.0%

この形の変換は Range ノードが担当する。入力の範囲と出力の範囲を指定するだけで、Function を書かずに変換できる。倍率だけなら Change ノードの JSONata でも足りる。

書き込むときは逆にする

設定値を機器へ書き込む場合、同じ係数で割る必要がある。目標温度 25.3℃ を設定するなら、レジスタへ書くのは 253 である。読むときの変換だけを実装して書き込み側を忘れると、設定値が 10 分の 1 になる。

7. 1つのレジスタに複数の情報

16 ビットを1つの数値として使わず、細かく分けて使う機器も多い。

ビット単位の状態

運転中、異常、準備完了といった ON/OFF を、1つのレジスタに 16 個まで詰め込める。この場合、レジスタの値を数値として読んでも意味をなさない。

レジスタ値 13 = 2進で 0000 0000 0000 1101 bit0 = 1 運転中 bit1 = 0 停止中ではない bit2 = 1 警報あり bit3 = 1 メンテナンス要求

「状態が 0 か 1 のはずなのに 5 や 13 が返る」という症状は、この形式であることのサインである。特定のビットを取り出すには、右へずらして最下位だけを見る。

// bit2 を取り出す const raw = msg.payload; const bit2 = (raw >> 2) & 1; msg.payload = bit2 === 1; return msg;

ビット番号の数え方に注意： 仕様書によって最下位を bit0 と呼ぶ場合と bit1 と呼ぶ場合がある。1つずれると、隣の状態を読んでしまう。機器を実際に動かし、想定したビットが変化するかを確かめてから確定する。

BCD（表示用の10進形式）

表示器やカウンタでは、10 進数の各桁を4ビットずつに割り当てる BCD という形式が使われることがある。1234 という表示値は、16 進で 0x1234 として格納される。これを普通の整数として読むと 4660 になる。

レジスタ値 16進表記 整数として読むと BCD として読むと
4660 0x1234 4660 1234
595 0x0253 595 253
13 0x000D 13 成立しない

BCD かどうかは、値の見た目から判断できる。16 進で表したときに A〜F が現れたら、そのデータは BCD ではない。各桁が 0〜9 に収まっているデータで、表示器の数字と 16 進表記が一致するなら BCD である。

// BCD として読む（各桁が 0〜9 のときだけ成立する） let bcd = 0; let isBcd = true; for (let i = 3; i >= 0; i--) { const digit = (msg.payload >> (i * 4)) & 15; if (digit > 9) { isBcd = false; break; } bcd = bcd * 10 + digit; } msg.payload = isBcd ? bcd : null; return msg;

8. 実機で正体を突き止める手順

仕様書が手元にある場合は、そこに答えが書いてある。無い場合や記述が曖昧な場合は、実物から突き止めることになる。

手順1：仕様書の該当欄を探す

通信仕様の章に、次のような見出しがある。訳語は各社まちまちである。

探す語 分かること
Data Type / データ形式 / signed・unsigned 符号の有無、16bit か 32bit か
Word Order / Byte Order / エンディアン 2レジスタ組のワード順
分解能 / Resolution / Scale / 単位 掛けるべき係数
ビット定義 / Bit assignment 1レジスタ内のビットの割り当て

手順2：既知の値を作って照合する

機器の表示器に出ている値、あるいは自分で設定した値と、届いた生値を突き合わせる。これが最も確実である。

  • 表示が 25.3℃ のとき 253 が届いたなら、係数は 0.1
  • 設定値を 0 にしたとき 0 が返り、100 にしたとき 10000 が返るなら、係数は 0.01
  • 値をゆっくり動かし、届く数値が滑らかに追随するかを見る

手順3：4通りを総当たりする

32 ビット値のワード順が分からないときは、4通り全部で読んで、意味の通る値を選ぶ。後述のサンプルフローがこれを一度に表示する。

手順4：妥当な範囲で絞る

解釈の候補が複数残ったら、物理的にありえるかどうかで判断する。

  • 室温が −300℃ や 1e38 になっていたら、その解釈は誤り
  • 積算流量が減ることはない。減っているなら符号かワード順が誤り
  • 回転数が毎秒 100 万回転になっていたら、桁が誤り

順番のこつ： 符号 → ワード順 → 係数 の順に確かめると早い。係数は最後に効くため、符号やワード順が誤ったまま係数だけを合わせようとしても、値は合わない。

9. Node-RED での実装

解釈が決まったら、変換を Node-RED で実装する。方法は2つある。

Function ノードで書く

取り出す項目が少ないなら、Function ノードで直接書くのが手早い。レジスタ配列を Buffer に組み立ててから読むと、符号やワード順の扱いを標準のメソッドに任せられる。

// レジスタ2個から 32bit float を取り出す（ABCD の機器の場合） const w = msg.payload; const buf = Buffer.alloc(4); buf.writeUInt16BE(w[0], 0); buf.writeUInt16BE(w[1], 2); msg.payload = buf.readFloatBE(0); return msg;
読みたい型 使うメソッド 必要なレジスタ数
符号なし 16bit readUInt16BE(0) 1
符号あり 16bit readInt16BE(0) 1
符号なし 32bit readUInt32BE(0) 2
符号あり 32bit readInt32BE(0) 2
32bit 小数 readFloatBE(0) 2

ワード順が CDAB の機器なら、Buffer へ書き込む順を入れ替えるだけでよい。

// CDAB の機器：下位ワードが先に届く buf.writeUInt16BE(w[1], 0); buf.writeUInt16BE(w[0], 2);

buffer-parser ノードで設定にする

取り出す項目が多い場合、Function のコードは長くなり、型やオフセットの取り違えを見つけにくくなる。buffer-parser ノードを使うと、同じ変換を表形式の設定として書ける。ワード順の入れ替えは Byte swap の設定で吸収でき、係数は scale 欄に書ける。

状況 向いている方法
取り出す項目が1〜2個 Function ノード
取り出す項目が多い、機器ごとに設定が違う buffer-parser ノード
解釈を探っている最中 Function ノード（4通りを一度に出せる）
追加パッケージを入れられない環境 Function ノード

10. サンプルフロー

実機がなくても解釈の練習ができるよう、レジスタの値を inject ノードで模擬する。届いた配列を Function で解釈し、debug に出す構成である。標準ノードだけを使うため、追加パッケージは要らない。

inject（模擬レジスタ） → function（解釈） → debug

3本のラインが入っている。

  • 符号の確認 — [253, 65523, 40000] を符号なしと符号ありの両方で表示する
  • ワード順の総当たり — 2レジスタを4通りに解釈し、意味の通る値を探す
  • ビットと BCD — 1レジスタの中身をビット単位と BCD の両方で表示する

12. まとめ

論点 要点
レジスタ 16 ビットの箱。型の情報を持たないため、解釈は読む側が決める
符号 32768 以上が負の領域になる。65523 と −13 は同じビットの並び
ワード順 32bit 値は 2 レジスタに跨る。ABCD / CDAB / BADC / DCBA の4通りがあり、規格で決まっていない
スケーリング 整数で小数を表すため、10 倍や 100 倍された値が入っている。書き込むときは逆に割る
詰め込み 1レジスタに 16 個の ON/OFF、あるいは BCD の 4 桁が入ることがある
調べ方 符号 → ワード順 → 係数 の順に確かめる。既知の値との照合が最も確実

  • 変数ガイド Part 1：バイナリデータとBuffer — バイトと文字コードの基礎

13. トラブルシューティング

症状 原因 対処
値が 10 倍や 100 倍で表示される 係数を掛けていない 仕様書の分解能を確認し、0.1 や 0.01 を掛ける
負のはずが 65000 台になる 符号ありの値を符号なしで読んでいる 32767 を超えたら 65536 を引く、または readInt16BE を使う
正のはずが負になる 符号なしの値を符号ありで読んでいる readUInt16BE に変える
小数が 2.34e-41 のような値になる 32bit float のワード順が逆 Buffer へ書き込む順を入れ替える（CDAB として読む）
カウンタが 65535 で 0 に戻る 32bit 値を 16bit として読んでいる 2レジスタを読み、readUInt32BE で組み立てる
カウンタの値が 1 のまま増えない 32bit 値の上位ワードだけを読んでいる 読み出し個数を 2 にする
状態が 0 か 1 でなく 5 や 13 になる 1レジスタに複数のビットが詰まっている 目的のビットを (raw >> n) & 1 で取り出す
取り出したビットが隣の状態を指す 仕様書のビット番号が 1 始まり 実機を動かして、変化するビットの位置を確かめる
表示器の 1234 が 4660 になる BCD を整数として読んでいる 16 進の各桁を 10 進の桁として組み立て直す
値がまったく変化しない 解釈ではなくアドレスの問題 アドレスの 0 始まりを確認する（MODBUS ガイド）
読みは合うのに書き込みが 10 分の 1 になる 書き込み側で係数を割っていない 書き込む前に係数で割る
